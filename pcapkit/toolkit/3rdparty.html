3rd-Party Support¶

The adapters below are best effort (#1687): they need not match the Built-in Support adapters one to one, since protocol rules belong in the default engine only, so the same capture can reassemble or trace differently from one engine to the next. Engine Support tabulates the gaps.

Scapy Tools¶

pcapkit.toolkit.scapy contains the adapters for the Scapy engine. The reassembly and flow tracing adapters return the data their pcapkit.foundation counterpart consumes, or None if the frame cannot be used for it.

Warning

This module requires Scapy to be installed.

pcapkit.toolkit.scapy.ipv4_reassembly(packet, *, count=-1)[source]¶

Make data for IPv4 reassembly.

A packet can be reassembled if it contains an IPv4 layer (scapy.layers.inet.IP) whose header – as many octets as its IHL counts, and at least 20 – lies inside the frame and every IP datagram carrying it (see _within_datagrams()), and the DF (scapy.layers.inet.IP.flags.DF) flag is False. A zero-length frame has none, though Scapy hands it back as an IPv4 layer of defaults at the RAW and IPV4 link types (see _frame()).

Parameters:

  • packet (scapy.packet.Packet) – Scapy packet.

  • count (int) – Packet index. If not provided, defaults to -1.

Return type:

Packet[IPv4Address] | None

Returns:

Data for IPv4 reassembly (reasm.ipv4.packet) if the packet can be reassembled; otherwise None.

See also

pcapkit.foundation.reassembly.ipv4.IPv4

pcapkit.toolkit.scapy.ipv6_reassembly(packet, *, count=-1)[source]¶

Make data for IPv6 reassembly.

A packet can be reassembled if it contains an IPv6 layer (scapy.layers.inet6.IPv6), in no later IPv4 fragment, and an IPv6 Fragment header (RFC 2460 Section 4.5, i.e., scapy.layers.inet6.IPv6ExtHdrFragment) among the extension headers Scapy dissects in that layer’s own chain.

Parameters:

  • packet (scapy.packet.Packet) – Scapy packet.

  • count (int) – Packet index. If not provided, defaults to -1.

Return type:

Packet[IPv6Address] | None

Returns:

Data for IPv6 reassembly (reasm.ipv6.packet) if the packet can be reassembled; otherwise None.

Raises:

ModuleNotFound – If Scapy is not installed.

See also

pcapkit.foundation.reassembly.ipv6.IPv6

Note

A later IPv4 fragment’s data is a slice of the datagram’s payload, with no upper-layer header in it (RFC 791 Section 3.2), but Scapy dissects IPv6 there whatever the fragment offset. And the header and addresses handed on are those of the IPv6 layer the Fragment header follows, so one inside a packet that layer carries, such as the inner packet of 6in6, is not taken.

pcapkit.toolkit.scapy.tcp_reassembly(packet, *, count=-1)[source]¶

Make data for TCP reassembly.

A packet can be reassembled if it contains a TCP layer (scapy.layers.inet.TCP) whose fixed header lies inside its datagram, and whose Data Offset counts at least that header, in no later IPv4 fragment; or a TCP segment behind an AH or IPv6 extension header in IPv4, read off the octets. It is keyed by the IP layer that carries it – in an IP-in-IP tunnel, the innermost (see _tcp_carrier()).

Parameters:

  • packet (scapy.packet.Packet) – Scapy packet.

  • count (int) – Packet index. If not provided, defaults to -1.

Return type:

Packet | None

Returns:

Data for TCP reassembly (reasm.tcp.packet) if the packet can be reassembled; otherwise None.

See also

pcapkit.foundation.reassembly.tcp.TCP

pcapkit.toolkit.scapy.tcp_traceflow(packet, *, count=-1)[source]¶

Trace packet flow for TCP.

A packet can be traced if it contains a TCP layer (scapy.layers.inet.TCP), on the terms tcp_reassembly() sets.

Parameters:

  • packet (scapy.packet.Packet) – Scapy packet.

  • count (int) – Packet index. If not provided, defaults to -1.

Return type:

Packet | None

Returns:

Data for TCP flow tracing (trace.tcp.packet) if the packet can be traced; otherwise None.

See also

pcapkit.toolkit.scapy.packet2dict(packet)[source]¶

Convert Scapy packet into dict.

Parameters:

packet (scapy.packet.Packet) – Scapy packet.

Return type:

dict[str, Any]

Returns:

A dict mapping of packet data. Its packet is the octets of the frame (see _frame()), none for a zero-length one. Each layer carries only the fields set on it (for a dissected packet, those read from the wire, with no defaults filled in). Field values that are themselves Scapy packets (e.g. IP options, DNS records), including those inside lists, are converted recursively. The packet itself is not modified.

Raises:

ModuleNotFound – If Scapy is not installed.

pcapkit.toolkit.scapy.packet2frame(packet)[source]¶

Report a Scapy packet to the flow tracer, with its PCAP frame record.

Parameters:

packet (scapy.packet.Packet) – Scapy packet.

Return type:

FrameRecord

Returns:

The packet2dict() mapping of the packet, which every trace format but PCAP writes unchanged, carrying the octets Scapy dissected the packet from, the PCAP record header the PCAP trace dumper writes, and the exact timestamp it reads the header’s resolution from.

Raises:

ModuleNotFound – If Scapy is not installed.

Note

The octets are packet.original, which Scapy’s readers keep as read, rather than bytes(packet), which rebuilds them; for a packet not read from a capture, such as one built by hand, they are the octets it builds into (see _frame()). orig_len is packet.wirelen, the record’s original length.

The fraction in frame_info.ts_usec is in the capture’s own resolution. That resolution is the one Scapy attaches with attach_resolution(), never one guessed from the value: a nanosecond count that is a whole number of microseconds has the same digits as the microsecond count. A packet that carries none, e.g. one built by hand, is taken to count microseconds.

pcapkit.toolkit.scapy._frame(packet)[source]¶

Return the octets of the frame a Scapy packet stands for.

Parameters:

packet (scapy.packet.Packet) – Scapy packet.

Return type:

bytes

Returns:

For a packet read from a capture, which every Scapy reader gives a wirelen, the record’s original length, packet.original: the octets of the record, which the readers keep as read. For any other, such as one built by hand, bytes(packet): the octets it builds into.

Note

Scapy dissects a packet only from a non-empty string, so a zero-length frame comes back as the first layer its link type names, every field left to its default. bytes() of it builds a header out of nothing – 20 octets at RAW and IPV4, 14 at ETHERNET – where the record has none (#1676).

pcapkit.toolkit.scapy._within_datagrams(layer)[source]¶

Return the octets from layer on that lie inside every IP datagram carrying it.

Parameters:

layer (scapy.packet.Packet) – A layer of a dissected Scapy packet.

Return type:

bytes

Returns:

The octets of layer and everything after it, up to the nearest end that the Total Length or Payload Length of an IP layer above it declares.

Note

When Scapy dissects an IP layer, it files whatever follows the datagram’s declared length as a Padding layer – an Ethernet frame’s padding up to its 60-octet minimum, or a trailer such as an FCS – and bytes() of any layer above that one ends with it. Those octets are no part of the datagram (#1584), so they are cut off here. An IPv4 Total Length of zero, as TCP segmentation offload leaves, declares nothing, so the datagram runs to the end of the frame (#1547); an IPv6 Payload Length of zero gives way to a Jumbo Payload option (#1434), whose length is read here rather than left to Scapy, which reads it in host byte order and adds the Hop-by-Hop Options header to it a second time.

Every IP layer above layer bounds it, not only the nearest: a datagram tunnelled in IP may declare more than the one carrying it holds, or nothing at all. An IPv4 layer built by hand has no ihl until it is built, so one given a Total Length alone has its IHL read off the octets it builds into (#1676).

pcapkit.toolkit.scapy._tcp_carrier(packet)[source]¶

Fetch the TCP segment of a Scapy packet, and the IP layer that carries it.

Parameters:

packet (scapy.packet.Packet) – Scapy packet.

Return type:

tuple[scapy.layers.inet.IP | scapy.layers.inet6.IPv6, scapy.layers.inet.TCP, bytes, bytes] | None

Returns:

The nearest IP or IPv6 layer above the packet’s TCP layer, that layer, and the segment’s header and payload (see _tcp_segment()); or None if there is no such IP layer, or an IPv4 layer above it is a later fragment, whose data is a slice of the datagram’s payload with no upper-layer header in it (RFC 791 Section 3.2, #1617).

An IPv4 layer whose protocol names an AH or IPv6 extension header (IPV4_EXTENSION_HEADERS) has those headers stepped over in its octets, up to EXTENSION_HEADER_LIMIT of them in a row (see _walk_extension_headers()), and what follows them is dissected from the octets: a tunnel, walked on as above, or a TCP segment (see _tcp_behind_extension_headers(), #1606). In the datagram an ICMP error quotes, they are left as Scapy dissects them.

Note

The nearest is the innermost IP layer of an IP-in-IP tunnel (RFC 2003, RFC 2473, RFC 4213), whose addresses are the TCP endpoints’ (#1581). packet['IP'] finds the outermost IPv4 layer instead, which is the tunnel’s, or with IPv4 carried in IPv6 the inner one. The extension header layers Scapy dissects between an IPv6 layer and its payload are not IP layers, so are stepped over.

Inside IPv4, Scapy dissects an AH alone of those headers, and behind one only IPv6 and, for a Next Header of 0, IPv4, so the octets are read instead. It also dissects IPv6 and AH inside a later fragment, binding neither to a zero fragment offset as it binds TCP.

pcapkit.toolkit.scapy._tcp_segment(tcp)[source]¶

Split the TCP segment tcp heads into its header and its payload.

Parameters:

tcp (scapy.layers.inet.TCP) – TCP layer of a dissected Scapy packet.

Return type:

tuple[bytes, bytes] | None

Returns:

The header, as many octets as the Data Offset counts, and the payload after it, up to the end of the datagrams that carry the segment, cf. _within_datagrams(); or None if the datagrams hold fewer than the 20 octets of the fixed header, or the Data Offset counts fewer (RFC 9293 Section 3.1), as there is then no header to split off.

Note

The Data Offset is read off the octets, which for a dissected layer carry the dataofs Scapy read, and for a layer built by hand the one it builds, as it leaves dataofs None until then (#1676).

pcapkit.toolkit.scapy._tcp_behind_extension_headers(segment)[source]¶

Split a TCP segment carried behind an AH or IPv6 extension header in IPv4.

Parameters:

segment (bytes) – Raw octets from the TCP header on, as far as the IPv4 layer carrying it goes (see _tcp_carrier()).

Return type:

tuple[bytes, bytes] | None

Returns:

The header, as many octets as the Data Offset counts, and the payload after it; or None if there are fewer than TCP_MIN_HEADER_LEN octets, the Data Offset counts fewer or more than were captured, or pcapkit’s own TCP parser rejects the options (see _default_accepts()).

Note

Scapy dissects no TCP layer there (see _tcp_carrier()), so the segment is read off the octets, and its options are left to pcapkit’s parser to check.

DPKT Tools¶

pcapkit.toolkit.dpkt contains the adapters for the DPKT engine. The reassembly and flow tracing adapters return the data their pcapkit.foundation counterpart consumes, or None if the frame cannot be used for it.

pcapkit.toolkit.dpkt.ipv4_reassembly(packet, timestamp, *, count=-1)[source]¶

Make data for IPv4 reassembly.

A packet can be reassembled if its network layer is IPv4 (dpkt.ip.IP) – one carried in IPv6 is not read – whose header was captured whole, and the DF (dpkt.ip.IP.df) flag is False.

Parameters:

  • packet (dpkt.dpkt.Packet) – DPKT packet.

  • timestamp (float) – Capture timestamp of the packet, which drives the reassembly timeout. DPKT’s reader yields it beside the record’s octets rather than on the packet, so it is passed in – as tcp_traceflow() does. A caller holding only a frame can read it back with packet2timestamp(), which is where DPKT leaves it. Handed on as a float, though DPKT reads a nanosecond PCAP’s as a Decimal (#1501), and as the one nearest the exact value it carries, if any, where DPKT’s own may be an ulp off (#1668; see _capture_time()).

  • count (int) – Packet index. If not provided, defaults to -1.

Return type:

Packet[IPv4Address] | None

Returns:

Data for IPv4 reassembly (reasm.ipv4.packet) if the packet can be reassembled; otherwise None.

Note

The header and payload are sliced out of the record octets DPKT attached to the frame, so they are the captured ones. A packet built by hand carries no such buffer, and its octets are then dpkt’s re-serialisation of it, in which a zeroed checksum or length comes back recomputed – attach_buffer() is what makes them the wire’s again. They are that re-serialisation too where dpkt’s own lengths misplace the layer in the record, as behind some stacks of VLAN tags (#1646). The packet itself is left untouched either way.

The header is the IHL’s octets, and the payload ends at the Total Length, or at the end of the frame for a zero one. A Total Length shorter than the IHL leaves the header whole and the payload empty (#1616).

See also

pcapkit.foundation.reassembly.ipv4.IPv4

Changed in version 1.5.0: timestamp is a new second positional parameter, so a 1.4.x call with packet alone fails.

Auxiliary Data¶

class pcapkit.toolkit.dpkt.RecordTimestamp[source]¶

Bases: object

A record’s capture timestamp, with what a PCAP frame record needs of it.

The readers DPKT uses yield (timestamp, octets) and nothing else, so a record’s exact timestamp, its resolution and its original length would be lost between the reader and packet2frame(). The engine’s readers yield a Timestamp or a DecimalTimestamp instead, which is the value DPKT yields – so a stored frame’s timestamp is exactly what it was before – and also carries what would otherwise be lost. Reassembly and flow tracing are handed a plain float of it (#1501): of its exact value, since DPKT’s own for a microsecond PCAP rounds twice (#1668; see _capture_time()).

A copy, a deep copy and a pickle at any protocol all rebuild a timestamp from what its __reduce__() returns, so each keeps the exact timestamp, the resolution and the original length. This class answers each of those protocols itself, ahead of the numeric base class: the pure-Python Decimal copies a subclass as type(self)(str(self)), with the constructor’s defaults for the rest (#1647).

pcapkit.toolkit.pyshark.ENCAP_TYPE_TO_LINKTYPE: dict[int, LinkType]¶

frame.encap_type – Wireshark’s internal WTAP_ENCAP_* number, which pyshark exposes as packet.frame_info.encap_type – to the matching LinkType member. This is tcp_traceflow()’s primary link-type source; FILTER_NAME_TO_LINKTYPE below is only its fallback.

A WTAP_ENCAP_* number is not a DLT: it is 25 where the DLT is 113, 15 where it is 0, and 2 where it is 6, so it needs this table rather than a cast. What it does do is distinguish encapsulations that the PDML root layer’s filter name cannot, which is the whole reason this table exists: sll is both LINUX_SLL (113) and LINUX_SLL2 (276), null is both NULL (0) and LOOP (108), raw is RAW (101), IPV4 (228) and IPV6 (229), ppp is PPP (9) and PPP_WITH_DIR (204), lapd is LAPD (203) and LINUX_LAPD (177). frame.encap_type separates every one of those pairs.

Every entry was measured, not transcribed, with editcap/tshark 4.6.9:

editcap -F pcap -T <encap> examples/captures/in.pcap out.pcap
# value := the network field at offset 20 of out.pcap's pcap file header
# key   := the frame.encap_type that `tshark -r out.pcap -c 1 -T pdml` then reports

so each pair is one round trip through Wireshark’s own wiretap/pcap-common.c, in the read direction pyshark actually exercises. In the source, the trailing comment on each line names the editcap -T encapsulation that produced it.

What the sweep does not cover, since that bounds this table: of the 226 encapsulations editcap -T accepts, 157 could be written as pcap from the Ethernet source above and the other 69 refused the rewrite, so they are untested. Those 157 yielded 153 distinct frame.encap_type keys, with no key mapping to two DLTs and no DLT reading back as two keys. Each is below except frame.encap_type 32 (editcap -T hhdlc, DLT 121), left out because LinkType has no member for 121. An encapsulation absent from this table raises rather than resolving to a near-miss DLT.

pcapkit.toolkit.pyshark.FILTER_NAME_TO_LINKTYPE: dict[str, LinkType]¶

Wireshark display-filter name -> LinkType member, used by tcp_traceflow() only when the frame layer carries no frame.encap_type field for ENCAP_TYPE_TO_LINKTYPE above to key on – every capture measured for that table did carry one, so this is a defensive path rather than the usual one. PyShark takes the name verbatim from the PDML <proto name=...> attribute, which is Wireshark’s own dissector filter name – the third argument to proto_register_protocol() in the relevant epan/dissectors/packet-*.c – and that vocabulary is not LinkType’s: Ethernet’s filter name is eth, never ETHERNET.

Every entry comes from the same sweep as ENCAP_TYPE_TO_LINKTYPE above: the root <proto name=...> of tshark -r out.pcap -c 1 -T pdml against the DLT in out.pcap’s own file header. In the source, the trailing comment on each line names the editcap -T encapsulation that produced it, so an entry can be re-checked, or corrected when upstream moves, by rerunning that one rewrite. Names are listed even where they already spell their LinkType member (docsis, fddi, pflog, …): there is deliberately no fallback onto a like-named member, because upper-casing the name is exactly what would answer 101 for a rawip6 capture and 0 for a DLT_LOOP one – valid DLTs, wrong ones, and silent (#843).

These classes of name are absent, each measured rather than assumed:

  • Ambiguous – one name, several DLTs, and the PDML node does not say which arrived. These cannot be mapped at any size: user_dlt (16 DLTs), bluetooth (6), usb (5), usbll (4), raw (3), and arcnet, gfp, i2c, lapd, mtp2, netanalyzer, null, ppp, sll, wlan, wpan (2 each).

  • Pseudo-protocols – fake-field-wrapper, which pyshark reports as data and which was the root for 29 of the swept encapsulations (no dissector), and _ws.malformed, the root for the one capture tshark could not parse. Neither names a link type.

  • Unswept – the 69 encapsulations editcap -T would not write as pcap from an Ethernet source. No evidence either way was gathered for them.

Caveats on what “unambiguous” means here. It means unambiguous within the 157 swept encapsulations: one of the 69 unswept could still root at the same name (ether-nettl and tr-nettl are the obvious candidates, for eth and tr). And some entries – llc, sctp, pppoes, fpp and irlap – name a payload dissector that happened to be the outermost PDML node for exactly one encapsulation, rather than a link-layer dissector registered against a WTAP_ENCAP_*. These caveats are why this table is the fallback and frame.encap_type is the primary key; eth and tr additionally check out against Wireshark’s own registrations (packet-eth.c on WTAP_ENCAP_ETHERNET, packet-tr.c on WTAP_ENCAP_TOKEN_RING).

pcapkit.toolkit.pypcapfile contains the adapters for the PyPCAPFile engine. The reassembly and flow tracing adapters return the data their pcapkit.foundation counterpart consumes, or None if the frame cannot be used for it.

Note

ProtocolError – If a decoded IPv4 layer’s src/dst cannot be parsed as an IPv4 address, or a decoded Ethernet layer’s src/dst cannot be parsed as a MAC address.

Note

A frame PyPCAPFile left undecoded is hex-encoded, as the engine reads it (see PyPCAPFile._read_records), so it is un-hexed (see _maybe_unhex()) and reported as its octets, not as twice as many characters of hex text (#1667).

pcapkit.toolkit.pypcapfile._transport(ipv4)[source]¶

Fetch the verbatim TCP segment carried by a PyPCAPFile IPv4 packet.

Parameters:

ipv4 (IP) – PyPCAPFile IPv4 packet.

Return type:

bytes | None

Returns:

The raw TCP segment, up to the packet’s Total Length, or None if the packet does not carry a TCP header. A later fragment carries none: from its offset on, its data is a slice of the datagram’s payload (RFC 791 Section 3.2, #1576). Nor does a segment too short for a header, or whose Data Offset is below 5 words (#1590).

Note

PyPCAPFile keeps every octet after the header as the payload, so a frame padded to the Ethernet minimum carries its padding there. The segment is cut at the Total Length to leave it out (#1577). A Total Length of 0, which TCP segmentation offload leaves in a capture taken on the sending host, keeps the rest of the frame (#1547).

pcapkit.toolkit.pypcapfile._maybe_unhex(value)[source]¶

Undo binascii.hexlify(), if value looks hex-encoded.

Parameters:

value (bytes) – Raw bytes, possibly hex-encoded.

Return type:

bytes

Returns:

value hex-decoded, if it is a valid even-length hex string; otherwise value itself, unchanged.

Note

The released PyPCAPFile (0.12.0) stores an IPv4 packet’s options (IP.opt) and payload (IP.payload) as binascii.hexlify()’d ASCII text once decoding stops short of the transport layer – which is exactly how PyPCAPFile calls it – rather than as the raw bytes this module otherwise assumes. Both forms are bytes, hex-encoded or not, which is why _is_raw() cannot tell them apart, and falling back to the original value when it does not decode as hex is what keeps this a no-op for the raw, non-hex stand-ins used in unit tests.

This is not a guarantee against every false positive, only a cheap and, in practice, reliable heuristic: a genuinely raw payload whose every byte happens to fall in the ASCII hex-digit range (e.g. a 24-byte TCP header built entirely from digits and A-F) is indistinguishable from real hex text and gets silently halved. There is no way to tell the two forms apart from the bytes alone; this is acceptable here because that byte range is a small fraction of the possible values a real header or payload can take.
