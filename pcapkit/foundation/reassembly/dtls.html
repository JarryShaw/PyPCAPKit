DTLS Handshake-Message Reassembly¶

pcapkit.foundation.reassembly.dtls contains DTLS only, which reconstructs a DTLS handshake message split across several records back to origin (RFC 6347 Section 4.2.3).

class pcapkit.foundation.reassembly.dtls.DTLS[_PT: Info, _DT: Info, _IT: tuple, _BT: Info](*, strict=True, store=True)[source]¶

Bases: ReassemblyBase[Packet[_AT], Datagram[_AT], tuple[_AT, int, _AT, int, int], Buffer], Generic[_AT]

Reassembly for DTLS handshake messages.

Parameters:

  • strict (bool) – if True, report a message that is not completely reassembled as the tuple of its received runs; otherwise as one contiguous payload, its holes zero-filled

  • store (bool) – if store reassembled datagram in memory, i.e., self._dtgram (if not, datagram will be discarded after callback)

Note

The buffer ID is the UDP 4-tuple plus the DTLS epoch: the record sequence number resets on each cipher-state change (RFC 6347 Section 4.1), so a new epoch opens a fresh buffer. Overlapping fragments are accepted (RFC 6347 Section 4.2.3, RFC 9147 Section 5.5). Not toolkit-fed: a protocol instance never sees the addresses, so a caller supplies the 4-tuple as flow to DTLS.read.

Example

>>> from pcapkit.foundation.reassembly.dtls import DTLS
# Initialise instance:
>>> dtls_reassembly = DTLS()
# Call reassembly:
>>> dtls_reassembly(packet_dict)
# Fetch result:
>>> result = dtls_reassembly.datagram
property last: Datagram[_AT] | None¶

The message reassembled by the most recent call to reassembly(), or None if that fragment did not complete one.

This is a synchronous alternative to datagram/fetch() for a caller – DTLS.read is the one that exists – that wants to know, immediately after feeding one fragment, whether that fragment was the one that completed its message, rather than waiting for the buffer (which may hold several other messages still in flight under the same buffer ID) to be flushed.

__protocol_name__: str = 'DTLS'¶

Protocol name of current reassembly object. Not set via __protocol_type__, which would import DTLS at class-definition time; ReassemblyMeta looks name up in the protocol registry instead.

Algorithm¶

See also

Holes are inclusive byte offsets into the message. They never wrap, and the upper bound is known from the start: every fragment carries the message’s total length (RFC 6347 Section 4.2.3).

A DTLS handshake record may carry more than one message fragment – RFC 6347 Section 4.2.3 allows several handshake messages (or fragments of them) to be coalesced into one record, and SSL._read_tls_handshake_messages reads however many fit rather than assuming exactly one. A fragment names the message it belongs to (message_seq), the message’s total length (length), and its own byte range within that message (fragment_offset, fragment_length). A message is reassembled by punching the arriving fragment’s range out of the message’s hole list; it is whole once no hole remains.

Terminology¶

reasm.dtls.packet¶

Data structure for DTLS handshake-fragment reassembly (DTLS.reassembly) is Packet – one fragment’s own bufid, message_seq, fragment_offset, fragment_length and raw payload, built by DTLS.read from a single DTLSHandshake.

reasm.dtls.datagram¶

Data structure for reassembled DTLS handshake message (element of DTLS.datagram) is Datagram – completed, the original packet identifier, the packet numbers that built it, and body, the reassembled payload (a contiguous bytes, or – under strict=True and an incomplete message – a tuple of the octet runs actually received).

reasm.dtls.buffer¶

Data structure for internal buffering (DTLS._buffer) is Buffer – every message under reconstruction for one BufferID (one UDP association at one DTLS epoch), each keyed by its message_seq and held as a Fragment – its hole descriptor list (HoleDescriptor) and its zero-filled payload buffer.

class pcapkit.foundation.reassembly.data.dtls.HoleDescriptor(first, last)[source]¶

Bases: Info

Data model for DTLS hole descriptor.

Both bounds are inclusive byte offsets into the reassembled message, so a hole covers last - first + 1 octets. They never wrap and need no open-ended sentinel: every fragment declares the message’s total Fragment.length (RFC 6347 Section 4.2.3), so it is known from the first fragment.

first: int¶

Offset of the first missing octet.

last: int¶

Offset of the last missing octet, inclusive.
