SCTP User-Message Reassembly¶

pcapkit.foundation.reassembly.sctp.reassembly contains SCTP only, which reconstructs an SCTP user message fragmented across DATA chunks (RFC 9260 Section 6.9) or I-DATA chunks (RFC 8260 Section 2.2.3) back to origin.

Added in version 1.9.0.

class pcapkit.foundation.reassembly.sctp.reassembly.SCTP[_PT: Info, _DT: Info, _IT: tuple, _BT: Info](*, strict=True, store=True, timeout=None)[source]¶

Bases: ReassemblyBase[Packet[_AT], Datagram[_AT], tuple[int, int, int], Buffer], Generic[_AT]

Reassembly for SCTP user messages.

Parameters:

  • strict (bool) – if True, report a message that is not completely reassembled as the tuple of its received runs; otherwise as one contiguous payload, the octets received up to its first hole, since a missing fragment’s length is unknown

  • store (bool) – if store reassembled datagram in memory, i.e., self._dtgram (if not, datagram will be discarded after callback)

  • timeout (float | None) – reassembly timeout in seconds, on the capture’s own clock; None selects __timeout__, which for SCTP disables expiry

Note

A DATA message is a run of consecutive TSNs, from a fragment with the B bit set to one with the E bit set, all on one stream with one U bit and, when ordered, one stream sequence number (RFC 9260 Section 6.9). An I-DATA message is found by its stream, U bit and message identifier, and its fragments are ordered by FSN rather than TSN (RFC 8260 Section 2.2.3). A fragment whose TSN, or FSN, is already held is a duplicate, and the one received first is kept (RFC 9260 Section 6.2).

The buffer ID is the packet’s ports and verification tag, which one direction of one association carries on every path, so a fragment retransmitted to an alternate destination address (RFC 9260 Section 6.4) joins its message; a message reports the addresses of its lowest fragment held. A fragment retransmitted after its message completed is reported as a message of its own. The Extractor feeds it through pcapkit.toolkit.pcap.sctp_reassembly(), and sctp_message() parses what it reassembles. A message’s packet holds the same parse, run on first read, by the analyze of __protocol_type__.

Example

>>> from pcapkit.foundation.reassembly.sctp.reassembly import SCTP
# Initialise instance:
>>> sctp_reassembly = SCTP()
# Call reassembly:
>>> sctp_reassembly(packet_dict)
# Fetch result:
>>> result = sctp_reassembly.datagram

Algorithm¶

A fragment names the message it belongs to differently in each chunk:

        flowchart TD
    F["a DATA or I-DATA chunk,<br/>B and E not both set"]
    Q{"chunk type?"}
    D["DATA: joins the run of TSNs either side of it,<br/>unless that run ends a message, it begins one,<br/>or stream, U bit or ordered SSN differ"]
    I["I-DATA: held under its stream, U bit and MID,<br/>by its FSN"]
    W{"B at the lowest held,<br/>E at the highest,<br/>none between missing?"}
    C["COMPLETE: the message leaves the buffer"]
    H["held until the buffer is submitted:<br/>PARTIAL, or TIMEOUT under a timeout"]

    F --> Q
    Q -->|DATA| D
    Q -->|I-DATA| I
    D & I --> W
    W -->|yes| C
    W -->|no| H

A DATA message’s fragments carry strictly sequential TSNs and one stream sequence number (RFC 9260 Section 3.3.1), so a missing TSN splits what is held into runs, each reported as a message of its own. An I-DATA message’s fragments are numbered by FSN from 0, and its TSNs say nothing of their order (RFC 8260 Section 2.2.3). Neither chunk says how long a missing fragment is, so a hole is never zero-filled.

The TSN space belongs to the association, and a multi-homed endpoint may retransmit a chunk to an alternate destination address (RFC 9260 Section 6.4). So a buffer is keyed on the ports and verification tag alone, which one direction of one association carries on every path, and a message reports the addresses of its lowest fragment held.

Terminology¶

reasm.sctp.packet¶

Data structure for SCTP user-message fragment reassembly (SCTP.reassembly) is Packet – one DATA or I-DATA chunk’s bufid, the addresses of the packet carrying it, chunk type, TSN, stream identifier, U, B and E bits, stream sequence number or message identifier and FSN, payload protocol identifier and user data, built by pcapkit.toolkit.pcap.sctp_reassembly() or pcapkit.toolkit.pcapng.sctp_reassembly().

reasm.sctp.datagram¶

Data structure for reassembled SCTP user message (element of SCTP.datagram) is Datagram – completed, the original packet identifier, the packet numbers that built it, the message’s stream, ordering and TSNs, payload, the reassembled user data (a contiguous bytes, or – under strict=True and an incomplete message – a tuple of the runs actually received), and packet, what sctp_message() parses payload to, on first read, as an IP or TCP datagram’s is.

reasm.sctp.buffer¶

Data structure for internal buffering (SCTP._buffer) is Buffer – every message under reconstruction for one BufferID (one direction of one association, over every path), each held as a Fragment: the DATA ones by each TSN they hold, the I-DATA ones by MessageID.

pcapkit.foundation.reassembly.sctp.data.BufferID¶

Buffer ID – the source and destination ports of the SCTP packet, plus its verification tag, which tells the association from an earlier one between the same endpoints (RFC 9260 Section 1.3). No address is in it, as the TSN space is the association’s and a chunk may be retransmitted to an alternate destination address (RFC 9260 Section 6.4).
