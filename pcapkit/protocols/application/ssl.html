SSL - Secure Sockets Layer¶

pcapkit.protocols.application.ssl.protocol contains SSL, which is the umbrella base class for the Secure Sockets Layer protocol family [*] – the SSL versions, Transport Layer Security and Datagram TLS:

  • SSLv2 – SSL 2.0, whose record layer shares no wire format with the others;

  • TLS – SSLv3 and TLS 1.0 through TLS 1.3, with SSLv3 as its thin subclass for explicit construction;

  • DTLS – DTLS 1.0, 1.2 and 1.3.

SSL.id lists the direct concrete subclasses, so a lookup keyed on SSL matches any of them.

The TLS record header (RFC 9846 Section 5.1) is a ContentType, a legacy record version and a length. The DTLS DTLSPlaintext header (RFC 9147 Section 4) has the same fields plus an epoch and a 48-bit sequence number between the version and the length, and DTLS adds a fragment header to each handshake message. Each record header is declared in its subclass’s own schema, and DTLS reads the epoch and sequence number. This base class carries the logic TLS and DTLS share – content-type dispatch, handshake-message decoding (including the DTLS fragment header), the extension registry and the header schema of each extension’s extension_data (pcapkit.protocols.application.ssl.schema), and the record-level validation that keeps dispatch from accepting bytes that cannot be a genuine record.

Added in version 1.6.0.

GREASE values (RFC 8701) are Reserved extension types with no decoder, so their bodies stay raw octets.

Each type’s layout is the schema Extension registers for it: a parser is handed the extension_data unpacked by that schema, and a constructor returns one.

Changed in version 1.7.0: Each extension decodes and builds through a schema of its own, in pcapkit.protocols.application.ssl.schema (#2833).

Extension type to method mapping, see _read_tls_extensions() and _make_tls_extensions(). A str value names the methods _read_ext_${name} and _make_ext_${name}, falling back to _read_ext_unknown() and _make_ext_unknown() when the class has no such method, as an unregistered type does; any other value is a (parser, constructor) pair of callables. Changed in version 1.7.0: A parser takes, and a constructor returns, the extension_data schema rather than its octets (#2833).

_dtls: bool = False¶

Whether the records are DTLS’s, which alone carry a DTLS-only extension (RFC 9146 Section 10.2); DTLS sets it.

_tls_content_is_cleartext(content_type, fragment, *, dtls, epoch)[source]¶

Whether a record’s fragment is cleartext to decode structurally.

handshake, alert and change_cipher_spec carry ciphertext once keys are derived, and the record header does not say so. Decoding ciphertext would fabricate content, or fail and lose the cleartext header to Raw.

  • DTLS: epoch 0 is cleartext, any later epoch encrypted (RFC 9147 Section 4.2).

  • TLS: handshake must tile (_tls_handshake_tiles()); alert must be exactly 2 octets and change_cipher_spec exactly 1, which encryption overhead never yields.

Any other content type is reported as not cleartext.

Parameters:

  • fragment (bytes) – Record fragment, undecoded.

  • dtls (bool) – Whether this is a DTLS record.

  • epoch (int) – The DTLS record’s epoch; unused when dtls is false.

bool

_read_tls_extensions(data, *, msg_type)[source]¶

Decode an extension list.

Structure of one extension [RFC 9846 Section 4.3]:

struct {
    ExtensionType extension_type;
    opaque extension_data<0..2^16-1>;

Each extension_data is unpacked by the schema Extension registers for its type (_read_ext_schema()), then read by the parser __extension__ registers. The framing delimits it, so one its schema or parser rejects with a ProtocolError is kept as its raw octets rather than failing the message.
