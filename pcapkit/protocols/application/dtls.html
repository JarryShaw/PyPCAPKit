DTLS - Datagram Transport Layer Security¶

pcapkit.protocols.application.dtls.protocol contains DTLS, which implements an extractor for Datagram Transport Layer Security (DTLS) [*] – DTLS 1.0 (RFC 4347), DTLS 1.2 (RFC 6347) and its connection-ID records (RFC 9146), and DTLS 1.3’s legacy-format and unified-header records (RFC 9147) – at the record layer, plus the epoch/sequence-number fields and the handshake-message fragment header that set DTLS apart from TLS, whose reliable, ordered transport needs neither. It also contains DTLSContext, which holds the connection IDs those records carry.

Version Identification¶

As with TLS, one class parses every version and read() sets alias from the record; id() stays ('DTLS',).

Legacy record version

alias

0xFEFF

DTLS 1.0

0xFEFD

DTLS 1.2

0xFEFD, or 0xFEFF on an initial ClientHello, whose supported_versions extension lists 0xFEFC

DTLS 1.3

any other 0xFExx

DTLS

unified header (first octet 001CSLEE, RFC 9147 Section 4.1)

DTLS 1.3

DTLS 1.3 never puts its own 0xFEFC on the record layer (RFC 9147 Section 4), so a legacy-format record is told apart only by the supported_versions peek. A version the table does not name keeps the generic DTLS alias rather than claiming a specific one.

A unified-header record has no legacy version to read. Its first octet’s top three bits are 001, which no legacy content type (20 through 27) sets, so the two formats are told apart by that octet alone.

A tls12_cid record is DTLS 1.2: RFC 9146 Section 10.3 limits the content type to that version, so one with another legacy version is refused.

Connection IDs¶

A tls12_cid record carries a connection ID between its sequence number and its length (RFC 9146 Section 4), and a DTLS 1.3 unified header with its C bit set carries one between its first octet and its sequence number (RFC 9147 Section 4). Either way the ID’s length is negotiated rather than carried. DTLSContext resolves it for both, in this order:

  • a connection ID that a ClientHello or ServerHello connection_id extension negotiated earlier in the capture, each peer naming the one it receives (RFC 9146 Section 3, RFC 9147 Section 9.1), and that the record’s ID begins with;

  • the cid_length the caller gives DTLSContext.

Without either the record stays Raw. A dissected one reports its connection ID alongside its other header fields, and keeps its encrypted content as octets. The context reaches DTLS through pcapkit.corekit.context:

import pcapkit
from pcapkit.protocols.application.dtls.protocol import DTLSContext

extraction = pcapkit.extract('dtls.pcap', context=DTLSContext(cid_length=8))

The connection IDs a DTLSContext learns belong to that instance. A new instance starts with none, and one the caller reuses keeps what it has learned. An extraction given none gets its own in its own registry, so it carries what its handshakes negotiate across its capture and no further. A registry passed as __context__ to several parses carries its instance across them.

Matching by value relies on IDs being self-delineating (RFC 9146 Section 4): with c1c2c3c4 registered, a record whose ID is c1c2c3c400010203 reads as carrying c1c2c3c4.

A rebuild parses each layer’s octets again, so from_data takes the same __context__. Without it the octets still rebuild exactly, and DTLS.from_data keeps its chain, but a record with a connection ID under a rebuilt UDP layer reads as Raw.

Records in One Datagram¶

A whole record after the first in a UDP datagram is dissected as a further DTLS layer, the previous record’s payload (RFC 6347 Section 4.1.1, RFC 9147 Section 4.3, #2535): a ChangeCipherSpec followed by an Alert reads UDP:DTLS 1.2:DTLS 1.2. A unified-header record is delimited by its length; one without a length runs to the end of the datagram, so it is the last (RFC 9147 Section 4). The exceptions:

  • A whole record that fails to decode becomes Raw together with everything after it.

  • Octets that open no whole record stay raw, with no error: an unsupported content type, a legacy version outside 0xFExx, a header cut short, a length past the end of the datagram, or a connection ID whose length is not known, which leaves the record’s end unknown.

  • A parse told to stop at DTLS (protocol='DTLS' or layer='Application') keeps the rest of the datagram raw.

  • Each record is a layer, so FRAME_LAYER_LIMIT bounds how many are dissected.

Known Limitations¶

A handshake message split across DTLS records is not decoded here (RFC 6347 Section 4.2.3, #2440). Each fragment is flagged is_fragmented and its body kept as raw octets. Extractor(reassembly=True, dtls=True) reassembles the message, and dtls_handshake() decodes it with analyze_handshake(), which reads it with read_handshake().

A connection ID negotiated in a fragmented hello is not learned: the message is not decoded here, so its connection_id extension is not read.

A connection ID a DTLS 1.3 NewConnectionId issues is not learned (RFC 9147 Section 9, #2625): the message is encrypted, so only the caller can give it to DTLSContext.

A unified-header record carries only the low two bits of the epoch, and its sequence number is header-protected, so the values it reports are the ones on the wire.

Added in version 1.6.0.

class pcapkit.protocols.application.dtls.protocol.DTLSContext(*connection_ids, cid_length=None)[source]¶

Bases: ProtocolContext

Connection IDs for the DTLS records that carry one (RFC 9146, RFC 9147).

Neither a tls12_cid record nor a DTLS 1.3 unified header carries its connection ID’s length, so match() finds it: from the connection IDs registered here, then from cid_length. DTLS registers those a ClientHello or ServerHello negotiates, and those of the records a constructed one carries as its payload. Those a DTLS 1.3 NewConnectionId issues are encrypted, so only the caller can register them (RFC 9147 Section 9).

The IDs belong to the instance: a new one starts with none, one reused across parses or extractions keeps what it has learned, and nothing is kept anywhere else. An extraction given no instance gets its own, in its own registry, the first time a hello negotiates an ID.

Matching by value relies on IDs being self-delineating (RFC 9146 Section 4): with c1c2c3c4 registered, a record whose ID is c1c2c3c400010203 reads as carrying c1c2c3c4. Where one registered ID is a prefix of another, a record carrying the shorter can read as carrying the longer, when the octets after it repeat the longer one’s rest and the record still fits; a unified header must also leave room for its record-number sample, which rules most such readings out.

Parameters:

  • *connection_ids (bytes) – Connection IDs known out of band.

  • cid_length (int | None) – Connection ID length of a record that no registered one opens.

Raises:

ProtocolError – If a connection ID is not 1 to 255 octets, or cid_length is not an int from 1 to 255.

match(octets, *, sequence_length=0, length_present=True, min_content_length=0)[source]¶

Find the length of the connection ID that octets opens with.

Each registered connection ID that octets begins with is a candidate, longest first, and cid_length comes last. The first whose record ends inside octets and carries at least min_content_length octets of content is the answer. After the ID come sequence_length octets, then a 16-bit length and that many octets, or, without the length, the rest of octets. Failing that it is the first candidate, so that reading the record reports what is wrong with it.

Parameters:

  • octets (bytes) – A record from its connection ID on.

  • sequence_length (int) – Octets between the ID and the length: none in a tls12_cid record (RFC 9146 Section 4), and a unified header’s sequence number (RFC 9147 Section 4).

  • length_present (bool) – Whether the record carries its length, as a unified header’s L bit says; a tls12_cid record always does.

  • min_content_length (int) – Fewest content octets a record may carry: a unified header’s record-number sample (RFC 9147 Section 4.2.3). A tls12_cid record’s minimum depends on its cipher suite, so none is assumed for it.

Return type:

int | None

Returns:

The connection ID’s length, or None with no candidate.

class pcapkit.protocols.application.dtls.schema.DTLSCiphertext(flags=NO_VALUE, cid=NO_VALUE, sequence_number=NO_VALUE, length=NO_VALUE, fragment=NO_VALUE, payload=NO_VALUE, *, __packet__=None, **kwargs)[source]¶

Bases: Schema

Header schema for a DTLS 1.3 ciphertext record, which has a unified header.

The first octet is 001CSLEE (RFC 9147 Section 4.1): C names a connection ID, S an 8- or 16-bit sequence number, L a length field, and EE the low two bits of the epoch. The record has no content type or version octet, since both are inside the ciphertext, so DTLS’s legacy header cannot describe it.

The record does not carry its connection ID’s length (RFC 9147 Section 4), so the parser gives it as the __cid_length__ key of the packet context; packing takes it from cid.

Sequence number, 8 or 16 bits as S says (header-protected on the wire).

class pcapkit.protocols.application.dtls.data.DTLSHandshake(msg_type, length, body, message_seq, fragment_offset, fragment_length, is_fragmented)[source]¶

Bases: Handshake

Data model for a DTLS handshake message.

DTLS adds a fragment header – message_seq, fragment_offset and fragment_length – on top of the TLS handshake header shared with Handshake (RFC 6347 Section 4.2.2), so that a handshake message that does not fit in one datagram can be split across several.

body decodes to a ClientHello, ServerHello or EncryptedExtensions when is_fragmented is False. A fragmented message’s body is the fragment’s raw octets; dtls_handshake() decodes the message once DTLS has reassembled it (#2440).

msg_type: HandshakeType¶

Handshake message type.

length: int¶

Total message length (24-bit), fragment headers and bodies excluded.

body: ClientHello | ServerHello | EncryptedExtensions | bytes¶

Message body – see the class docstring for when this decodes.

message_seq: int¶

Message sequence number.

fragment_offset: int¶

Fragment offset (24-bit) into the reassembled message.

fragment_length: int¶

Length (24-bit) of this fragment.

is_fragmented: bool¶

Whether this fragment is a strict subset of the message, i.e. fragment_offset != 0 or fragment_length != length.

See SSL - Secure Sockets Layer for ClientHello, ServerHello, EncryptedExtensions, Extension and its decoded bodies, Alert and ChangeCipherSpec, shared verbatim with TLS.
