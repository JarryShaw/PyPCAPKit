The double relationship between Unit Tests and the dependants that also call it is the part that reading a single file cannot show, and it is deliberate rather than redundant. Vendor Update, Conda Update and GitHub Pages each call Cron Head as their head job (dotted, above), and its test gate calls unit-tests.yml with gate-only: true only when the caller’s trigger is schedule or workflow_dispatch – the gate’s if: skips workflow_run and pull_request – so only on the Saturday path and a manual run, where no completed Unit Tests run exists yet to read a verdict from. On the workflow_run path (thick arrows), each reads the verdict Unit Tests already reached instead of re-running the gate a second time, and acts on it only once the head’s verdict job, described under the edge list below, says it is a verdict on the commit it builds (#1967). Create Release has no schedule, and its gate job’s if: reads version_check’s evidence rather than the event, so its gate can run whichever way the run was raised, once version_check itself has passed: on a v* tag push, and on a workflow_run from Vendor Update when some target is not yet published (Release Process gives the conditions).

workflow_run Edges¶

Each edge cites the on: block it comes from, so grepping those blocks re-derives the list:

  • .github/workflows/cron-vendor.yml, its workflow_run trigger – Vendor Update fires on completion of Unit Tests.

  • .github/workflows/cron-conda.yml, its workflow_run trigger – Conda Update fires on completion of Unit Tests.

  • .github/workflows/deploy-pages.yml, its workflow_run trigger – GitHub Pages fires on completion of Unit Tests.

  • .github/workflows/create-release.yml, its workflow_run trigger – Create Release fires on completion of Vendor Update.

  • .github/workflows/coverage-comment.yml, its workflow_run trigger – Coverage Comment fires on completion of Unit Tests.

  • .github/workflows/ci-reports.yml, its workflow_run trigger – CI Reports fires on completion of Experimental Tests and of Python Compatibility.

workflow_run fires for every completion of the named workflow – success, failure, or skipped – and regardless of what triggered it, including a pull request’s own run of Unit Tests. Every downstream workflow therefore re-checks github.event.workflow_run.event and .head_branch (or, for Create Release and Coverage Comment, .conclusion; for CI Reports, the event alone) itself before doing anything with an outward effect; none of the filtering happens in the on: block.

Those checks say nothing about which commit was verified. A workflow_run checks out github.sha, main’s tip when the event is raised, not github.event.workflow_run.head_sha, the commit the completed run tested, and in a merge wave the two differ: Conda Update 38325136710 bumped 2e941bbb7 under the verdict for 9083163f5 (#1643). So Vendor Update, Conda Update and GitHub Pages each run Cron Head’s verdict job first, in their head job, and act only when its verified output says the tip is the verified commit, or that commit plus bot commits to conda/build and conda/requirements.txt alone; otherwise they skip, and the tip’s own Unit Tests run raises them again. Vendor Update’s run still concludes success then, since verdict ran, so Create Release reads its vendor-update job to tell it from a real one (#1748). The rule and its evidence are in util/verdict_covers_checkout.py. Conda Update also writes after the checkout, so it applies the same rule a second time: its push rebases onto main’s tip only when the commits that brings in pass it, and otherwise pushes nothing, and Conda Tag tags the commit that push landed rather than the tip (#1632).

Vendor Update’s own commit raises it again: the push gets a Unit Tests run, whose completion starts another crawl. The commit bumps the version only when the crawl changed code. If every change is to comments or docstrings, the commit is “Updated vendor documentation without a version bump”, and the Create Release run that follows sees the same version, so it has nothing new to publish (#1674). A crawl raised by such a commit’s own Unit Tests run does not commit comment changes on top of it, so documentation commits cannot chain. The rule is in util/vendor_code_changed.py. A bump commit carries every module the crawl wrote, a new one included, so the crawl it raises does not find one untracked and bump again (#1685).

Reusable-Workflow Calls (uses:)¶

A uses: call is a different relationship from triggering: it runs inside the caller’s own workflow run, as one of the caller’s own jobs, rather than starting an independent run after the caller finishes. The calls target unit-tests.yml, always with gate-only: true, and cron-head.yml:

  • .github/workflows/create-release.yml, job unit-tests – calls ./.github/workflows/unit-tests.yml with gate-only: true.

  • .github/workflows/cron-head.yml, job unit-tests – calls ./.github/workflows/unit-tests.yml with gate-only: true.

  • .github/workflows/cron-conda.yml, cron-vendor.yml and deploy-pages.yml, job head in each – calls ./.github/workflows/cron-head.yml, with no inputs. The call’s verified output is its verdict job’s, and the acting job reads it beside needs.head.result.

Cron Head (#1967) is the one copy of the test gate and the verdict job that Conda Update, Vendor Update and GitHub Pages share. It holds contents: read and no more, which is what each caller grants its head job and what unit-tests.yml is called with. Every expression in it reads the caller’s github context, so its jobs decide on the event that started the caller and check out the caller’s github.sha. A job of the call skips on every path – the gate everywhere but the schedule and a manual run, verdict everywhere but a workflow_run – so each acting job keeps !cancelled(), for the reason the skip-cascade section below gives, and treats a head result other than failure as passing.

Their schedules are eight hours apart on Saturdays: GitHub Pages at 02:00, Vendor Update at 10:00 and Conda Update at 18:00 UTC (#1967). The owner’s ruling kept a schedule on each and allowed them aligned or spread, and nothing orders them:

  • None reads another’s output. A Vendor Update push reaches Conda Update and GitHub Pages anyway, as a Unit Tests run whose completion raises both on the workflow_run path. Create Release reads only the Vendor Update run that triggered it, through its vendor_update job, so the time of the others does not matter to it.

  • Aligned, they cost more. With Vendor Update and Conda Update both at 10:00, each scheduled pair read back from 2026-09-26 on checked out the same commit (#1967) – on 2026-10-17, Conda Update 39023770904 and Vendor Update 39023891165 both gated 44ed96fc3, their Gate (full suite, …) jobs taking twelve and ten minutes. Their writing jobs share the repository-maintenance group, so conda-update waited for vendor-update to finish, and a third job joining that group cancels the one pending there.

Spread, each head gates alone, and Conda Update runs once Vendor Update’s Create Release has had the day to publish, so its Check the GitHub release exists step finds the release rather than skipping the GitHub upload (#1634).

To debug Vendor Update, Conda Update or GitHub Pages without waiting for Saturday, start a manual run on a branch, as in gh workflow run cron-conda.yml --ref <branch>. A manual run is build-only by default: Cron Head’s test gate and every build and test step the schedule runs still run – each conda-dist leg, Windows included, builds the dispatched commit with conda-update’s changes applied – while every step that pushes, tags, uploads, deploys or posts a report skips, no job that runs names an environment, and the Create Release run it raises releases nothing. tests/project/test_build_only_dispatch.py pins this.

Conda Update’s manual run also takes a publish input, off by default, for putting a version’s missing platform files on Anaconda (#2060). A scheduled run uploads only a build it bumped, and it bumps only when Verify Changed files sees a change, which util/conda_vendor.py does not make when no dependency moved. gh workflow run cron-conda.yml --ref main -f publish=true therefore runs as the schedule does, through the same test gate, environments and repository-maintenance group, but with the build bumped regardless: Decide whether to bump says so although nothing changed, so Bump Version, Commit Changes and Push Changes run, conda-tag tags the pushed commit, every conda-dist leg uploads it, the GitHub Release steps run, and discussion posts the report as scheduled. The mode job is the one place the input is read: its publishes output is 'true' on the schedule, on a workflow_run and on such a run, and 'false' on any other manual run, and every step or job that publishes or names an environment requires it to be 'true'. On any ref but main, publish fails mode with an ::error, so the run fails and conda-update never starts. The workflow-level concurrency group stays keyed on the run, so a manual run never displaces a pending scheduled one. No later run repeats a forced bump, so where Push Changes does not push it because main moved past the checkout or during the push, the run stays green having published nothing, and says so in a warning and in its report (#2060); the remedy is to dispatch Conda Update again with publish on main. Where another run already pushed the same build, that run tags and uploads it, and a second dispatch is needed only if it did not. tests/project/test_conda_publish_dispatch_2060.py pins this.

gate-only: true selects not only unit-tests.yml’s gate (the full suite, on latest) but also changelog (checks CHANGELOG.md against its source entry) and python-versions, which reads gate’s version (see Python Versions below). It skips the rest – the matrix jobs, test, test-ktlo, integration, integration-ktlo, engine-tests (a job per engine, each looping over its Python versions), pypcap-parity, pypcap-parity-ktlo and unittest-ordering, each of which has already run once for this commit from Unit Tests’ own push trigger (and, all but unittest-ordering, which runs on main pushes only, from its pull_request trigger), so running any of them again per caller would test the same commit several times over. It also skips changes, project-tests, whose project pins gate’s full suite runs too (see Project Pins below), and required-checks (see Required Status Checks below), which are gated out by their own if: rather than by having already run. changelog carries no if: at all and runs on every path regardless – deliberately, per the comment above the job: create-release.yml feeds CHANGELOG.md to the GitHub Release body, so the release path is exactly where a drifted file must not go unchecked. Confirmed on run 36210743295 (a schedule-triggered GitHub Pages run): both Changelog drift and Gate (full suite, Python 3.14) succeeded, with the matrix jobs that existed then – Python ${{ matrix.python-version }}, Integration Python …, Engines Python … and PyPCAP/PyPCAPFile parity Python … – all reporting skipped.

The Skip Cascade (#888)¶

The relationships above compose into a failure mode worth seeing on its own graph. Create Release’s version_check – ahead of the uses: call above – carries:

if: >-
  ${{ !cancelled() &&
  (github.event_name != 'workflow_run' || (github.event.workflow_run.conclusion == 'success' &&
  github.event.workflow_run.event != 'workflow_dispatch')) &&
  !(github.event_name == 'push' && github.actor_id == vars.RELEASE_APP_BOT_ID) &&
  needs.vendor_update.outputs.updated != 'false' }}

Its third clause skips the tag-push run that the release App’s own tag starts (Release Process, “The Release App”). On the workflow_run path, this evaluates false, and the job is skipped outright, whenever the upstream Vendor Update run’s own conclusion was anything other than success – including skipped, which is exactly what Vendor Update’s own jobs report when their workflow_run-path guards decline (see cron-vendor.yml’s vendor-update job). Since #1748 it is also false for a Vendor Update that concluded success with vendor-update skipped – its verdict job found the Unit Tests verdict was for another commit – which the vendor_update job reads from that run’s jobs first (observed on run 38650191283). It is false for a manual, build-only Vendor Update as well, which pushed nothing, and so is vendor_update’s own if:. !cancelled() keeps a skipped vendor_update, on a push, from skipping it. unit-tests then depends on that job with needs: [ version_check ] and an if: that calls no status-check function, so a skipped dependency skips it too – and every job past it is gated the same way: github needs [ unit-tests, version_check ], tag and pypi need [ github, unit-tests, version_check ], and conda needs [ tag, github, unit-tests, version_check ].

This is a transitive reduction, as in Release Process: version_check and unit-tests are also direct needs: of tag, pypi and conda, but github already implies those edges, since it depends on both itself. Drawing them would add lines without changing which job can start before which, or which job a skip in version_check reaches.

The whole run then reports skipped, not failed – there is no red X to notice. Observed in production on runs 36511610205 and 36510774776, both workflow_run-triggered Create Release runs on main that concluded skipped with every one of their jobs – Release test gate, Check Version, GitHub Release, Conda Tag (release), PyPI distribution for Python … and Conda deployment (release) … – reporting skipped in turn.

This is a distinct mechanism from the PCAPKIT_TAG_EXISTS skip Release Process already documents under “Precautions” (a later run skipping because the tag a previous run already created still exists): this one can skip the very first attempt, before any tag is ever created, purely because the upstream Vendor Update run did not itself conclude success.

Such a run is also kept out of the release’s concurrency group (its concurrency block, #1705). It is keyed on its own github.run_id rather than on the ref, so it cannot cancel a run waiting there with release work. Keyed on the ref, run 38499295798 joined at 02:06:32Z on 2026-10-14, and the pending 38499150441, whose Vendor Update had succeeded, was cancelled a second later. A run whose Vendor Update concluded success with vendor-update skipped (#1748) is still keyed on the ref: the group reads only the event, which does not say which jobs ran. It can still displace a run pending there, and releases nothing in its place, so that release waits for the next Vendor Update on main.

pull_request_target¶

Project Status and Milestone are the workflows on pull_request_target, which runs the base branch’s copy of a workflow with a write token on an event a fork can cause, so neither runs anything the pull request supplies.

Project Status is the one that runs with a secret: it writes the project board’s Status field with PROJECT_TOKEN, which a fork’s pull_request run would not receive. It therefore never checks out the repository and has no uses: step. It fetches util/project_status.py, and util/_actions.py, which it imports (#2047), through the API at github.sha – the base branch’s tip under that event – and takes only the item number from the payload. tests/project/test_project_status.py asserts this over the file. Milestone (#2218)¶

Each issue and pull request gets its release milestone as it opens, reopens and closes, by the rule under “Milestones and the Project Board” in Running the Repository, which action_for in util/milestone.py applies:

  • an open item, a merged pull request, or an issue closed as completed gets the open milestone titled PyPCAPKit v<major>.<minor> from the checked-out __version__ – 1.5.0b14 gives PyPCAPKit v1.5;

  • a pull request closed unmerged, or an issue closed as not planned or as a duplicate, loses any milestone it has;

  • an issue closed with no reason recorded is left as it is.

A milestone already on an item wins over the one the rule gives. An item that holds a different milestone, such as a later release set by hand, keeps it on open, reopen and close; the milestone is given only to an item that has none. Removal is the exception: an unmerged or not-planned close takes away whichever milestone the item holds, since work closed without shipping belongs to no release.

The run re-reads the item through the API rather than trusting the event payload. Where no open milestone has the title, the item is left without one and the run emits a ::warning::: the script never creates a milestone, since opening the next one is a release step done by hand. A removal needs no milestone, so it goes ahead regardless.

A workflow_dispatch backfills: it applies the same rule to every item, open or closed, with no milestone whose number is above the highest-numbered item of the previous release’s milestone, the newest of the PyPCAPKit v<major>.<minor> milestones below the current one. Items at or below that bound belong to releases already made, and those among them without a milestone were left so by hand. With no earlier milestone to bound it, the backfill warns and changes nothing. Its dry_run input is ticked by default, so a dispatch reports what it would change until it is unticked. Its updates go out a second apart, under GitHub’s secondary rate limit on content-creating requests, and a request refused with a rate limit is retried a bounded number of times, after the Retry-After GitHub sends or an exponential backoff from a minute. The Set the milestone step picks the mode.

Runs on one item share a concurrency group with queue: max, as Project Status’s do, so a quick open, close and reopen never overlap and none is cancelled. Queue order is not guaranteed, but each run re-reads the item, so the last to execute writes its state as it then stands.

Coverage (#1063)¶

Coverage is measured inside an existing leg rather than by a workflow of its own: the Python 3.15 leg of test (matrix key coverage: true) runs its unchanged pytest selection under coverage run --rcfile=.github/coverage.toml. That rcfile repeats pyproject.toml’s [tool.coverage.*] settings (tests/project/test_coverage_rcfile.py asserts it) and adds parallel and patch = ["subprocess"], without which only the xdist controller is measured, not its workers, plus core = "ctrace": with the suite purging and re-importing pcapkit, one module’s peak RSS was 4.17 GiB under the default sys.monitoring core against 0.41 GiB under ctrace, and that growth killed the runner. sigterm = true and a pytest_sessionfinish hook in tests/conftest.py that saves each xdist worker’s data early keep a worker that dies during shutdown from losing its file (#1423). The leg’s Report coverage step then runs util/coverage_report.py, which fails, posting no total, unless the controller and every xdist worker saved a data file (#1387), and otherwise writes the total and a per-package table to the job summary. The leg uploads the HTML report as the coverage-html artifact (30 days), with the bare numbers as the coverage-summary artifact and the per-process debug log as coverage-processes-log.

The PR comment comes from Coverage Comment (coverage-comment.yml), not from unit-tests.yml. That file is also a reusable workflow, a called workflow can only narrow the token its caller passes, and every caller grants contents: read, so a pull-requests: write job there would break them. Coverage Comment runs no tests. On workflow_run it uses the default branch’s file and its own token, so fork pull requests get a comment too. It treats the artifact as untrusted: it never checks out pull-request code. It takes the PR number from the API, as the open PR whose head is the run’s head sha, and renders its own Markdown from validated numbers. It edits one comment, found by a hidden marker, on each push. The first line says when the tests failed. Neither workflow’s coverage step is a required check. A push run has no pull request, so its report goes to Discussions instead (see CI Reports).

CI Timing Review (#1538)¶

CI Timing (ci-timing.yml) runs util/ci_timing.py every Monday, or on dispatch with a days window and an optional concurrency_hours runner-pool measurement. Through the API it lists every completed run in the window of Unit Tests, Python Compatibility, Lint, CodeQL, GitHub Pages and Experimental Tests (#1732, so its two-hour legs stay measured), a day per query because a filtered listing stops at 1,000 runs (Pages completed 1,154 in the week to 2026-10-09). It then reads the jobs of an evenly spaced sample – 150 push and 150 pull-request runs of Unit Tests, 60 runs of each other workflow – and the summary says how many runs each sample holds and which span they cover. For the week to 2026-10-19 that was 677 calls (#1930: 49 listing pages, one per workflow per day and one more per further 100 runs; 601 job reads; 15 for the JUnit artifacts; 12 workflow-file reads) of GITHUB_TOKEN’s 1,000 an hour, on a read-only token (actions: read, contents: read). It took 16.6 minutes, 908 seconds of it on the job reads, which the API answers at up to 2.4 s each and which are made one at a time. The step’s cap (35 minutes) and the job’s (40) sit above that budget, and the summary and upload steps run on always(), so a report written before a cap stopped the job is still published. Progress goes to the log as the script runs. The report goes to the job summary and to the ci-timing-report artifact (90 days), and the newest earlier report is the next run’s baseline. The discussion job then posts it to the ci-timing: weekly CI timing report thread (see CI Reports). It is not a workflow_run on Unit Tests, which would add a job per run to a runner pool measured saturated at 20 concurrent jobs.

Per-test timings come from the test and integration legs, and from experimental.yml’s, which run pytest with --durations=30 --durations-min=1.0 and --junitxml and upload the file as junit-unit-<version>, junit-integration-<version> or junit-experimental-<version> (14 days). Work Kept Off the Pull-Request Queue (#1538)¶

Cuts in unit-tests.yml keep work that cannot gate a merge from competing with pull-request jobs for the 20-runner pool. None touches a required check or adds a permission to the reusable workflow.

  • unittest-ordering runs on main pushes only, per #1052 item H, and has needs: [test], so its cells join the queue once test finishes rather than when the push run is created, ahead of that run’s own Python legs and of pull-request jobs created later in a merge wave.   • engine-tests has no DPKT cell. Its only path would be tests/toolkit/test_dpkt_unit.py, which test runs with DPKT installed on every leg. What that gives up is the file in a venv holding only test and DPKT.

The 3.15 engine cells are not among the cuts: 3.15 is in the supported tier (#1633), so its cells block on every run.

Light Pull Requests (#2243)¶

A docs-only or test-only pull request runs only the jobs its files can affect, by the owner’s ruling on #2243: a docs-only one the docs build and Lint, a test-only one the tests on latest and Lint. The KTLO (keep the lights on) tier – end-of-life 3.8-3.10, still built and tested – never blocks, is never a required context, and never shows a commit or a pull request red (#1672). In unit-tests.yml the KTLO legs are jobs of their own since #1738: test-ktlo, integration-ktlo and pypcap-parity-ktlo, which neither required-checks nor unittest-ordering needs:, so not even a failure no step can contain, such as a lost runner or the job cap, reaches a gate. Each runs its gating twin’s steps, by YAML alias (Reusing workflow configurations), and keeps its legs’ check names, Python 3.10 (KTLO) and so on. In python-compatibility.yml and create-release.yml a KTLO leg shares its job with supported legs. Every job holding KTLO legs works the same way:

  • Every step that can fail on a KTLO leg has an id and continue-on-error: ${{ matrix.ktlo == true }} (see the comment above test-ktlo), unless it is masked on every leg, as the timings uploads are. Its outcome is then failure but its conclusion success, so the job, its check run and required-checks read success. A step that needs an earlier one’s work waits on that step’s outcome: a leg that cannot install stops there, and a pypi leg stops at its first failure.

  • The last step but the job summary’s (see CI Reports), KTLO summary, runs on KTLO legs only and reports each failed outcome as a warning and a job-summary line, through util/leg_summary.py (see Workflow Scripts (#1967)). A step’s own annotations take ANNOTATION_LEVEL: warning on a KTLO leg, error on a supported one. engine-tests’ KTLO cells, a step of their own with continue-on-error: true, report the same way.

  • Never job-level continue-on-error alone: it passes the run, but the leg’s check run still concludes failure, which showed every commit red while the Compat Python 3.7 (KTLO) leg carried it. unit-tests.yml’s KTLO jobs carry it on top of the step-level guards, as a backstop for the failures no step contains, as experimental.yml’s job does; it “prevents a workflow run from failing when a job fails” (Workflow syntax), so the Unit Tests run its workflow_run consumers read stays green.

Errors remain on a failed KTLO step, though none changes a conclusion: the runner’s Process completed with exit code N. for a run: step, and an action’s own. And #1634’s tag check still blocks the pypi KTLO legs: it fails every leg alike, and masked, the leg would go on to publish.

On PyPy an xdist worker’s RSS grows with every test it runs, rather than in a few heavy modules, so a PyPy leg’s Run unit tests hands its pytest command to util/pytest_shards.py, as GraalPy’s leg does (see below), which runs it once per directory its SHARDS names, tests/protocols and then tests/corekit, and once more over the rest, ignoring each (#2005). Each run starts its workers afresh. Each run but the last writes a JUnit file of its own beside junit.xml, which Upload test timings takes too, and the step fails if any run did.

Nothing below requires-python’s 3.8 is in any matrix (#2051): pip refuses such an interpreter at install, so a leg there could only prove the refusal. Nor are 3.8 and 3.9 in engine-tests, which installs every interpreter on ubuntu-latest, where setup-python has no Ubuntu 26.04 build of any of them. Nor are they in pypcap-parity, which also runs on ubuntu-latest; none of them was measured on that job.

The experimental tier is free-threaded CPython and GraalPy, spelt as setup-python reads them (3.14t, graalpy-25.4). Each runs a leg of experimental, the matrix job of .github/workflows/experimental.yml (“Experimental Tests”), named Python <version> (experimental), and nothing else: no integration, Compat, wheel or conda leg, so never a required context. They run in a workflow of their own, rather than as legs of test, by the owner’s ruling on #1732 that nothing waits on them. That workflow reports separately and holds up nothing: a job cannot needs: one in another workflow, nothing calls it, and no workflow_run names it but CI Reports’, which posts its finished runs (see CI Reports), so the Unit Tests run completes without it, and with it Required checks passed, unittest-ordering and the workflows that wait on Unit Tests completing (coverage-comment.yml, deploy-pages.yml, cron-vendor.yml and cron-conda.yml). It runs on Unit Tests’ push and pull_request events, skips a docs-only or test-only pull request by the same changes script, and lets a newer commit supersede a run, a pull request’s or, unlike Unit Tests, a push to main’s (#1903): since nothing waits on the legs, main’s newest commit is the one worth testing, whereas Unit Tests keeps a run per push for unittest-ordering, which runs only there.

A superseded run is skipped or stopped, never cancelled (#1938): GitHub counts a cancelled check against its commit, so a cancelled run marks the commit red. The workflow has no concurrency group either, since a group cancels its pending run once a newer one queues. Its first job, current (“Check the commit is still current”), sets up latest and installs requests, which the script fetches with, then runs util/superseded.py’s check. A push’s commit is current while it is the head of main; a pull request’s while the pull request is open and its head is still the event’s pull_request.head.sha; any other event’s always. Every other job needs current and skips where its output is false, so a run superseded before it starts ends with skipped checks and a Superseded notice. Each of those if: conditions opens with !cancelled(), which drops the implicit success(), so a failed current step, which leaves the output empty, or a failed current job runs the rest; the legs still need changes and python-versions to succeed. Run unit tests runs its whole command – the scope’s sudo where there is one, then prlimit, timeout and pytest – under the script’s watch, outside the scope, which asks again every 60 seconds. The watcher runs on a CPython of its own, latest from a second setup-python step, watcher-python, with update-environment: false, so the leg’s PATH, LD_LIBRARY_PATH and pip cache are as its own setup-python left them, and requests goes into that interpreter, never the leg’s GraalPy or free-threaded build. The two steps are capped at 1 minute each, and where either fails the tests run unwatched. Once the commit is superseded, or the pull request merged or closed, it sends SIGTERM, then SIGKILL 30 seconds on: to pcapkit-tests.scope by name (sudo -n systemctl kill) where the tests run in it, since they run as the runner’s user under a root-owned sudo and in timeout’s own process group, and to the command’s session otherwise. Ubuntu’s /etc/sudoers sets use_pty, which sudoers(5) says has no effect where sudo has no terminal, as in a step; the scope is reached by name either way. Once the command exits, the watcher writes a Superseded notice and a job-summary line and exits 0, so the leg ends green and frees its runner. It also writes stopped=true to the step’s outputs: pytest, stopped, writes no junit.xml, so Upload test timings then sets if-no-files-found: ignore rather than warn of the missing file the notice already explains (#2073). Every wait is bounded: where the command outlives SIGKILL by 15 seconds, it writes a Superseded run not stopped warning and exits 70, not 0, since the tests may run on, holding the step’s output, until timeout or the step’s cap ends them, and the failed step is then a warning like any other on these legs. Otherwise the step ends with the tests’ own status. An API the script cannot read counts as current, so it never stops the tests, and it asks with If-None-Match, as a 304 answer costs no rate limit.

The legs never block, by the KTLO mechanics above: every step that can fail has continue-on-error: true, their annotations are warnings, and Experimental summary, the job’s last step but the job summary’s, reports each failed step. A failure no step contains, such as a lost runner, fails the job, and the job’s own continue-on-error: true keeps it from failing the run: it “prevents a workflow run from failing when a job fails” (Workflow syntax), though the leg’s check run still reads failure. A job past its timeout-minutes is cancelled, and that page does not say whether the job-level guard covers a cancellation. So setup-python, the install, the watcher’s setup-python and requests (#1938, below) and the tests have caps of their own, of 5, 10, 1, 1 and 120 minutes, under the job’s 140, which leaves 3 for the rest: a step at its cap fails rather than cancels, and the guard holds (actions/runner’s StepsRunner.RunStepAsync). The runner’s has timed out error stays, changing no conclusion, as Process completed with exit code N. does. Everything but the install and the tests took under 20 seconds on every uncovered leg of runs 38569321543-38569522442. test’s caps are main’s: 45 minutes for the job, and none on a step. Test Tiers¶

Every test module runs in one of two test tiers (#1958): ALL, which runs on every leg, and LATEST, which runs on latest alone. They are orthogonal to the unit and fixture-dependent tiers, which decide what a module may read and so which job collects it; a test tier decides on which of that job’s legs it runs.

module_tier() in tests/_tiers.py decides, in one place, for every tests/**/test_*.py. ALL is a curated, opt-in list (#1958, #1963): short enough to save time on every leg, the same on every leg so QA stays consistent, and enough on its own to validate a change on each interpreter, while latest runs the whole suite as the gate.

  • The marker. A module joins ALL with a module-level __tier__ = 'ALL', read by AST, under a #: Test tier (#1958): <reason> comment. It is a module constant rather than a pytest marker, so unittest-ordering’s plain unittest runs read the same module. A value that is not 'ALL' or 'LATEST', or a marker assigned twice or anywhere but at the module’s top level, fails the tier guard.

  • The default. A module that states no tier is LATEST, so a new module runs on latest until it says why every leg needs it. __tier__ = 'LATEST' is optional, and records why a module someone might expect on every leg is not; a module that compares sys.version_info, sys.implementation or sys.maxsize, reads sys.flags, calls sysconfig.get_config_var() or probes sys with hasattr/getattr has to state its tier either way, so a version gate never lands on latest alone by omission. The check is syntactic and best-effort: an alias, a flag imported from pcapkit.utilities.compat or a gate in a helper is not seen, and such a module states its tier by hand.

A module opts in when it exercises behaviour that can differ between interpreters or versions:

  • compat shims and version or implementation gates;

  • C-accelerated versus pure paths, and code sensitive to garbage collection, weak references or finalisation;

  • int, bytes and struct edge cases, and sys.maxsize or recursion limits;

  • pickling and copying, metaclass and ABC machinery, and enum mechanics;

  • stream and buffer semantics, threading and locking, and the warning and exception hooks;

  • a third-party engine whose installable releases vary by interpreter, such as pypcap and pypcapfile, which install below 3.12 only, and Scapy, which the integration and pypcap-parity legs install on every interpreter and a test leg off latest skips;

  • the hand-picked round trips, whatever their names, and the #1202 edge-case tables, whose cases are each written out by hand, as the owner ruled on #1958; and

  • the smoke slice: a representative module per protocol family and per package, so each leg still drives the main parse and build paths.

Everything else is LATEST: the per-protocol field-by-field tests, whose behaviour is interpreter-independent pure Python, each real sweep – a round trip over every class or registry entry a table enumerates, every offset of a packet or every capture, as the owner ruled on #1732 and #1958 – and the docs, project and structure tests. The vendor extra is installed on latest alone and the crawlers are pure Python, so the vendor modules are LATEST, each saying so, but for the file-restore and environment-variable tests, which stay on every leg. The tier guard itself is ALL, since tests/conftest.py runs it at collection on every leg.

Project Pins¶

The project pins run once per push (#1954): the modules under tests/project whose run does not vary by interpreter, as they read the repository’s text or drive a util/ script. is_project_pin() in tests/_tiers.py decides, by the AST of each module and of the repository code it runs: a module is a pin unless it, a module it takes names from, or a file it runs by path imports pcapkit, or compares sys.version_info or sys.implementation. A computed import, or a .py name computed for a loader or a child process, counts as importing it, and so does a file that does not parse. Every pin is in the LATEST test tier (see Test Tiers above), and a tests/project module marked __tier__ = 'ALL' is no pin. The modules that import pcapkit are no pins either; those the tiers send to latest run on test’s latest leg, under coverage.

File Size Caps (#1969)¶

A test that writes without bound fills the runner’s disk rather than failing: #1372’s out.json grew to several gigabytes on every run. So every pytest and unittest command in .github/workflows/unit-tests.yml runs as python util/cap_file_size.py python -m ...: test’s Run unit tests; integration’s, pypcap-parity’s and gate’s Run full test suite; the KTLO twins of test, integration and pypcap-parity, which share their steps; the engine cells that engine-tests’ Write the per-cell script writes; unittest-ordering’s cells; and each run step of project-tests.

util/cap_file_size.py sets RLIMIT_FSIZE, soft and hard, to 2 GiB, or keeps a lower hard limit, and execs the command, so the step’s exit status and continue-on-error behave as without it and every process the command starts inherits the cap. A write past it raises OSError: [Errno 27] File too large in Python, since CPython ignores SIGXFSZ, so the test errors; any other program is killed by the signal, whose default action the script restores before it execs. experimental.yml’s experimental legs get the same 2 GiB through prlimit --fsize (see above); its windows leg has no cap, as Windows has no RLIMIT_FSIZE.

tests/project/test_file_size_caps_1969.py fails when a command in unit-tests.yml runs pytest, unittest or util/run_unittest_leg.py without the script, and runs the script against a small limit.

CI Reports (#2030)¶

A report with no pull request to comment on goes to GitHub Discussions. One category, CI reports, holds every report, and each job has one thread in it, titled <workflow file stem>: <job or report name>. A run adds a comment to its job’s thread rather than opening a new one; the comment links the run, names its commit and its status, and ends in a hidden <!-- report-status: ... --> marker. How often depends on the script’s --mode:

  • scheduled: every run posts, on schedule and on workflow_dispatch, since a manual run is a deliberate report.

  • push, for a run on a push or a workflow_run relay of one: a run that warned or failed posts every time, and a green run posts only where the thread’s newest marker is not success, so one “back to green” comment follows a bad run and later green runs stay silent. A thread with no marker counts as green.

ci-timing.yml posts as scheduled to ci-timing: weekly CI timing report, and benchmark.yml to benchmark: weekly engine benchmark report: the ratio table examples/benchmark/native.sh writes, with its absolute-time footnote and the runner it ran on, reporting warning where a Python version was not measured in full (#2125). cron-vendor.yml posts to cron-vendor: vendor constant update report, as push on its workflow_run and scheduled otherwise, and reports warning where vendor-update passed over a failed target or test gate. A failed or cancelled head skips vendor-update, so its discussion job runs on always() and then posts a line of its own with head’s result; a skip on purpose, on a pull request’s workflow_run or a verdict for another commit, skips it too.

cron-conda.yml posts to cron-conda: conda distribution update report by the same rules: push on its workflow_run, scheduled otherwise, and a line of its own for a failed or cancelled head. Its report lists each Platform pins notice and warning from Refresh the platform pins, whose output that step keeps in a log, the files the run changed, and the build Push Changes pushed, or that it pushed none. Its discussion job waits for conda-tag and conda-dist and adds their results, so a failed tag or upload posts as failure. A pin warning reports warning. cron-python-versions.yml runs only on schedule and workflow_dispatch, so it posts as scheduled to cron-python-versions: Python version update report. detect’s report, read from the plan Recompute the tiers writes, lists each tier that moved and why, the files it regenerated, the ruleset edits to make by hand, the script’s notes, the audit’s outcome, and why no pull request opens, if none does. It reports warning for a hand-edit note, for a failed audit of a changed tree, or for an unset vars.RELEASE_APP_CLIENT_ID. Its discussion job needs detect alone, because pr waits for the owner’s approval of github-release, and the pull request it opens is its own record.

lint.yml has no push trigger, so it posts as scheduled to lint: weekly lint report, on schedule and workflow_dispatch, never on a pull request, whose run has checks of its own. Its report lists each tool step’s outcome, then the blocks those steps wrote to the job summary, which each also appends to a file the report reads. It reports warning where an advisory step failed, as each does while its findings stand, and failure where actionlint failed the job. deploy-pages.yml posts to deploy-pages: documentation build report by cron-vendor.yml’s rules: push on its workflow_run, scheduled on its schedule, and never on a pull request or a verdict for another commit. Its report is the results of head, deploy-pages and publish-pages, so it uploads no artifact, and its discussion job checks out the script and util/_actions.py, which it imports, alone. The --status is the publish’s result after a green build, the build’s where the build did not pass, and the gate’s where the gate skipped the build.

The category is the workflow-level REPORT_CATEGORY. The API cannot create one, so it is made by hand, in Settings, Discussions.

The reporting job uploads its report as an artifact, and a discussion job of its own downloads it and runs util/discussion_report.py, which finds the category and the thread by name and opens the thread on first use. That job alone holds discussions: write, beside contents: read for its checkout, so every other job keeps its permissions. It uses GITHUB_TOKEN and first-party actions only. Reporting never fails a run: a missing category, a missing report or a failed API call is one warning, and the job is continue-on-error, since a failed Vendor Update run is one Create Release reads as not updated. A CI timing run failed by a HARD threshold is posted all the same, on always(), and so is a Python Versions run failed by its audit. The report steps of vendor-update, conda-update and detect are continue-on-error on !cancelled(), and come last in each job.

The test workflows report through a workflow_run relay, so none of their own jobs gains a write scope: unit-tests.yml is a reusable workflow whose callers grant contents: read. Unit Tests’ push runs go through coverage-comment.yml, whose discussion job takes a run whose event is push while comment keeps a pull request’s. Experimental Tests’ and Python Compatibility’s go through ci-reports.yml, whose discussion job takes a push or schedule run and never a pull request’s. Both discussion jobs run the same steps, and alone hold discussions: write, with contents: read for a checkout of the default branch’s scripts, never the run’s head, checks: read for the run’s check suite and actions: read for its artifacts. A push run posts as push to <workflow file stem>: <branch> push runs, so main’s Unit Tests thread is unit-tests: main push runs; a scheduled one posts as scheduled to <workflow file stem>: <branch> scheduled runs. Each relayed run’s concurrency group is its own, since a group cancels a pending run when a newer one joins it.

Write the run report runs util/check_suite_report.py, which reads the run’s check suite in a single GraphQL call and renders every name and annotation it quotes as a code span. The report links the run, names its commit and conclusion, the jobs that did not pass, and the warning and failure annotations that count. The conclusion becomes the --status: success, cancelled (and stale), skipped (and neutral), and failure for anything else, timed_out and startup_failure among them. A green run reports warning where a job failed without failing it, or where an annotation counts:

  • On a push run, by the owner’s ruling, an annotation counts only on a non-blocking leg, whose steps are forced to succeed: a job named (KTLO) or (experimental), as a KTLO leg whose tests fail warns (#1672), or an annotation titled (KTLO, non-blocking), as engine-tests’ KTLO cells write. A passing blocking job’s annotations neither count nor appear, unless the run failed.

  • On any other run, which posts every time, every annotation on a passing job counts.

  • pip’s Retrying ... after connection lines never count, on any leg, and neither do the annotations a workflow’s expected list in the script holds as written on every run by design. Each entry is a job, a level and a title prefix, an empty prefix matching only an empty title, so a reworded message still matches. Every list is empty, and tests/project/test_unit_tests_push_reports_2030.py pins them.

A run whose legs all skipped tested nothing, as when current found its commit superseded or changes found no code changed, so where it did not fail it posts nothing, rather than a “back to green” after a bad report. The legs are the jobs those gates skip, which the script names by a pattern per workflow and the test file holds to the jobs’ if:.

The report ends in each job’s summary, one <details> block a job, in the check suite’s order. GitHub serves no job summary through its API, so every step that writes one copies it to the job’s job-summary.md: the scripts through util/_actions.py, where the step sets JOB_SUMMARY_COPY, and the shell with tee. No step that runs the tests sets it, since a test writing the summary through the helper would write into the copy. The job then ends in Name the job summary, which writes the job’s name beside it, and Upload the job summary, which uploads both as the job-summary-<job>-<index> artifact (7 days) for the report to download; both run on always() and are continue-on-error. The summaries share the room a comment leaves, smallest first, and one cut to fit links the run. Run unit tests in experimental.yml sets no JOB_SUMMARY_COPY either: the line util/superseded.py writes there for a stopped run reaches the copy through the watcher’s --summary-copy option, which the tests it runs never see (#2078). The post step runs only where the report step’s post output is true, and sets GITHUB_WORKFLOW to the relayed run’s workflow, which util/discussion_report.py labels the run with.

codeql-analysis.yml posts to codeql-analysis: CodeQL report, as scheduled on its schedule and push on a push to main, and never on a pull request, whose findings belong to the pull request. Its discussion job runs after analyze and alone holds security-events: read, beside discussions: write and contents: read. Write the report runs util/codeql_report.py, which lists the default branch’s open CodeQL alerts by severity, read through GitHub’s List code scanning alerts for a repository endpoint, and hands on the step output status that Post the report to Discussions passes as --status. A success of analyze reports warning while any alert is open and success at none, so every push run with an open alert posts and the first run back at none posts once; any other result of analyze stands. Where the alerts cannot be read, the step writes a warning, the report marks them unavailable, and analyze’s result stands unchanged.

CodeQL Configuration (#2130)¶

Initialize CodeQL in codeql-analysis.yml reads .github/codeql/codeql-config.yml through its config-file input. The config’s paths-ignore leaves out tests and changes nothing else, so the default queries still run over pcapkit and every other path. Python is not built, so an ignored file is left out of the analysis (Specifying directories to scan) and cannot be the source of a data flow.

py/clear-text-logging-sensitive-data and py/clear-text-storage-sensitive-data call a value secret from its name alone, by CodeQL’s sensitive-data heuristics. The tests that build a pcapng Decryption Secrets Block call its bytes secrets. Through extract() those bytes reach logger calls in pcapkit.foundation.extraction and the buffer file’s write in pcapkit.corekit.io, and with tests analysed, a dismissal of each such alert is lost whenever a pull request moves the line it names. The alert on the logger call in pcapkit.utilities.warnings begins in pcapkit itself, at the block’s secrets_length field, the spec’s name for it, so it is still raised and still dismissed by hand. tests/project/test_codeql_config_2130.py pins the config and the input.

Action Pins (#1968)¶

A tag or a branch is a reference its owner can move, so every uses: of an action outside this repository names a full commit, with the release that commit is as a trailing comment:

- uses: actions/checkout@<40-hex commit> # v7.0.1

A step’s uses is therefore the commit alone, as the YAML reads it; the comment is what Dependabot rewrites with the commit on a bump. A local ./ workflow call stays as it is. .github/dependabot.yml watches the github-actions ecosystem from the repository root beside pip, on the same weekly schedule, so a new release reaches the workflows as a Dependabot pull request rather than by a tag moving under a run.

tests/project/test_actions_pinned_1968.py fails on a uses: under .github that names a tag, a branch or a commit without its version comment, and when .github/dependabot.yml drops the github-actions ecosystem. pinned() and versions() in tests/_workflows.py read a pin, for a test that names a particular action.

Workflow Lint (#1967)¶

Lint’s lint job runs actionlint over every workflow in its actionlint step. The step downloads the release that ACTIONLINT_VERSION names and checks it against ACTIONLINT_SHA256, from that release’s checksums file, before unpacking it. Dependabot does not read this pin, so a bump changes both. The workflows use YAML anchors, which actionlint reads from 1.7.10 on, and the pin is 1.7.12 or newer.

actionlint runs the image’s shellcheck over each run: block. Unlike Lint’s other steps, this one blocks: a finding fails the job, as the owner ruled on #1967 once #2023, #2037 and #2038 had fixed every finding it reported. It runs last and on !cancelled(), so a finding skips none of the advisory steps and a failed Python setup does not skip it. Lint is a required check of ruleset 23497679 (#1967), so a red Lint holds a merge. The image’s shellcheck is not pinned, so a runner image that adds a check can turn Lint red on unchanged code; the fix is to the script it flags. The step’s run summary counts the findings by actionlint rule and by shellcheck code.

The step’s -ignore pattern, which matches a message, not a file, hides a false positive: concurrency.queue, which project-status.yml and milestone.yml set and GitHub documents, is a key no actionlint release knows yet (rhysd/actionlint#657). The pattern goes once a release that knows it is pinned.

tests/project/test_actionlint_in_lint_1967.py fails when the step is gone, pins an older release or no checksum, unpacks before it verifies, passes an -ignore pattern other than that, or stops blocking: when it carries continue-on-error, exits with a status other than actionlint’s, or sits above an advisory step or a failed setup would skip it. It fails too when no workflow sets concurrency.queue any more.

Dependency Updates (#1968)¶

Dependabot opens every dependency bump, weekly, from .github/dependabot.yml (the owner’s ruling on #1968):

  • pip over /, /docs and /examples/benchmark. The docs build pins Sphinx and sphinx-autodoc-typehints exactly in docs/requirements.txt, and Dependabot proposes bumps to both pins; the owner accepted that, so each bump is reviewed against the docs build rather than held back. The benchmark’s requirements-*.txt files are watched because nothing else moves them.

  • github-actions over /, per Action Pins above.

Neither conda/requirements.txt nor the benchmark’s image digests are watched: Conda Update’s Refresh the platform pins and Setup Conda Distribution steps rewrite the former, and Dependabot reads only a FROM line that names its image, while the benchmark’s Dockerfile takes its base image through ARG PYTHON_IMAGE from examples/benchmark/python-images.txt.

PyUp opens no bump: .pyup.yml sets update: False and lists no requirements:. A file listed there takes its own update, which defaults to all, so the list would override the global setting. Deleting .pyup.yml would not stop the bot either, as without it PyUp runs on its defaults. The PyUp App’s installation, and the pyup.io/safety-ci commit status it posts, are repository settings.

Python Versions¶

.github/python-versions.toml (#1660) declares every Python version CI runs: one line per version, with its tier – supported, ktlo, experimental, or pre-release, which no version carries – and, where ubuntu-latest cannot provide it, the runner it needs. latest names the newest supported CPython, which every job on one interpreter runs. util/python_versions.py reads the file with the runner’s own python3 – its tomllib needs 3.11, and every image that runs it has 3.12 or newer – and writes each matrix as JSON: a python-versions job in unit-tests.yml and python-compatibility.yml, version_check in create-release.yml and conda-update in cron-conda.yml hand theirs on through fromJSON, and each single-interpreter job reads latest.

A tier change is a one-line edit to that file, plus the matching edit to ruleset 23497679’s Compat contexts. The file’s exemptions list each pin kept off latest, with its reason in the comment above it, such as the conda jobs’ != '3.15'. tests/project/test_python_versions_1660.py fails on a pin the file does not list, on an exemption with no comment, and on a classifier, doc or comment that no longer matches the file – a tier range, the coverage leg’s version. Its tests, and the other tests that read the file, skip on the KTLO interpreters, which have no tomllib. Some edits it names rather than makes: a new pypi KTLO leg needs its own ktlo_* output for release_status, and a pre-release leg needs non-blocking mechanics no workflow has, so the script refuses one.

Python Versions (cron-python-versions.yml) proposes those edits. Every Monday, or on dispatch, its detect job runs util/update_python_versions.py with no secret: it reads python.org’s release cycle, PyPy’s releases, setup-python’s versions-manifest.json and the runner-images README, recomputes the tiers by the rules in that script’s docstring, rewrites the file and the prose these tests pin to it, and runs the audit modules on the result. Only when that changes something does pr enter github-release, so the owner approves only those runs. It mints a release App token (Release Process, “The Release App”) with contents and pull requests write, force-pushes bot/python-versions and opens or updates its one pull request, whose body lists each move and why, the Compat contexts to change in the ruleset by hand, and every renamed check run. It never pushes main, edits the ruleset or writes a workflow file, which that token cannot push, so workflow comments name the tiers rather than restate them. While the branch’s pull request is open, it does not re-push tiers a commit on the branch already proposes, hand edits or merges of main on top or not, nor overwrite commits it did not make: when the branch holds some and proposes other tiers, detect fails before asking for the approval. Once that pull request is merged or closed, the next run with something to propose recreates the branch from main, a closed proposal’s tiers included. It reports a pre-release instead of writing it. Nor does it retire a job (#1747): when the tiers leave a matrix job with no leg, as 3.11 reaching end of life leaves pypcap-parity, it writes them as computed, warns, and puts the job first in the body as a manual step: retire or remove it, and the needs: that list it, such as the one in required-checks, before merging. A proposal is still identified by its tiers alone, so retiring the job on main does not propose them again. The experimental entries are hand-maintained: no source it reads rates them, so every run keeps their lines as written, and a hand edit to one changes no proposal.

Deployment environment:¶

These jobs declare a deployment environment: and can therefore pause for an approval, in create-release.yml and cron-python-versions.yml:

  • github – environment: github-release

  • tag – environment: conda-tag

  • pypi – environment: pypi

  • conda – environment: anaconda

  • pr – environment: github-release, for the release App’s key (see Python Versions)

ANACONDA_TOKEN is a secret of the anaconda environment, and the PYPCAPKIT token and PYPCAPKIT_ACTIONS_DEPLOY_KEY are secrets of conda-tag. GitHub gives an environment’s secrets only to a job that names it, so the scheduled jobs reading them name it too (#1968):

  • Conda Update’s conda-update and conda-tag – environment: conda-tag

  • Conda Update’s conda-dist – environment: anaconda

  • Vendor Update’s vendor-update – environment: conda-tag

A manual run names neither, except Conda Update’s with publish, whose jobs name them as the schedule’s do (#2060).

Both conda-dist and the release conda job have a windows-latest leg, which builds, smoke-tests and publishes the win-64 package (#2060). It blocks as the other legs do: no step continues on error. Its one step that reads ANACONDA_TOKEN is Upload conda packages to Anaconda (Windows), the Intel leg’s anaconda-client call (#2044) under bash -el, which skips a build-only manual run as every upload does. tests/project/test_conda_windows_leg_2060.py pins the leg.

A required reviewer on conda-tag or anaconda would therefore hold every scheduled bump for an approval, besides the release-graph reason Release Process gives for keeping them without one. Each run of these jobs also records a deployment to its environment. tests/project/test_secret_environments_1968.py checks that every job reading one of these secrets names the environment holding it.

No other workflow in scope here declares one – including deploy-pages.yml, whose publish-pages job pushes straight to the gh-pages branch via JamesIves/github-pages-deploy-action rather than through an environment:-gated deployment. Its deploy-pages job builds the site, a pull request’s included, with contents: read, and uploads it for publish-pages, which alone holds contents: write and never runs on a pull request. Its Check gh-pages holds no newer build step skips the deploy when gh-pages already holds the build of a commit this run’s commit is behind, so a build that finishes late cannot replace newer documentation (#1968). Of these environments, only github-release carries a required reviewer; Release Process covers why one approval on that single environment is enough to gate the whole release graph, and is the page to read for the reasoning rather than repeating it here.
