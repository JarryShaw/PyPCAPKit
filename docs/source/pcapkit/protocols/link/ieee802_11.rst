IEEE 802.11 - Wireless LAN MAC Header
=====================================

.. module:: pcapkit.protocols.link.ieee802_11
.. module:: pcapkit.protocols.link.ieee802_11.protocol

:mod:`pcapkit.protocols.link.ieee802_11.protocol` contains
:class:`~pcapkit.protocols.link.ieee802_11.protocol.IEEE802_11`, which implements
the extractor for the IEEE 802.11 MAC header [*]_ of a protocol version 0
frame, as a ``LINKTYPE_IEEE802_11`` capture carries it or
:class:`~pcapkit.protocols.link.radiotap.protocol.Radiotap` hands it on. Its fields, in
the order they appear, numeric ones little-endian:

.. table::

   ======================= ======= ============================================
   Name                    Octets  Present
   ======================= ======= ============================================
   ``frame_control``       2       always (§9.2.4.1)
   ``duration_id``         2       always (§9.2.4.2)
   ``addr1``               6       always (§9.2.4.3)
   ``addr2``               6       Management, Data, and Control frames that
                                   carry a TA (§9.2.4.3, §9.3.1)
   ``addr3``               6       Management and Data frames (§9.2.4.3)
   ``seq_ctrl``            2       Management and Data frames (§9.2.4.4)
   ``addr4``               6       Data frames with To DS and From DS set
                                   (§9.2.4.3)
   ``qos_control``         2       QoS Data subtypes (§9.2.4.5)
   ``ht_control``          4       QoS Data subtypes and Management frames
                                   with +HTC/Order set (§9.2.4.6)
   ======================= ======= ============================================

:func:`~pcapkit.protocols.link.ieee802_11.schema.layout` gives the rule per
frame type. A Control frame of a subtype whose layout this class does not
model, and an Extension frame, are read as the minimal frame format of
§9.2.3: the first three fields only. A Control Frame Extension frame and an
S1G Beacon lay out B8-B15 of Frame Control differently; see
:class:`~pcapkit.protocols.link.ieee802_11.data.FrameControl`.

.. versionadded:: 1.6.0

Scope
-----

* **The frame body** (§9.2.4.7) of a data frame of a subtype carrying one,
  unprotected and holding an MSDU rather than an A-MSDU, is an IEEE 802.2
  :class:`~pcapkit.protocols.link.llc.protocol.LLC` PDU; any other is kept as
  :class:`~pcapkit.protocols.misc.raw.protocol.Raw`. A mesh STA's Mesh Control
  field ahead of the MSDU is not read: bit 8 of QoS Control announces it only
  in a mesh BSS, which the header does not tell.
* **The FCS** (§9.2.4.8), where one was captured, stays at the end of the
  body: this class does not decide whether a capture carries one, which
  behind radiotap is a Flags bit
  :class:`~pcapkit.protocols.link.radiotap.protocol.Radiotap` decodes but does not
  pass on.
* **Pad octets** that radiotap's data-pad flag says follow the header stay
  at the start of the body, for the same reason.
* **A protocol version other than 0** is refused: version 1 is the PV1
  frame format of §9.8, whose Frame Control field is laid out differently,
  and versions 2 and 3 are reserved.
