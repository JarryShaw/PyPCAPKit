1.5.0 -- unreleased
===================

The largest release since 1.0, and the first recorded here as it happened rather
than reconstructed. New extraction engines, ESP with payload decryption,
SCTP and NGAP over SCTP, a library logger that no longer hijacks the consumer's,
and a defect programme run through the issue tracker, citing issues and pull
requests from :pr:`340` to :pr:`2257`.

Preceded by ``1.5.0a1`` (2026-09-15), ``1.5.0b1`` to ``1.5.0b3`` (all 2026-09-19)
and ``1.5.0b4`` to ``1.5.0b14`` (2026-09-20 to 2026-10-22), dated in UTC and all
published as prereleases and so resolved only by ``pip install --pre``.
``1.5.0b1`` half-shipped: the tag, the GitHub release and the Conda deployments
landed, but PyPI rejected the wheel because ``twine check`` found a Sphinx-only
``:mod:`` role in ``README.rst``, which ``pyproject.toml`` declares as the
dynamic long description. ``1.5.0b2`` reshipped it -- an existing version cannot
republish -- and ``1.5.0b3`` followed the CI change that stops a TestPyPI outage from
costing a release its wheels (:pr:`497`, :pr:`498`).

pcapkit.const
-------------

Changed
~~~~~~~

* **a breaking change to** :mod:`pcapkit.const.reg.apptype`.
  :class:`~pcapkit.const.reg.apptype.apptype.AppType` becomes a memberless base over one
  registry per transport protocol -- :class:`~pcapkit.const.reg.apptype.tcp.TCP`,
  :class:`~pcapkit.const.reg.apptype.udp.UDP`,
  :class:`~pcapkit.const.reg.apptype.sctp.SCTP` and
  :class:`~pcapkit.const.reg.apptype.dccp.DCCP` -- because ``aenum`` refuses to subclass
  an enumeration that has members. ``isinstance(TCP.http, AppType)`` still holds and
  ``AppType.get(port, proto=...)`` proxies to the registry, so nothing under
  :mod:`pcapkit.protocols` changes. **The rows IANA assigns no port, and those it
  assigns no transport protocol, stop being members**; they become list-table docstrings
  on the registry that owns them. ``__members_proto__`` is now a per-registry
  :class:`.MultiDict` keyed on port, so every service IANA registers on port 80
  survives. ``get()`` answers with the canonical service, curated from ``/etc/services``
  because IANA names no precedence, and ``get_all()`` reaches the aliases (:pr:`754`).
* the ``%``-formatted ``raise ValueError(...)`` calls in the generated
  :mod:`pcapkit.const.reg.apptype.apptype`, left by :issue:`759`, are f-strings
  (:issue:`792`). The remainder followed: the ``_missing_`` guards in
  :mod:`pcapkit.vendor.tcp.flags`, ``.ftp.command`` and ``.http.method``,
  :class:`~pcapkit.const.reg.apptype.apptype.AppType`'s
  ``__new__``/``__repr__``/``__str__``, and the ``extend_enum`` fallbacks in ``get()``
  and in the span-handling tail. The ``consider-using-f-string`` disable drops from
  ``tcp.flags`` and ``reg.apptype.apptype`` and stays on ``ftp.command`` and
  ``http.method``, whose ``__repr__`` still used ``%``. Edited in the vendor templates
  and applied to the generated const files by hand, since a crawl would fetch IANA's
  live registry and rewrite unrelated rows (:issue:`798`).
* the ``__repr__`` methods :issue:`798` left on ``%``
  (in ``pcapkit/const/ftp/command.py`` and ``pcapkit/const/http/method.py``) are
  f-strings, so the disable drops from both files and both ``pcapkit/vendor/``
  templates. The other bespoke templates (``{const,vendor}/ftp/return_code.py``,
  ``{const,vendor}/http/status_code.py``, ``vendor/http/frame.py``) and
  ``vendor/default.py`` still carry it, so :issue:`804`'s claim that nothing in
  ``pcapkit/{const,vendor}/{ftp,http}/`` needs it holds for this pair only; ``repr()``
  output is unchanged (:issue:`804`).
* ``test_const_enum_no_mint.py``'s ``is_manufactured()`` exemption for the
  hex-suffixed names :pr:`878` (below) preserves moves from a per-*file* to a
  per-*name-shape* one. The per-file exemption was shape-blind: rewriting a branch to ``'Xyplex_%d' % value`` -- exactly the
  value-derived shape the predicate exists to flag -- left the sweep green. The check
  now exempts only a ``'..._0x%s' % hex(value)[2:].upper().zfill(4)`` expression, and
  the exact ``exempt_hits == 53`` bound stays. Test-only. Closes :issue:`879`
  (:pr:`881`).
* **a breaking change to** :attr:`.AppType.proto`: it is the single transport of the
  registry the member lives in, not every transport IANA assigned the service, and
  ``register_apptype`` takes its transports as varargs (:issue:`806`, :pr:`815`).
  Aliases show in ``repr()`` and ``str()``, and can be registered per transport
  (:issue:`807`, :pr:`837`).
* **a breaking change to** :class:`.TransportProtocol`: its base moves from
  ``aenum.IntFlag`` to ``aenum.IntEnum``, so ``|`` between two members gives a plain
  ``int`` rather than a composite member (:issue:`808`, :pr:`836`).
* **a breaking change to** :class:`~pcapkit.const.pcapng.tls_key_label.TLSKeyLabel`: the
  hand-written class in :mod:`pcapkit.protocols.misc.pcapng` becomes the generated
  :class:`pcapkit.const.pcapng.tls_key_label.TLSKeyLabel` (``PCAPNG_TLSKeyLabel`` in
  :mod:`pcapkit.const.pcapng`), crawled from the IANA registry :rfc:`9850` creates
  (:issue:`886`, :pr:`890`), and the old path is removed (:issue:`1744`,
  :pr:`1754`).
* **a breaking change to** :meth:`.Method.get`: the method token is case-sensitive, per
  :rfc:`9110#section-9.1`, so ``Method.get('get')`` no longer resolves to ``GET``
  (:issue:`896`, :pr:`907`). It also looks a key up by value, so
  ``BASELINE-CONTROL`` and ``VERSION-CONTROL`` resolve (:issue:`908`, :pr:`915`).
* **a breaking change to**
  :class:`~pcapkit.const.ipv6.extension_header.ExtensionHeader`: it is generated from
  IANA's IPv6 Extension Header Types registry rather than the Protocol Numbers
  registry's flag, and the two disagree on 147 (``BIT-EMU``) (:issue:`925`, :pr:`926`).
* the TCP and UDP :class:`~pcapkit.const.reg.apptype.apptype.AppType` registries load on
  first use rather than at import (:issue:`1538`, :pr:`1560`).
* **a breaking change to** :class:`~pcapkit.const.mh.lla_code.LLACode`: ``Wilcard`` is
  spelled ``Wildcard`` and ``MH`` is ``MN``, the names :rfc:`5568` gives codes 0 and 2,
  with no alias for either old name (:issue:`1848`, :pr:`1872`).

Fixed
~~~~~

* constant lookups that rejected a value the registry defines. ``RouterAlert(0)`` is
  the only value :rfc:`2113` defines and the one IGMP, RSVP and MLD actually send, and
  it was discarded because the vendor crawler skipped a header row IANA's CSV does not
  have; IPX ``Socket(0)`` is that protocol's own default, so ``bytes(IPX(...))``
  crashed on its own defaults; and the FTP ``_missing_`` overrides were plain
  methods rather than classmethods, so every unregistered value raised ``TypeError``
  instead of extending the enumeration (:issue:`492`, :pr:`503`).
* the string-keyed ``get()`` in :mod:`pcapkit.const.ftp.command` and
  :mod:`pcapkit.const.http.method` tested membership with the raw key but
  registered ``key.upper()``, so the *first* lowercase or mixed-case token
  raised ``TypeError: 'RETR' already in use``. Reachable from wire data:
  :mod:`pcapkit.protocols.application.ftp` matches with ``re.I`` and passes the
  match verbatim, and :rfc:`959#section-5` makes FTP commands case-insensitive,
  so ``retr file.txt`` was a valid request the library could not parse. ``get()``
  and ``_missing_`` now look the key up under the canonical upper-case name, so
  every casing resolves to the existing member; a duplicate ``GET`` would have
  lacked the real one's ``safe`` and ``idempotent`` attributes (:issue:`582`,
  :issue:`583`). :mod:`http.method <pcapkit.const.http.method>` no longer folds case:
  :rfc:`9110#section-9.1` makes the method token case-sensitive, so :meth:`.Method.get`
  matches it exactly (:issue:`896`, above).
* ``get()``'s documented ``default`` was ignored on the integer path across the
  generated :mod:`pcapkit.const` tree, because ``_missing_`` cannot see the caller's
  ``default`` -- ``Hardware.get(99999, 0)`` raised ``ValueError`` instead of returning
  ``0``. The integer path now consults ``default`` before letting the error escape.
  ``-1``, the placeholder the generated signature already carried, still separates "no
  default" from "a default"; :pr:`859` replaced it with an identity sentinel once the
  shared base :pr:`858` (below) put ``get()`` behind one call site. The sweep covers the
  integer registries generated from the shared template, not only those :issue:`584`
  named; ``pcapng`` :class:`~pcapkit.const.pcapng.option_type.OptionType` and ``reg``
  :class:`~pcapkit.const.reg.apptype.apptype.AppType` carry a bespoke integer fallback
  and are deliberately left alone, since neither drops a default by raising. Not
  reachable from wire data, so a contract fix rather than a parse fix (:issue:`584`).
* ``_missing_`` in the Mobility Header flag enumerations
  (:class:`~pcapkit.const.mh.binding_ack_flag.BindingACKFlag`,
  :class:`~pcapkit.const.mh.binding_update_flag.BindingUpdateFlag`,
  :class:`~pcapkit.const.mh.handover_ack_flag.HandoverACKFlag`,
  :class:`~pcapkit.const.mh.handover_initiate_flag.HandoverInitiateFlag`) ended in
  ``return cls(value)``, the constructor that had just failed, so every in-range value
  that is not already a member re-entered ``_missing_`` unbounded and raised
  ``RecursionError`` -- ``F(0)``, no flags set, and every composite such as
  ``BindingACKFlag(0x06)``. Defining ``_missing_`` at all caused it, by shadowing the
  ``aenum`` ``Flag`` machinery that resolves exactly those values;
  ``pcapkit/const/tcp/flags.py`` had none and so never had the defect (it has one now,
  from :issue:`647` below, with the same tail). Each now ends in
  ``return super()._missing_(value)``, as ``pcapkit/vendor/default.py`` emits and most
  const modules (:issue:`647`'s new ones included) already did, so ``F(0)`` is an empty
  flag and ``BindingACKFlag(0x06)`` is ``S|D``. Minting through ``extend_enum`` was
  rejected for a flag type: naming ``0x06`` ``Unassigned_0x06`` would hide the composite
  and add a member per bit pattern. The range guard is untouched (:issue:`623`).
* constant registries rejected an invalid value differently from the built-in
  ``enum``, or did not reject it at all. :class:`~pcapkit.const.tcp.flags.Flags`,
  ``ftp.command.CommandType`` and ``reg.apptype.TransportProtocol`` are ``IntFlag``
  types with no ``_missing_``, so ``aenum`` composed a pseudo-member for any integer:
  ``Flags(-1)`` returned ``65520`` (every TCP flag set, from a value no 16-bit field
  can hold) and ``Flags(-65536)`` none.
  :class:`ftp.command.Command <pcapkit.const.ftp.command.Command>`, :class:`.FEATCode`
  and :class:`http.method.Method <pcapkit.const.http.method.Method>` are ``StrEnum``
  types whose ``_missing_`` called ``value.upper()`` before checking the type, so an
  integer raised ``AttributeError``. These now raise a bare ``ValueError``, as
  ``enum.IntEnum`` does and the other modules already did. :issue:`647`'s proposal to
  replace those with :exc:`pcapkit.utilities.exceptions.EnumError` was deliberately
  rejected: :exc:`.EnumError` is ``(BaseError, TypeError)``, not a ``ValueError``, so it
  would diverge from the built-in, walk past the ``except ValueError`` in every
  generated ``get()`` body (silently undoing :issue:`584`), and log CRITICAL from
  ``BaseError.__init__`` once per discarded default. The one deliberate divergence is
  kept and pinned: mutable registries look up, miss, and ``extend_enum`` rather than
  raising, so ``Method('FROBNICATE')``, ``ProtectionAuthority(1 << 70)`` and
  ``AppType.get(65000, proto=tcp)`` still register; the :issue:`775` and :issue:`860`
  entries below record how each came to return an unregistered member instead. The flag
  guards end in ``return super()._missing_(value)``, so in-range composites still
  decompose and :issue:`623` stays fixed; :class:`~pcapkit.const.tcp.flags.Flags`
  accepts ``0 <= value <= 0xFFFF``. A new
  ``tests/const/test_const_enum_builtin_parity.py`` asserts that every registry raises
  the same exception type as a stdlib ``enum.IntEnum``; it keys on ``aenum.Enum``
  because an ``IntFlag`` is not an ``IntEnum`` subclass, which is how the ``IntFlag``
  ones escaped the existing sweeps (:issue:`647`).
* **a breaking change to** :meth:`.AppType.get`: an out-of-range port is refused
  rather than minted. Its ``except ValueError`` caught the range rejection from
  ``_missing_`` and minted regardless, so ``AppType.get(-1, proto='tcp')``
  returned an unreachable ``PORT_-1_tcp`` while ``TCP(-1)`` raised. It now tests
  ``_missing_`` for ``None`` ("no row for this port") and lets the rejection
  through; a valid but unassigned port still minted, until :pr:`874` (below) made it
  an unregistered member. :meth:`.Transport._make_port`
  **passes an unvalidated** ``int``, **so** ``TCP.make(srcport=99999)`` **now raises
  where it minted junk**; in 1.4.1, ``TCP(srcport=N)`` raised ``AttributeError`` for
  any bare ``int``. Separately, the crawler rendered one ``_missing_`` branch per
  registry row, so the spans IANA registers on more than one transport
  emitted the same condition twice and every registry answered with the first:
  ``AppType.get(6010, proto='udp')`` gave a member whose ``proto`` read ``tcp``,
  ``6666/udp`` answered ``ircu`` rather than ``reserved``, and ``proto='sctp'``
  minted ``x11`` where IANA assigns nothing. A branch naming a transport now
  tests ``cls.__transport__``; the branches naming none are unchanged (:pr:`764`).
* **a breaking change to** :meth:`.AppType._dispatch`: it resolved a ``proto`` naming
  several transports by its lowest set bit, and ``tcp`` is lowest, so every composite
  containing it dispatched into the TCP registry -- silently, and undetectably to a
  caller checking equality, since ``AppType.__eq__`` compares on ``port`` alone.
  :class:`.TransportProtocol` was still an ``aenum.IntFlag`` and a member's ``proto``
  carried the whole set IANA assigned the service, so ``tcp | udp`` was an ordinary
  value to pass back in; the :attr:`.AppType.proto` and :class:`.TransportProtocol`
  entries above record how :issue:`806` and :issue:`808` later retired both. Over
  every multi-transport member this misrouted port 888 (``accessbuilder`` resolved to
  TCP's ``cddbp``) and port 999 (``puprouter`` resolved to TCP's ``garcon``). It now
  raises :exc:`.ProtocolError`, a ``ValueError`` subclass, so the
  documented contract holds. No library caller passes a composite
  (:issue:`759`).
* ``get()``'s string-key miss and every generated registry's ``_missing_``
  bounded-range branch called ``aenum.extend_enum()`` on an unrecognised value, so
  e.g. ``Hardware(40)`` minted a permanent member. Fixed at the shared sites in
  ``pcapkit/vendor/default.py``, plus a new ``register(value, name)`` base classmethod
  for the caller-named path that still mints. Every generated registry is
  updated; the non-minting ``get()`` miss applies to all of them, but the
  ``_missing_`` fix changes behaviour only for those with a bounded-range
  ``extend_enum`` branch. ``pcapkit/toolkit/scapy.py`` and
  ``pcapkit/toolkit/pyshark.py`` fed ``get()`` a string key with no default and now
  raise :exc:`.MissingKeyError` instead of receiving a placeholder; the reader sites in
  ``hopopt.py``/``ipv6_opts.py`` convert
  the ``KeyError`` into :exc:`.ProtocolError`. Riding along:
  ``pcapkit/toolkit/pyshark.py`` gains a ``FILTER_NAME_TO_LINKTYPE`` map
  (``eth`` to ``ETHERNET``, ``tr`` to ``IEEE802_5``), consulted ahead of
  ``LinkType.get`` since pyshark reports a filter name, not a DLT name. The other
  minting call sites in ``_missing_``, ``get`` and the hand-written ``mh.py`` and
  ``ngap.py`` were deferred; the ``register``/``register_alias`` sites are not
  deferred but the by-design caller-named path (:pr:`838`).
* **a breaking change to** :class:`pcapkit.const.ipx.socket.Socket`'s ``_missing_``:
  archived range branches that were strict subsets of a range tested earlier --
  ``(0x0020, 0x003F)`` after ``(0x0001, 0x0BB8)``, and ``(0x4000, 0x4FFF)`` and
  ``(0x8000, 0xFFFF)`` after ``(0x0BB9, 0xFFFF)`` -- so they never fired. The
  generator ``pcapkit/vendor/ipx/socket.py`` now lists each subset range ahead of the
  range containing it. **36891 of the 65521 values that** ``_missing_`` **resolves
  (56.3%) change name**: 32 from ``Registered by Xerox`` to ``Experimental``, 4095 from
  ``Dynamically Assigned`` to ``Dynamically Assigned Socket Numbers`` and 32764 from
  ``Dynamically Assigned`` to ``Statically Assigned Socket Numbers``. No defined
  member changes and every value still resolves (:pr:`847`).
* ``LinkType(209).name`` returned ``'IPMB_LINUX'``, which tcpdump's own table
  marks "Legacy names (do not use)", because a 2024-05-04 regeneration emitted
  that row above the current ``I2C_LINUX = 209`` and ``aenum`` gives a value to
  the member defined first. ``pcapkit/vendor/reg/linktype.py`` sinks a row whose
  note mentions "legacy" after every current row, so the current name is defined
  first; in the registry crawled for this release that affects value 209 alone.
  ``IPMB_LINUX`` stays a reachable alias (``LinkType['IPMB_LINUX']`` still resolves
  to 209). Not breaking: only the canonical name for the shared value moves
  (:pr:`848`). The rule sinks only a row whose value another row also holds,
  counting values inside ranges, so a current row that merely mentions a legacy
  name stays first (:issue:`852`, :pr:`854`).
* **a breaking change to** more const registries' ``_missing_``: applies the
  owner's mint/unmint ruling (settled on :pr:`847`, confirmed on :issue:`775`: a
  final, concrete assigned name mints, and a notation for readers does not) across
  the ``_missing_`` files still calling ``extend_enum``. Most convert wholly, each
  minting a bare status word (``Unassigned``,
  ``Reserved [...]``, ``Reserved for Private/Experimental Use``,
  ``Unspecified in the IANA registry``, ``Deprecated``), which the ruling treats as a
  notation rather than an assignment. Some are mixed:
  :class:`~pcapkit.const.reg.ethertype.EtherType`'s ``DEC Unassigned`` and "Old Xerox
  Experimental values. Invalid as an Ethertype since 1983." branches convert, while
  vendor-company names (Xyplex, Motorola, Walker Richer & Quinn and others) keep
  minting, since a proprietary protocol has no public name beyond the company's;
  ``IEEE802_3_Length_Field`` and ``Berkeley_Trailer_encap_IP`` also keep minting but
  are not company names. :class:`~pcapkit.const.ipx.socket.Socket` (ipx)'s
  allocation-policy names (``Experimental``, ``Dynamically Assigned Socket Numbers``,
  ``Statically Assigned Socket Numbers``, ``Dynamically Assigned``) convert, while
  ``Registered by Xerox`` keeps minting, a real ownership fact. Left alone are
  :class:`~pcapkit.const.mh.cga_type.CGAType`, whose ``Tag_<hex>`` mint is not an
  IANA-style range, and the files holding the classes :issue:`860` moves onto
  :class:`.EnumRegistry` (the ``AppType``, ``StatusCode``, ``ftp.return_code``,
  ``ftp.command``, ``Method`` and ``OptionType`` modules; :pr:`869` and :pr:`874`,
  below). Each conversion changes both the vendor crawler and the generated file, per
  :pr:`838`'s and :pr:`858`'s precedent. The worked examples in
  ``docs/source/contributing/conventions/mint-criterion.rst`` keep
  ``Registered by Xerox`` under Mint (:pr:`861`).
* **a breaking change to** :class:`~pcapkit.const.reg.ethertype.EtherType`'s
  ``_missing_`` ordering: values ``0x0101``-``0x01FF`` now resolve to their Old Xerox
  Experimental name instead of an ``IEEE802_3_Length_Field_0x0101``-style one. The
  generated method tested ``0x0000 <= value <= 0x05DC`` (IEEE802.3 Length Field) first,
  and the Old Xerox range sits wholly inside it, so that branch was unreachable. Unlike
  :issue:`841`'s IPX fix, these bounds come from the live IANA CSV, so the fix is
  general: ``pcapkit/vendor/reg/ethertype.py``'s ``process()`` collects range rows and a
  new ``EtherType._insert_range`` places each ahead of the first already-placed range
  that fully contains it, leaving non-overlapping pairs in CSV order; this pair is the
  only containment among the CSV's ranges. Closes :issue:`862` (:pr:`865`).
* **a breaking change to** :class:`~pcapkit.const.http.method.Method`: ``__new__``
  called ``str.__new__(cls)`` with no argument, so every registered member's ``str``
  payload was empty regardless of value -- ``str(Method.GET) == ''`` and
  ``Method.GET == 'GET'`` was ``False``; ``.value`` was always correct. :pr:`869`
  (above) had fixed the *unregistered* path only, leaving
  ``str(Method('frob')) == 'frob'`` beside ``str(Method.GET) == ''``. Fixed to
  ``str.__new__(cls, value)``, mirroring ``Command.__new__``, in the generator
  (``pcapkit/vendor/http/method.py``) and the generated module. No sibling hand-rolled
  ``__new__`` has the defect
  (:class:`~pcapkit.const.pcapng.option_type.OptionType`/:class:`~pcapkit.const.reg.apptype.apptype.AppType`
  deliberately store a display string). Consequences, all corrections:
  ``Method.GET == 'GET'`` is ``True``; ``bool(Method.GET)`` flips ``False`` to ``True``;
  ``json.dumps(Method.GET)`` emits ``"GET"`` not ``""``; ``sorted()`` is lexicographic
  rather than input-order-stable; and ``{m: ... for m in Method}`` gains an entry per
  member where it had one, because every member previously hashed as ``''`` and compared
  equal. Nothing under ``pcapkit/protocols`` relied on the old behaviour. Closes
  :issue:`870` (:pr:`871`).
* **a breaking change to** :class:`.TransportProtocol` and
  :class:`~pcapkit.const.reg.apptype.apptype.AppType`: step 2 of :issue:`860`, the
  :class:`~pcapkit.const.reg.apptype.apptype.AppType` half (the other bespoke registries
  were :pr:`869`, above). :class:`~pcapkit.const.reg.apptype.apptype.AppType` and its
  transport subclasses move onto :class:`.EnumRegistry` and both mint sites --
  ``_missing_``'s range branches and ``get()``'s own mint (``PORT_{port}_{transport}``
  -> ``'unknown'``) -- now build through a new ``_unregistered_member`` override that
  reconstructs ``svc``/``port``/``proto``, per the owner's ruling that only
  IANA-registered values are legitimate and that ``get()`` lacks the information to
  create new ones. Every branch converts, including those naming a real service assigned
  to a whole port span (``x11``, ``active-net``, ``satvid-datalnk``, ``vrml-multi-use``,
  ``ircu``, ``swx``, ``flex-lm``); unlike :class:`.FEATCode`'s fix (:pr:`869`, above)
  there is no import-time self-mutation to cure by declaring members statically, so
  these stay deliberately unregistered lookups.
  :class:`~pcapkit.const.reg.apptype.apptype.AppType` gains a working ``register()``;
  the base's would have built a member with ``svc='<null>'``. **The breaking part**:
  :class:`.TransportProtocol` moves from power-of-two values
  (``tcp=1, udp=2, sctp=4, dccp=8``) to sequential ``auto()`` (``sctp=3, dccp=4``), per
  the owner's follow-up ruling once ``|``-joined composites stopped being parsed.
  :meth:`.AppType.get` treats whatever ``int`` it is given as a whole, so the
  renumbering changes what specific integers *mean*: on ``AppType.get(80, proto=...)``,
  a bare ``4`` resolved to :attr:`.SCTP.http` on ``main`` and now **silently** resolves
  to ``DCCP.unknown``, because a real member sits at ``4`` under both numberings; a bare
  ``8`` used to mint ``DCCP.PORT_80_dccp`` and now raises ``ValueError``. The
  composed-value case is deliberately untested, per the owner's ruling that a breaking
  change already retired that path (:pr:`874`).
* closes the remaining scope of :issue:`775`:
  :class:`~pcapkit.const.reg.ethertype.EtherType` and
  :class:`~pcapkit.const.ipx.socket.Socket`, the last registries whose ``_missing_``
  minted a permanent member, now return a non-registering
  ``cls._unregistered_member(value, name)``. The issue's AST census of ``extend_enum``
  in ``_missing_``/``get`` is down to the single
  :class:`~pcapkit.const.mh.cga_type.CGAType` carve-out (its mint is not an IANA-style
  range). ``EtherType(0x0888)`` used to add a member to ``__members__`` and return the
  identical object on a repeat; it now returns ``<EtherType.Xyplex_0x0888: 2184>`` with
  ``__members__`` unchanged, absent from ``_value2member_map_``, equal but not identical
  across lookups -- likewise ``Socket(0x0010)``. The regenerated
  :class:`~pcapkit.const.reg.ethertype.EtherType` was not checked against the live IANA
  CSV, only against the committed fixture. Keeping each branch's hex-suffixed name
  reintroduces the value-derived shape ``test_const_enum_no_mint.py``'s
  ``is_manufactured()`` sweep forbids; rather than weaken the predicate, a narrow
  exemption covers exactly these files, since the collision the check guards against
  cannot occur once ``_unregistered_member`` never registers (:pr:`878`).
* :meth:`.OptionType.register()` and :meth:`.Command.register()` built members that
  ``get()`` could not find again, and :meth:`.OptionType.register_alias()` raised
  ``not a registered OptionType`` for every argument. Both registries now round-trip

Changed
~~~~~~~

* :class:`.Probe`, :class:`.CipherSuite` and :class:`.IntegritySuite` are :class:`.Info`
  subclasses rather than ``typing.NamedTuple``. They are Mappings now, so ``len()`` and
  iteration yield field names rather than values. :class:`.TCPSegment` in
  :mod:`pcapkit.toolkit.pcap` stays a ``typing.NamedTuple``, since it is built for every
  TCP frame and an :class:`.Info` costs more to construct.
* :attr:`.ModuleDescriptor.klass` reads an already-imported module out of
  ``sys.modules`` rather than re-entering ``importlib.import_module``, since next layer
  dispatch resolves a descriptor there on a per-frame path. Neither a registry *hit*
  holding a :class:`.ModuleDescriptor` nor a *miss* writes the resolved class back: a
  memoised hit went stale on ``importlib.reload`` (:issue:`1559`), and recording a miss
  in a class-level ``collections.defaultdict`` is the defect
  :issue:`421`/:pr:`426` fixed at this layer, :issue:`425`/:pr:`428` for the option,
  chunk and block registries, and :issue:`555`/:pr:`560` at the schema layer. A
  resolution now costs ~117 ns rather than ~436 ns, which is **not measurable in**
  ``extract()`` **wall clock**. The change is taken for its shape: ``sys.modules``
  stays the only module cache, whereas a memo of the class would serve the pre-reload
  class after an ``importlib.reload`` forever and fail ``isinstance`` against the live
  one. Proposed by ``@Ts-Boom`` in :pr:`563`; the implementation differs because that
  one added a second, never-invalidated cache of resolved classes (:issue:`574`).
* :meth:`.SeekableReader.truncate()` raises instead of returning a size, and the
  misspelled ``writeable()`` is now ``writable()``. Both break external
  callers; nothing inside the package calls either. ``io.IOBase`` documents one
  gate over two methods -- "If False, write() and truncate() will raise
  OSError" -- and this reader's ``writable()`` answers False, yet ``truncate``
  returned its new size, where ``open(path, 'rb').truncate()`` raises. The refusal is
  ``UnsupportedOperation('truncate')``, the same one ``write`` raises; pcapkit's
  subclasses ``io.UnsupportedOperation``. The old resizing is kept as the private
  ``_truncate_buffer``: it resizes a private lookback window, not the stream, and it is
  the only route to the "position sits before the window" state that ``seek`` and the
  buffered read paths must refuse, for which :issue:`643` and :issue:`644` landed
  tests. ``writeable()`` was never an override of anything, so ``io``, ``shutil`` and
  third parties never saw it, and the value reported is unchanged (:issue:`645`).
* **a breaking change to** ``@final``, now enforced at runtime on :class:`.Info` and
  :class:`.Schema`. ``info_final`` and ``schema_final`` both end ``return final(cls)``,
  so every finalised class carried ``typing.final``'s ``__final__`` marker and nothing
  read it. ``@final`` **alone on an** :class:`.Info` **or** :class:`.Schema` **subclass
  -- without** ``@info_final`` **or** ``@schema_final`` **-- now raises**
  :exc:`.InfoError` **or** :exc:`.SchemaError` **at first construction**, the class
  being marked final but never finalised and so carrying no generated ``__init__``.
  ``__init_subclass__`` cannot catch that, since ``final`` applies after class creation,
  so the check sits in the existing one-shot :attr:`.FinalisedState.NONE` branch and a
  finalised class pays nothing. **Deriving from a finalised class raises too**, from new
  :meth:`.Info.__init_subclass__` and :meth:`.Schema.__init_subclass__` hooks (before,
  only :class:`.EnumSchema` had one). :exc:`.SchemaError` **is a** ``ValueError``, so
  code catching ``TypeError`` around a subclass declaration will not see it.
  ``@info_final @final`` and ``@final @info_final`` both finalise silently; the re-entry
  check keys on ``__finalised__`` rather than ``__final__``, because only the former
  records *the decorator* having run. ``@info_final`` twice warns and returns the class
  unchanged. :mod:`pcapkit.utilities.compat` takes ``final`` from ``typing_extensions``
  below 3.11 rather than 3.8, because ``typing.final`` only records ``__final__`` from
  3.11. The guard cannot fire on the library's own classes (:issue:`778`).
* **a breaking change to** :meth:`.Info.to_dict()`: it returns an
  :class:`.OrderedMultiDict` at every level rather than a ``dict``, so a key that
  repeats, such as a second IPv6 extension header of one type, survives a
  ``from_dict(to_dict())`` rebuild. ``type(d) is dict`` no longer holds (:issue:`1453`,
  :pr:`1466`, :issue:`1484`, :pr:`1523`).
* **a breaking change to** ``pcapkit.utilities.decorators``: it moves to
  :mod:`pcapkit.corekit.decorators`, with no re-export. ``seekset``, ``beholder`` and
  ``prepare`` are no longer importable from :mod:`pcapkit.utilities`, and the module
  logs as :mod:`pcapkit.corekit.decorators` (:issue:`1735`, :pr:`1737`).
* **a breaking change to** the sentinels: all live in :mod:`pcapkit.corekit.sentinels`,
  which exports the objects ``NULL``, ``NO_VALUE`` and ``NO_DEFAULT`` and their
  common base :class:`.Sentinel`, but not their types, and ``NoValue`` is spelled
  ``NO_VALUE`` (:pr:`916`, :issue:`911`, :pr:`922`, :issue:`937`, :pr:`939`). No
  moved name keeps a re-export, so
  :class:`.NoValueType` has only that home, not its 1.4.x one in
  :mod:`pcapkit.corekit.fields.field` (:issue:`1744`, :pr:`1754`).

Fixed
~~~~~

* stdlib exceptions leaking out where the library's own were promised: a malformed IP
  field value raised a bare ``ValueError`` instead of :exc:`.FieldValueError`
  (:issue:`465`); a ``bool`` address was silently packed as ``0.0.0.1`` or
  ``0.0.0.0``, ``bool`` being an ``int`` subclass (:issue:`491`, :pr:`500`); and
  ``@prepare`` discarded extra arguments silently and treated a *declared* zero length
  as end of stream, which is now distinguished from a genuinely exhausted one and
  raises :exc:`.StreamEOFError` (:issue:`454`, :issue:`458`).
* :meth:`.FieldBase.unpack` zero-padded up to a field's declared ``length`` with
  ``rjust()`` however little data ``buffer`` held; a ~40-octet PCAP-NG Decryption
  Secrets Block with a bogus inner length forced a multi-gigabyte allocation,
  since ``length`` is often wire-derived. A declared length past 262144 octets --
  libpcap's ``MAXIMUM_SNAPLEN`` and this package's default ``snaplen`` -- that
  the buffer cannot back now raises :exc:`.FieldValueError`; the option and list
  loops' tolerance for a short read past a truncated area (:issue:`431`) is far
  under that ceiling and untouched (:issue:`554`).
* that ceiling bounds one field, and a packet holds many, so the *sum* of a parse's zero
  padding was still unbounded: 200 minimal PCAP-NG Decryption Secrets Blocks (4,800
  wire octets, each declaring ``secrets_length`` 262,142 against two supplied octets)
  retained 50.0 MiB, 10,922x per block, with the per-field guard never firing.
  :meth:`.FieldBase.unpack` now keeps a per-context ledger of octets supplied against
  octets synthesised, and raises :exc:`.FieldValueError` once the total of shortfalls
  *past 65,536 octets* passes ``262144 + 16 * supplied``. The same 200 blocks retain 0.2
  MiB (54.6x). A shortfall of 65,536 octets or fewer, the span of a 16-bit wire length,
  is padded unconditionally and charged to nothing, so no snapshot-truncated capture is
  subject to the budget; without that band the same legitimate frame parsed differently
  depending on what had been parsed before. **What this does not close**: a length
  declared by a 16-bit field can still be repeated without limit, and at this layer a
  crafted file is indistinguishable from a legitimate snapshot-truncated capture of
  offload-sized segments; separating them needs the frame's own
  ``incl_len``/``orig_len``. Nothing resets the ledger, so it bounds everything a
  context has parsed rather than one file (:issue:`573`).
* which exception a malformed TCP SACK option raised depended on unrelated
  process state: a clean interpreter raised :exc:`.ProtocolError` as documented, but
  a process that had popped :mod:`pcapkit.corekit.fields.misc` from ``sys.modules``
  (as the :issue:`439` ABC-cache regression tests do in every ``setUp``/``tearDown``)
  raised :exc:`.FieldValueError` from a different layer, before the documented check
  (:issue:`525`). :meth:`.ListField.unpack` resolved :class:`.SchemaField` through a
  function-local import re-run on every call; a module reimported mid-process
  is a second, distinct class, so ``isinstance`` misclassified the field and
  billed each item by its declared length instead of what it consumed. **Any
  caller relying on the previously-observed** :exc:`.FieldValueError` **now gets**
  :exc:`.ProtocolError`, deterministically, matching the docstring.
* a :class:`.NumberField` whose ``length`` was a callable could not pack or parse at any
  width ``struct`` has a native integer code for. ``length`` is ``-1`` until the
  callable resolves, ``-1`` has no native code, and the template builder raised
  ``_need_process`` for it and never cleared it -- a latch. Resolving the real width
  rebuilt the template but left the latch set, so ``pre_process`` handed ``bytes`` to
  a template that had become ``>Q``
  (``struct.error: required argument is not an integer``), and parsing failed in
  mirror by calling ``int.from_bytes`` on an integer ``struct.unpack`` had produced.
  The flag is now recomputed from the width in force, which also keeps a callable
  resolving to a width with no native code (3 octets) byte-packed. **Every native
  width (1, 2, 4 and 8 octets) was affected, not only the 8 reported**, on
  :class:`.NumberField` and :class:`.EnumField` alike. This made every extended 8-octet
  MPTCP DSS form unbuildable, those widths being chosen at runtime from the DSS flags;
  :pr:`585` worked around it in the TCP schema alone (:issue:`591`).
* :meth:`.NumberField.pre_process` sized a value with floor division dressed as a
  ceiling. When a field is packed while ``length`` is still the ``-1`` placeholder, the
  width came from ``math.ceil(value.bit_length() // 8)``; the ``//`` had already
  floored, so ``math.ceil`` did nothing and the width was one octet short: ``256`` at
  one octet, ``65536`` at two, ``16777216`` at three. **The reach is wider than "just
  past a boundary"**: every bit length that is not a multiple of eight is wrong, so
  ``1`` (bit length 1, floored to *zero* octets) and every value from 1 to 127 failed
  too. It is now the ceiling it was meant to be. The repair is reached only by packing a
  field the caller never resolved (a schema resolves every field first), which is why
  :issue:`591`'s suite, whose values all had byte-aligned bit lengths, missed it;
  :issue:`591`'s fix neither caused nor masked it.
  Deliberately left alone: a signed field is sized without room for its sign bit, so
  an unresolved signed field still cannot pack ``128``. The same typo in the ILNP
  nonce option builders is a separate change (:issue:`599`).
* :meth:`.FieldBase.unpack` padded a short read on the wrong side. When a buffer falls
  short of the declared length -- the accommodation that lets a snapshot-truncated
  capture parse (:issue:`431`) -- the shortfall was zero-filled with ``rjust()``,
  placing the zeros at the *front*, as if the octets never read were the leading ones;
  a short read has lost the trailing ones. It is now ``ljust()``, correct for **both**
  byte orders: one octet of a four-octet little-endian ``120`` read as ``2013265920``,
  and three octets of a four-octet big-endian ``0x01020304`` as ``0x10203``. A full
  read is untouched (:issue:`604`).
* :meth:`.SeekableReader.truncate` put its padding where the reader's bookkeeping says
  the content is, and ``read`` then returned one octet fewer than the buffer held. Same
  family as :issue:`604`, but separate defects. The buffer keeps content at
  ``[0:_buffer_cur]`` with padding behind it, so a reduction must keep the octets it
  has and an extension must append at the *tail*; ``temp[-size:]`` sliced the buffer
  rather than the content, keeping trailing padding and discarding octets read, and
  ``temp.rjust(size)`` prefixed the zeros. Separately, ``read`` capped at
  ``min(size, self._buffer_cur - 1)``, one short at the start and reaching into
  padding further in, and made up the shortfall from the stream *past* the skipped
  octet. The reported symptom needed both: ``read(4)``, ``truncate(8)``, ``seek(0)``,
  ``read(8)`` over ``b'abcde'`` returned ``b'\x00\x00\x00e'`` and now returns
  ``b'abcde'``. Further contract faults are fixed with it: the position was reset
  to the buffer start rather than left alone; an omitted ``size`` resized to ``0``
  rather than the current position; and ``_buffer_cur`` was left addressing octets a
  reduced buffer no longer had, so the next read raised
  ``ValueError: memoryview assignment: lvalue and rvalue have different structures``
  from ``_write_buffer``. ``truncate(0)`` raised the same by a second route
  (``buf[-self._buffer_size:]`` is ``buf[-0:]``, the whole buffer), so
  ``_write_buffer`` now counts from the front; that state is reachable only through
  ``truncate``. A reduction also advances ``_buffer_set`` past the dropped octets,
  keeping ``_buffer_set + _buffer_cur`` equal to how far the stream has been consumed,
  which ``seek`` reads as its licence to fetch more; clamping ``_buffer_cur`` alone
  made that sum under-report, and the next forward ``seek`` silently spliced in octets
  from the wrong offset (``read(8)``, ``truncate(3)``, ``seek(6)``, ``read(1)`` over
  ``b'abcdefghijklmnop'`` returned ``b'l'`` where ``b'g'`` sits at offset 6). Latent
  rather than live: nothing here calls ``truncate``, though it is public
  (:issue:`622`).
* the 16-bit band the :issue:`573` entry above records as deliberately left open: a
  length declared by a 16-bit wire field could still be repeated without limit. The
  crafted PCAP-NG of 2,000 Enhanced Packet Blocks, each with an option declaring 65,535
  octets against four real ones, synthesised 1,637x its size in zeros and now
  synthesises none, with every frame and option still parsed. The bound is taken one
  layer up, where the missing information exists: a PCAP-NG block's Block Total Length
  is authoritative and cross-checked against its trailing copy, so the option area is
  that length less the fixed fields, ``captured_len`` and its padding, and an option
  declaring more payload than the area has left is malformed. A snapshot-truncated
  capture says so through ``captured_len`` and leaves its options whole, so it never
  trips this -- which the :pr:`571` ``len(buffer) < length`` rejection could not
  distinguish, and why it was declined. A new ``bounded_option`` clamps the payload to
  the octets the area has left and warns with :exc:`.SchemaWarning`; it is applied to
  every variable-width option and record payload in the PCAP-NG schema, and
  deliberately not to the block-level payload fields, the 32-bit band the running
  ledger already budgets. A companion ``bounded_area`` clamps a packet block's option
  area to the octets the block itself holds less the trailing Block Total Length: the
  area was otherwise sized from a declared length nothing checks against the file, so a
  block declaring 1,000,000 octets while holding 36 synthesised 65,535 zeros with no
  warning. Both are no-ops on a well-formed block. The non-packet blocks' option
  areas keep the framing assumption; the general fix for a declared length reaching a
  read is :issue:`678`. Clamping rather than refusing keeps the :issue:`431`
  accommodation, since a PCAP-NG block read has no catch point above
  :meth:`.FieldBase.unpack` and one refusal would abort a whole extraction rather than
  one block; and the clamp reads only the block's own declared framing, never a running
  total, so identical input answers identically whatever preceded it. The skip for a
  remainder already past zero is load-bearing on the unpacking path, where clamping
  would give the field a negative template such as ``'-2s'``. No clamp fires on the
  sample captures, and :issue:`678`'s uncaught ``ValueError`` on truncated input is
  unchanged (:issue:`594`).
* **a breaking change to** :attr:`.FieldBase.length`: it called ``struct.calcsize`` on
  a template built from a negative resolved length (e.g. ``'-5s'``, from a
  ``length=`` callback whose running counter had been overdrawn), raising a bare
  ``struct.error`` that ordinary caller code does not catch. The chokepoint every
  affected schema shares now raises :exc:`.ProtocolError`, covering
  ``application/{ftp,httpv1,httpv2,ngap}.py``, ``internet/{hip,ipv6_route,mh}.py``,
  ``link/ethernet.py``, ``misc/pcapng.py`` and ``transport/sctp.py`` with no other
  file changed; a non-negative length is unaffected. This closes the follow-on the
  ``httpv2`` length-guard entry under :mod:`pcapkit.protocols` filed as out of scope
  (:issue:`805`).
* **a breaking change to** :meth:`.EnumRegistry.register()`: it now raises
  ``ValueError`` naming the existing member and pointing at ``register_alias()``, where
  it used to silently alias an already-registered value under the caller's new name --
  ``aenum`` treats a taken value as an alias request, so
  ``register(existing_value, 'TOTALLY_NEW_NAME')`` returned the existing member,
  minted nothing and raised nothing, contradicting its docstring.
  :class:`pcapkit.corekit.enum.EnumRegistry` is a new mixin implementing ``get``,
  ``get_all``, ``register``, ``register_alias``, ``register_aliases`` and
  ``_unregistered_member`` once, per the owner's ruling on :issue:`842`; it
  first converts registries with no bespoke ``__new__``
  (:class:`ipv6.extension_header.ExtensionHeader <pcapkit.const.ipv6.extension_header.ExtensionHeader>`,
  :class:`tcp.flags.Flags <pcapkit.const.tcp.flags.Flags>` and the ``mh.*_flag``
  modules), and serves ``IntEnum``, ``IntFlag`` and ``StrEnum`` alike. The guard reaches
  only those: the other const registries still carry the old generator's bare
  ``extend_enum(cls, name, value)``, so :mod:`pcapkit.const` ships contradictory
  ``register`` contracts until :pr:`858` (below). These also gain the generated
  template's ``KeyError`` catching on a missing name, so ``Flags.get('NOPE', 2048)``
  returns :attr:`.Flags.ACK` rather than raising; and a key that is neither ``int`` nor
  ``str``, which raised ``TypeError`` on the ``IntFlag`` registries
  (``Flags.get(3.5)``), now raises ``ValueError``, tried as a value. On
  :class:`~pcapkit.const.ipv6.extension_header.ExtensionHeader` it raised ``KeyError``,
  the shift :pr:`858`'s entry attributes to the other registries (:pr:`855`).
* **a breaking change to** :meth:`.EnumRegistry.register()`, extended: the const
  registries still on the generated template's bare ``extend_enum`` now inherit the
  guard :pr:`855` (above) added, so ``TransType.register(6, 'TOTALLY_NEW_NAME')``
  raises ``ValueError`` naming the value and the member that holds it and pointing at
  ``register_alias()``, where it used to mint and raise nothing.
  ``pcapkit/vendor/default.py``'s template now emits
  ``class {NAME}(EnumRegistry, IntEnum)`` and drops its own
  ``get``/``register``/``_unregistered_member``. The modules with a bespoke
  ``__new__`` (``ftp/command``, ``ftp/return_code``, ``http/method``,
  ``http/status_code``, ``pcapng/option_type`` and ``reg/apptype`` among them) are
  left alone, so **every other class** inherits :class:`.EnumRegistry` (:pr:`855`).
  ``get()``'s dispatch shifts only for a key that is neither ``int`` nor ``str``
  (``KeyError``, tried as a name; now ``ValueError``, tried as a value), a key type
  nothing in the library passes. ``pcapkit/corekit/enums.py`` is renamed ``enum.py``,
  the owner's ruling (:pr:`858`).
* ``EnumRegistry.get()``'s ``str``-key branch tried only a name lookup
  (``cls._member_map_[key]``) and on a miss raised or returned ``cls(default)``,
  never the *value* path, so on a ``StrEnum`` registry a key that resolved through
  the constructor (``_Str('known-value')``) raised ``KeyError`` through ``get()``,
  and a supplied ``default`` overrode a good value match the code never
  attempted. It now falls back to a plain ``_value2member_map_`` lookup once the
  name lookup misses and before consulting ``default``. Deliberately not
  ``cls(key)``: :meth:`.FEATCode._missing_` (``pcapkit/const/ftp/command.py``) mints via
  ``extend_enum`` for any unrecognised string, so routing through the constructor
  would let a failed name lookup mint a permanent member once a registry like it
  converts; a dict lookup never reaches ``_missing_``. A name still wins when a
  string is both a name and a different member's value. Step 1 of :issue:`860`;
  step 2, converting the bespoke registries, follows (:pr:`869`, :pr:`874`,
  below). The non-``str`` path is unchanged. Widens rather than breaks: a call that
  raised ``KeyError`` now resolves, and no caller that got a correct result gets a
  different one (:pr:`863`).
* **a breaking change to** ``EnumRegistry.get()``: its docstring claimed "It never
  mints", but each ``cls(default)`` call site reached ``_missing_`` for a ``default``
  inside a still-minting registry's range, growing the registry as a side effect of
  resolving ``default`` rather than ``key``. Per the owner's ruling that only
  ``register()`` mints, and ``get()`` only through the ranges ``_missing_`` mints,
  each site now resolves ``default`` through a plain
  ``_value2member_map_`` lookup; ``key`` resolution is unchanged, so
  ``EtherType.get(0x0888)`` still mints ``Xyplex_0x0888`` through its own ``_missing_``,
  as :issue:`775`'s deliberate exception permits. A ``default`` naming no registered
  member now falls through to the error ``key`` itself would have raised, rather than a
  fresh error about the default -- the accepted cost of the ruling. The docstring's "It
  never mints" is qualified to ``default`` only. So
  ``Hardware.get('Definitely-Not-A-Member', 40)``,
  with ``40`` in :class:`~pcapkit.const.arp.hardware.Hardware`'s declared-but-unassigned
  range, now raises ``KeyError`` naming the original key. Closes :issue:`864`
  (:pr:`868`).
* :meth:`.ProtoChain.__add__` returned the left operand's cached ``protocols`` and
  ``aliases``: once ``a.protocols`` had been read, ``a + ProtoChain(IPv4)`` reported
  ``chain == 'Ethernet:IPv4'`` but ``protocols == (Ethernet,)``. ``copy.copy(self)``
  carried the cache across; the result is now built fresh, as ``from_list`` builds one,
  and ``+=`` follows, since it falls back to ``__add__`` (:issue:`1099`).
* a :class:`.SchemaField` with no declared length handed its ``-1`` placeholder to the
  nested schema as that schema's length, so every item of such a list warned
  ``packet length < 0``: a HIP ``LOCATOR_SET`` and an MH CGA
  Parameters item among them. :meth:`.SchemaField.unpack` now passes what is left in the
  buffer as a declared length -- not ``None``, which would turn a truncated item's
  :exc:`.FieldValueError` into ``prepare()``'s quiet :exc:`.StreamEOFError`.
  Fixed-length items are unchanged; the HTTP/2 ``SETTINGS`` pair, whose size is fixed,
  is given it in its own schema instead (:issue:`1140`, below) (:issue:`1148`).
* a signed :class:`.NumberField` decoded as unsigned, a zero-length
  :class:`.PayloadField` misread, and an empty :class:`~pcapkit.protocols.misc.raw.Raw`
  did not rebuild (:pr:`1331`).
* ``from_dict(to_dict())`` lost nested values, and ``len()`` of an :class:`.Info`
  counted its hidden keys (:pr:`1334`).
* :class:`.StringField` packs back exactly the octets it unpacked, where a guessed
  charset, a ``U+FFFD`` substitution or a character-count length used to change them;
  the decoded text is unchanged (:issue:`1293`, :pr:`1336`). A charset that rejects
  ``'replace'`` falls back to UTF-8 (:issue:`1706`, :pr:`1728`), and Python 3.8
  unquotes through ``pcapkit.utilities.compat.unquote`` (:issue:`1693`, :pr:`1707`).
* :class:`.IPv4InterfaceField` keeps a mask that is not a netmask, and a deep copy of an
  :class:`.OrderedMultiDict` keeps its order (:pr:`1346`).
* **a breaking change to** padding: non-zero padding octets are kept on rebuild
  rather than zeroed (:issue:`1223`, :pr:`1436`).
* fields keep the bits and octets they captured on rebuild: a :class:`.BitField`'s
  unnamed bits (:issue:`1487`, :pr:`1495`), a :class:`.NumberField`'s bits outside
  ``bit_length`` (:issue:`1488`, :pr:`1497`), and the bytes an untyped
  :class:`.ListField` unpacked (:issue:`1489`, :pr:`1494`). An unnamed
  :class:`.ListField`, :class:`.PayloadField` or :class:`.SchemaField` gets a default
  name (:issue:`1491`, :pr:`1493`).
* each non-final :class:`.Info` subclass is finalised on its own state (:issue:`1490`,
  :pr:`1496`), and its constructor reads only the class's own annotations
  (:issue:`1692`, :pr:`1702`).
* copying or pickling a stream proxy no longer recurses (:issue:`1524`, :pr:`1544`).
* ``@prepare`` reads ``length`` and ``packet`` by keyword as well as by position, so
  ``Schema.unpack(data)`` and ``Schema.unpack(data, length=2)`` work where they
  raised ``IndexError`` (:issue:`444`, :pr:`450`).
* :class:`.ListField` unpacks a schema item from the per-item copy its callback and
  ``length_callback`` configured, not from the unconfigured original
  (:issue:`433`, :pr:`453`).
* an ``*IntField`` given a ``signed=`` that contradicts its fixed sign, such as
  ``UInt8Field(signed=True)``, raises :exc:`.FieldValueError`; the argument used to be
  discarded silently (:issue:`545`, :pr:`549`).
* negative lengths raise :exc:`.ProtocolError` rather than a bare stdlib error:
  :attr:`.FieldBase.length` tells a malformed template from a negative resolved length
  (:issue:`825`, :pr:`827`), and :class:`.NumberField` checks a negative resolved
  ``length`` and a negative ``bit_length`` (:issue:`828`, :pr:`829`, :issue:`831`,
  :pr:`834`).
* :attr:`.ModuleDescriptor.klass` raises :exc:`.ProtocolError` for a class name that
  resolves to nothing, or one never given, rather than a bare ``AttributeError``; the
  registry modules share one ``NULL`` sentinel compared by identity, where each had
  its own string (:issue:`832`, :issue:`833`, :pr:`835`).
* :class:`.PortEnumField` given a ``proto`` with no ``.name`` -- a string such as
  ``'tcp'``, or a composite such as ``TransportProtocol.tcp | TransportProtocol.udp``,
  which is a bare ``int`` -- raised ``AttributeError`` on a port the registry does not
  hold. The miss takes its transport from the registry's ``__transport__``, as
  :meth:`.AppType.get` does (:issue:`1774`, :pr:`1781`).
* :meth:`.EnumLookup.get` answers a value miss quietly, whether ``default`` answers it
  or the miss is raised: a registry's ``_validate_value`` rejection logs nothing and
  installs no exception hook there, while :meth:`.EnumRegistry.register` still reports
  the same rejection loudly (:issue:`1845`, :pr:`1873`).
* each sentinel is a singleton, as ``None`` is: calling its type, ``copy``,
  ``deepcopy`` and ``pickle`` at every protocol give back the one object, and
  ``NO_VALUE`` reprs as its own name rather than as an object address. Their new
  common base, :class:`.Sentinel`, is public; a sentinel's type cannot be subclassed,
  and neither it nor the sentinel takes an attribute write. A pickle written before this
  change at protocol 0 or 1 still loads, though not as the singleton (:issue:`1841`,
  :issue:`1842`, :pr:`1876`).
* defects off CPython on Linux. On GraalPy, :class:`.SeekableReader`'s reads aliased a
  buffer a later slide rewrote, so they copy out of it, and a :class:`.MultiDict` nested
  each value list, so it is built from a ``dict`` (:issue:`1963`, :pr:`1974`); and a
  sentinel type refused the cache writes ``_py_abc`` makes, so ``isinstance`` against it
  raised ``TypeError`` (:issue:`1960`, :pr:`1966`). ``Field.pack`` hands ``struct`` a

  for ``s`` and ``p`` and GraalPy accepts for ``c`` where CPython does not, so it packs

  Windows, ``SeekableReader(buffer_save=True)`` with no ``buffer_path`` could not reopen
  its temporary file; it creates one it can, and deletes it on ``close()`` or collection
  (:issue:`2098`, :pr:`2105`).
* :class:`.PortEnumField` and :class:`.SwitchField` are exported from
  :mod:`pcapkit.corekit`, :mod:`pcapkit.corekit.fields` and ``pcapkit.all``, and
  :class:`.SchemaField`, ``nested_packet_context`` and :class:`.BytesField` from the

* a :class:`.ListField` callback is handed the per-item copy it configures, not the
  shared field, and a :class:`.SchemaField` with a callable length sizes its template
  from the resolved length rather than ``1024s``. No parse in the library reached either

pcapkit.dumpkit
---------------

Fixed
~~~~~

* a flag value with no declared bits no longer dumps as ``Type::None [0]``. **This
  changes user-visible output in every textual dump format.** ``make_dumper``'s
  ``object_hook`` renders each enumeration member as ``Type::name [value]`` and
  interpolated the name unguarded, but a ``Flag`` value composed entirely of
  undeclared bits has ``name is None``, so the literal ``None`` landed in the name
  half: ``Flags(0)`` rendered as ``Flags::None [0]`` in ``json``, ``tree``, ``text``,
  ``txt``, ``plist`` and ``xml``, out of both :class:`.Extractor` and
  :class:`.TraceFlow`. A nameless member now renders with the value's decimal spelling,
  so ``Flags(0)`` gives ``Flags::0 [0]`` and ``Flags(8)`` gives ``Flags::8 [8]``. That
  is the spelling the enumeration libraries use for an undeclared residue
  (``Flags(2057).name`` is ``ACK|9``), and it cannot be mistaken for a member name,
  since an identifier may not begin with a digit, whereas ``NONE`` is a real declared
  name elsewhere. The guard is on ``name is None`` and not on the value, because the
  defect was never about zero (``Flags(1)`` and ``Flags(9)`` are equally nameless).
  Surfaced by :pr:`634`, which made a flagless TCP segment reach this path
  (:issue:`648`).
* ``tests/dumpkit/test_nameless_enum_rendering_unit.py`` (added by :pr:`670`) carried
  probes assuming every flag-enum registry is 16 bits wide:
  ``test_scalar_return_renders_a_nameless_member_as_its_value`` used one fixed tuple
  ending in ``65536``, and ``test_no_flag_registry_renders_the_literal_none`` swept
  every registry but only against ``registry(0)``. Widths differ:
  ``ftp.command.CommandType`` 3 bits, ``reg.apptype.TransportProtocol`` 4 (computed at
  runtime), the ``mh`` ack/initiate flags 8, and
  :class:`mh.binding_update_flag.BindingUpdateFlag <pcapkit.const.mh.binding_update_flag.BindingUpdateFlag>`
  and :class:`tcp.flags.Flags <pcapkit.const.tcp.flags.Flags>` 16.
  ``tcp.flags.Flags(65536)`` correctly raises (``0 <= value <= 0xFFFF``), so the sweep
  was failing on correct behaviour. The probes now derive each registry's bound from its
  declared members, and a new test pins that one past the widest in-field value is
  refused. Test-only (:issue:`702`).
* the plist writer emitted mapping keys unescaped, so a key carrying ``&``, ``<`` or
  ``>`` produced a report that is not well-formed XML. ``dictdumper``'s
  ``_append_dict`` interpolates the key into ``'<key>{item}</key>'`` and calls
  ``_encode_value`` on the value only, so both branches of :mod:`pcapkit.dumpkit.common`
  that build a mapping now escape their keys through one ``escape_key`` helper -- a
  :class:`.MultiDict`, where :issue:`575` escaped an enum-derived key inline and nothing
  else, and a plain dict, where nothing was escaped. The json, tree and text writers
  are untouched. A non-``str`` key is escaped too: a PCAP-NG decryption secrets block
  keys TLS key log entries by a raw bytes client random whose repr can carry any of
  those characters. The upstream half is ``JarryShaw/DictDumper#125``; this does not
  wait on it. The json writer's quoting defect stands, upstream as
  ``JarryShaw/DictDumper#121`` (:issue:`772`).
* the JSON writer emitted mapping keys unescaped, so the report of ``test.pcapng`` did
  not parse (``Expecting ':' delimiter``): its TLS key log is keyed by a ``bytes`` client
  random whose repr holds ``"`` and ``\``. ``escape_key`` in
  :mod:`pcapkit.dumpkit.common` now JSON-escapes keys for JSON output, as :issue:`772`
  made it XML-escape them for plist, and the JSON report of every ``examples/captures/``
  file now parses. The upstream defect, ``JarryShaw/DictDumper#121``, stands
  (:issue:`1152`). The PCAP-NG end-to-end test of that report no longer skips; test-only
  (:issue:`1795`, :pr:`1809`).
* **a breaking change to** the dump schema: the output writers dropped or corrupted
  what the packets carried. An :class:`.OrderedMultiDict`, which every option list is,
  now dumps as a list of single-key entries in wire order
  (:pr:`1305`). Inside an object the writers fall back on, a class, module or
  function is written as its qualified name rather than expanded, and an object met
  again on its own expansion path as ``<circular reference: T>`` (:issue:`1372`,
  :pr:`1381`).
* tree output raised on a ``complex`` value, and is now documented as lossy
  (:issue:`1266`, :pr:`1366`).
* plist dates are written to whole seconds, so ``plistlib`` reads them back
  (:issue:`1448`, :pr:`1450`).
* a PCAP trace record scales its fraction to the trace's resolution (:issue:`1500`,
  :pr:`1529`), and writes the octets it has rather than a truncated record's claimed
  length (:issue:`1541`, :pr:`1543`).
* a subclass of a dumper ``make_dumper`` builds recursed without end in its
  ``object_hook`` fallback, which called ``super(type(self), self)`` (:issue:`2144`,
  :pr:`2146`).

pcapkit.foundation
------------------

Added
~~~~~

* the ``engine='pypcap'`` and ``engine='pcap_ct'`` extraction engines,
  independent distributions of the same ``libpcap`` interface, and
  ``engine='pypcapfile'`` (:pr:`386`, :pr:`405`). They buy speed by doing less --
  neither ``pypcap`` nor ``pcap_ct`` dissects at all, so they offer no reassembly
  or flow tracing, and ``pypcapfile`` has no IPv6 decoder. Install only **one** of
  ``pypcap`` and ``pcap-ct``: both own the top-level ``pcap`` module, and with
  both present ``pcap-ct`` wins the import and the other becomes unselectable. The
  missing interface constants :data:`~pcapkit.interface.core.PyPCAP`,
  :data:`~pcapkit.interface.core.PCAP_CT` and :data:`~pcapkit.interface.core.PyPCAPFile`
  are now exported alongside :data:`~pcapkit.interface.core.DPKT`,
  :data:`~pcapkit.interface.core.Scapy`, :data:`~pcapkit.interface.core.PyShark` and
  :data:`~pcapkit.interface.core.PCAPKit` (:pr:`412`). Python 3.11 is the last
  interpreter on which every built-in engine can run, and even there ``pypcap`` and
  ``pcap-ct`` cannot coexist.
* :meth:`.EngineBase.unsupported_reason`, a preflight every engine answers and
  :meth:`.Extractor.run` consults before anything is imported. An engine that cannot
  run in the current environment now gives one warning naming the real cause (a
  Python version, a missing ``tshark`` or ``libpcap``, the wrong ``pcap``
  distribution) and a clean fall back to ``pcapkit``'s own parser, rather than an
  error from inside the third-party package (:pr:`396`, :pr:`405`). The same holds
  for an engine whose package is not installed at all (:issue:`1045`).
* ``conflict`` on the reassembly data models: absolute, inclusive ranges where
  two fragments claimed the same span with different bytes, previously lost
  silently on both the IP (:pr:`482`) and TCP (:issue:`443`, :pr:`478`) paths.

Changed
~~~~~~~

* ``layer=`` and ``protocol=`` are honoured rather than inert. Both were read
  under the wrong names, so every value a caller passed was dropped into
  ``**kwargs``; the CLI's ``-L`` also now validates its argument. The packet
  context reaches the schema layer for the first time, so a field the wire elides
  can be resolved from its enclosing packet (:pr:`404`). ``follow_tcp_stream``
  dispatches on the engine type, where both branches of the old test were dead and
  the native adapter ran against every engine's frames (:pr:`402`).
* reassembly and flow-tracing defaults moved (:pr:`435`), visible to
  a caller. ``Datagram.completed`` widened from ``bool`` to a :class:`.Completion`
  enumeration (``COMPLETE``, ``PARTIAL``, ``TIMEOUT``); only ``COMPLETE`` is truthy, so
  ``if datagram.completed:`` is unaffected but ``datagram.completed == True`` no
  longer holds. TCP flow tracing is **bidirectional by default**, which merges each
  flow's two halves and closes one only once both have FINed -- 331 flows become 111
  on the sample HTTP capture, the difference being single-frame stray tails; pass
  ``trace_bidirectional=False`` for the old behaviour. IP reassembly also gained the
  60-second timeout [:rfc:`1122`, :rfc:`8200`], clocked off the capture's own
  timestamps, tunable with ``reasm_timeout=``; TCP reassembly gets no timeout by
  default. ``trace_analyse=`` is new, and reassembles each traced flow's application
  layer.
* conflicting TCP overlaps resolve first-write-wins, per :rfc:`9293` section 3.10,
  where they had silently resolved last-write-wins (:issue:`443`, :pr:`478`). A
  deliberate, narrow behaviour break: a conforming retransmission carries
  identical bytes. IP fragment reassembly keeps last-write-wins, because
  :rfc:`791` specifies the opposite resolution, and records the disagreement
  instead (:pr:`482`).
* renames with no compatibility alias left behind: ``HoleDiscriptor`` is spelled
  :class:`.HoleDescriptor` and its package alias ``TCP_HoleDiscriptor`` is
  ``TCP_HoleDescriptor`` (:pr:`350`).
* subclass registration is **opt-in** for :class:`.Engine`, :class:`.Reassembly`,
  :class:`.TraceFlow` and ``dumpkit``'s :class:`.Dumper` (:issue:`514`). Each registers
  if and only if its registry keyword is given -- ``engine=`` for :class:`.Engine`,
  ``protocol=`` for :class:`.Reassembly` and :class:`.TraceFlow`, ``fmt=`` for
  :class:`.Dumper`. Previously an absent keyword fell back to the class' own name, so
  *every* subclass of the public class was registered, and declining meant subclassing
  the parallel ``*Base`` class under an alias, which every built-in does (hence no
  public class had a subclass, while every built-in derives from its ``*Base`` class).
  **This breaks out-of-tree code that subclasses one of these classes and relies on the
  derived key**; pass the keyword, or call the matching ``register_*`` function. Nothing
  the library ships is affected, and the ``*Base`` classes remain importable. Silent
  failures are now loud: an unrecognised class keyword raises :exc:`.UnsupportedCall`
  instead of being swallowed by ``**kwargs`` (passing ``name=`` to a
  :class:`.Reassembly` subclass silently ignored the key, since ``protocol=`` is the
  real one), and so does :class:`.Dumper`'s ``ext=`` without ``fmt=``. A class attribute
  is not an opt-in: ``__engine_name__`` and ``__protocol_name__`` still set the name a
  class reports, registered or not. Each metaclass gained a class-level ``registry``
  property mirroring :attr:`.EnumSchema.registry`, and a :class:`.Dumper` subclass no
  longer touches the filesystem while its ``class`` statement runs. :class:`.Engine`'s
  keyword is ``engine=`` rather than the ``name=`` first shipped, because ``mcls``,
  ``name``, ``bases`` and ``namespace`` collide with ``abc.ABCMeta.__new__``'s
  parameters on Python 3.10 and raise ``TypeError`` before the hook runs. There is no
  ``name=`` alias: a keyword that works on some interpreters and not others is the trap
  being removed.
* **a breaking change to** :meth:`.Extractor.register_engine`, ``register_reassembly``
  and ``register_traceflow``, and the ``register_extractor_*`` wrappers over them: each
  now accepts only a subclass of the public :class:`.Engine`, :class:`.Reassembly` or
  :class:`.TraceFlow` (:issue:`1016`). They had accepted a subclass of the matching
  ``*Base`` class since :issue:`513`, which was a tolerance for pcapkit's own
  built-ins (every built-in derives from the base, none from the public class) rather
  than a contract: ``*Base`` is documented as internal, and the public class is the one
  carrying the registration hook. Third-party code that subclasses :class:`.EngineBase`,
  :class:`.ReassemblyBase` or :class:`.TraceFlowBase` directly and registers through
  these functions now gets :exc:`.RegistryError` naming the public class; subclass the
  public class instead. The error messages are unchanged. The built-ins never pass
  through a registrar; ``Extractor._register_internal_engine`` and its sibling internal
  registrars check the base for internal registration, and are what the :issue:`513`
  regression test now exercises. ``register_protocol`` is untouched (:pr:`1020`).
* extraction is around 46% faster on a 1,117-frame HTTP capture, with byte-identical
  output (:pr:`420`). A reassembled datagram's payload is analysed on first read
  rather than eagerly, cutting IP reassembly's own cost by 90.7% and TCP's by 23.7%
  (IP reassembly submits a datagram for every frame, fragmented or not) (:pr:`424`).
  Flow tracing over the same capture went from 1416.6 ms to 744.0 ms, because the flow
  dumper handed each record to a :class:`~pcapkit.protocols.misc.pcap.frame.Frame`
  constructor that re-dissected the whole stack to return the bytes it had just been
  given; options are no longer parsed twice either (:pr:`427`).
* **a breaking change to** :attr:`.Extractor.engine` and
  :meth:`.Extractor.record_header`: both are now declared to return ``EngineBase[_P]``
  rather than :class:`.Engine`, and the private ``_exeng`` attribute follows. The
  built-in engines subclass :class:`.EngineBase` directly, so none was ever an
  :class:`.Engine`, which adds only the ``__init_subclass__`` registration hook. A type
  checker sees the change: code passing the result to an :class:`.Engine`-typed
  parameter must now accept :class:`.EngineBase`; and because the old declarations were
  *unparameterised*, ``engine.read_frame()`` and ``record_header().read_frame()`` used
  to be ``Any`` and are now the extractor's own frame type, so an assignment that relied
  on ``Any`` there no longer type-checks (:issue:`1022`).
* the documentation of the engine base classes: the member stubs (``name``,
  ``module``, ``registry``, ``extractor``, ``unsupported_reason``, ``run``,
  ``read_frame``, ``close`` and the rest) moved from :class:`.Engine` to
  :class:`.EngineBase`, where they are defined, and :class:`.Engine` now documents only
  the ``__init_subclass__`` registration hook it adds, so the ``EngineBase[_P]`` that
  :attr:`.Extractor.engine` returns leads to an API. Cross-references to ``Engine.run``,
  ``Engine.read_frame``, ``Engine.close`` and ``Engine.unsupported_reason`` now point
  at :class:`.EngineBase`, which stays out of ``__all__``, as :issue:`1016` settled
  (:issue:`1024`).
* **a breaking change to** ``register_mh_extension``: ``schema`` is keyword-only, as
  in the other schema-taking registrars (:issue:`516`, :pr:`526`).
* the ``pypcap`` and ``pcap_ct`` engines probe the ``pcap`` backend once per extraction
  rather than three times, and find its distribution without parsing each candidate's
  ``METADATA``, which ``importlib.metadata`` does on Python 3.15 and which made
  ``pcap_ct`` extraction about 2.4x slower there (:issue:`2110`, :pr:`2112`,
  :issue:`2113`, :pr:`2121`).

Fixed
~~~~~

* TCP reassembly mixed absolute sequence numbers with buffer-relative slicing, so
  on any capture carrying a SYN with a realistic initial sequence number
  incomplete datagrams were dropped silently, and the ``completed=False`` branch
  of the public API was unreachable (:issue:`349`, :pr:`376`).
* ``format='text'`` raised ``AttributeError`` before writing anything, naming a
  ``dictdumper.Text`` that has never existed. It now points at ``Tree``, as the
  ``'txt'`` alias beside it already did.
* :class:`.Extractor` had the ownership of its input stream inverted: a handle it opened
  itself, from ``fin`` given as a path, was **never closed**, while a stream the
  *caller* supplied and still needed **was**. ``_cleanup`` closed under
  ``not self._flag_s`` (the flag that gated the ``open()``), and the
  :class:`.SeekableReader` wrapping a non-seekable input asked for
  ``stream_closing=not self._flag_s`` in the same wrong direction. The leak was one
  descriptor per extraction, which surfaced as a ``ResourceWarning`` failing the test
  suite (:pr:`577`, :pr:`596`, :pr:`600`; :issue:`606` only made the test immune).
  Both conditions now follow ownership via a single ``Extractor._owns_input``, and a
  finaliser releases the handle of an extraction *abandoned* before end of file
  (``auto=False``, iterated part way and dropped); the files :issue:`610` names
  emit no such warning. Leaving a ``with`` block follows the same rule, so a caller's
  stream stays open after it (:issue:`1999`, :pr:`2000`). The finaliser is a
  ``weakref.finalize``, so it also runs where ``__del__`` never does, as on GraalPy
  (:issue:`1997`, :pr:`1998`).
* ``extract(..., no_eof=True)`` never returned. End of stream was detected and
  ``ExtractionWarning: EOF reached`` fired, but every loop that handles it
  (``record_frames``, ``__next__``, ``__call__``) read ``if self._flag_n: continue``,
  so the flag suppressed the error that *ended* the loop without supplying another
  ending and an exhausted input was retried forever. The flag is not pointless --
  ``__main__`` sets ``no_eof`` for ``fin='-'``, and the end of what has arrived on a
  live capture is not the end of the capture -- so this is a termination condition
  rather than a deletion. The input's own position tells a paused capture from a
  finished one: ``prepare`` raises end of stream when zero bytes remain and restores
  the position first, so two consecutive ends of stream at the same position mean
  nothing arrived between them (``Extractor._note_eof_progress``). A pipe is
  unaffected, since a read there *blocks* while the writer is open but idle. This also
  fixes ``pcapkit -``, which hung on **any** finished stdin. **One deliberate
  narrowing**: a *seekable* input does not block, so a file still being appended to
  ends at the data present when the extraction reached it; a timed grace period would
  make the cut-off intermittent rather than absent, so following a growing file is
  left to a policy of its own. Pre-existing and untouched: an append landing
  *mid-record* raises ``ValueError: read length must be non-negative or -1``. The
  end-to-end tests are bounded by a **child process** rather than
  ``tests._support.time_limit``, because the in-process deadline proved intermittent on
  this loop, and an intermittent guard against a hang leaves a wedged suite rather than
  a red test. Guesses at the cause are ruled out: the parse path's
  ``except Exception`` handlers are never entered during the spin, and the memory is
  the retry loop's ``EOF reached`` records, which the runner retains (:issue:`620`).
* ``register_protocol`` displaced one protocol class with another and said nothing.
  The registry behind :data:`pcapkit.protocols.__proto__` is keyed on
  ``cls.__name__.upper()``, and several dispatchable classes are named ``HTTP``
  (the base :class:`pcapkit.protocols.application.http.HTTP` and the ``httpv1`` and
  ``httpv2`` implementations), so a bare assignment decided the winner:
  ``register_protocol(httpv2.HTTP)`` moved ``__proto__['HTTP']`` to the ``httpv2``
  class with no exception, log line or :exc:`.RegistryWarning`, and
  ``ProtocolBase.expand_comp('HTTP')`` then resolved to whichever registered last. The
  overwrite now raises a :exc:`.RegistryWarning` naming the displaced and the replacing
  class. The sharpest path is not a call to the registrar:
  :meth:`.Protocol.__init_subclass__` registers unconditionally, so merely *defining* a
  subclass of the public :class:`~pcapkit.protocols.protocol.Protocol` under a name a
  built-in holds displaced that built-in. A plain ``import pcapkit`` emits zero new
  warnings: the built-in ``HTTP`` classes derive from :class:`.ProtocolBase`, so
  ``__init_subclass__`` never fires for them, and import-time seeding keys off the
  distinct names ``HTTP``, ``HTTPv1`` and ``HTTPv2``. The guard deliberately reads "key
  present and the incumbent is a different class", not mere presence (:pr:`726` later
  gave its sibling registrars the same identity guard): this function is the funnel
  every wrapper registrar ends in, so registering one class under two codes
  (``register_tcp`` then ``register_udp``, a documented path) reaches it twice with
  nothing displaced. The collision is reported, not resolved: re-keying is a
  registry-format change that none of the bare-name readers can absorb (each degrades
  *silently* to a string or :class:`~pcapkit.protocols.misc.raw.Raw` on a miss), so it
  belongs to the registry redesign in :issue:`514`. The issue called this the one
  registrar with no warning; in fact none warned by itself, the siblings only by
  delegating to a guarded classmethod (:issue:`675`).
* the ``#:`` autodoc comments in ``pcapkit/foundation/traceflow/traceflow.py`` that
  named a bare ``Type``, which Sphinx resolves against every class named ``Type`` in
  the project rather than ``typing.Type``, and silently linked to
  :class:`pcapkit.const.l2tp.type.Type`, an L2TP field-type enum; once :issue:`684`
  rendered :attr:`.TraceFlow._foutio`, the built docs pointed at the wrong class with no
  warning. These sites now spell it ``~typing.Type[Dumper]``, among the sites
  :issue:`709` lists. The other bare ``Type`` sites, in hand-written
  ``:type:`` fields under ``docs/source/pcapkit/foundation/``, are fixed separately by
  :pr:`714` (:issue:`709`).
* ``register_protocol``'s overwrite warning could claim a protocol was replaced with
  itself. The guard was correct (``incumbent is not protocol``, an identity check from
  :pr:`681`), but the message built both operands with a bare ``repr()``. A factory
  defining a same-named closure-local class on every call (as
  ``tests/protocols/test_construction_keyword_check_unit.py``'s ``_protocol_class``
  does) produces two distinct classes sharing one ``__module__`` and ``__qualname__``,
  so a real overwrite read "overwriting X with X." The message now compares the two
  reprs and, only when they coincide, appends each object's ``id()``;
  ``__module__``/``__qualname__`` would not disambiguate, being what the repr already
  renders (:issue:`710`).
* more registrars warned on mere key presence rather than an actual overwrite,
  outside the wording of :issue:`718`'s identity guard
  (``incumbent is not None and incumbent is not new``, landed by :pr:`726`), whose issue named only code-keyed
  registrars: ``register_engine``, ``register_reassembly`` and ``register_traceflow``
  on :class:`.Extractor`, and ``register_dumper`` on both :class:`.Extractor` and
  :class:`.TraceFlow`. Each now compares the incumbent by identity
  before warning; both ``register_dumper`` sites compare only the stored dumper, so
  re-registering with just a new file extension stays silent too. Non-breaking: a
  correct caller sees strictly fewer warnings (:issue:`739`).
* **the class registrars listed below** now raise :exc:`.RegistryError` for a non-class
  argument, where a bare ``TypeError`` ("issubclass() arg 1 must be a class") used to
  escape -- from the guard itself for the ``register_dumper`` methods, and from inside
  ``abc`` for the others. They are ``register_dumper``, ``register_engine``,
  ``register_reassembly`` and ``register_traceflow`` on :class:`.Extractor`,
  :meth:`.TraceFlow.register_dumper` (reached
  through ``register_traceflow_dumper``), and
  :func:`pcapkit.foundation.registry.protocols.register_protocol`. Each guard gains an
  explicit ``isinstance(x, type)`` test ahead of its ``issubclass``; in those that
  accept a :class:`.ModuleDescriptor` it runs after the descriptor is unwrapped, so a
  descriptor naming a non-class attribute is rejected too, while ``register_protocol``
  takes no descriptor. No guard's target class changes, and a wrong class still raises
  :exc:`.RegistryError` as before. :exc:`.RegistryError` subclasses ``TypeError``, so
  ``except TypeError`` still catches it; a caller matching the exact type, or the old
  message, does not. The same guard in the protocol ``register`` classmethods is
  fixed separately by :issue:`1026` (:issue:`1021`).
* a missing extraction engine package now gives a single :exc:`.EngineWarning` rather
  than a duplicate (:issue:`1045`, :pr:`1046`). :meth:`.Extractor.import_test` warned
  that the package was absent, then :meth:`.Extractor.run` warned again when it fell
  back to the default engine; ``run`` now stays silent there, and ``import_test`` says
  what ``run`` used to:
  ``engine <name> (<module>) is not installed; using default engine instead``, the
  module name in backticks. Only code that matched ``import_test``'s old wording, or
  that expects the duplicate warning, breaks.
* :class:`.Extractor` defects: :attr:`.Extractor.output`'s :exc:`.UnsupportedCall` named
  ``format`` rather than ``output``; ``make_name`` looked an unknown format up in the
  ``__output__`` ``defaultdict`` and so inserted it; and the Scapy engine never set
  ``_offmt``, so :attr:`.Extractor.format` raised ``AttributeError`` under
  ``engine='scapy'`` (:issue:`1095`).
* the DPKT, Scapy and PyShark engines call :meth:`.Extractor.record_header()` at setup
  again, as they did until 2023, so the global-header step is shared with the default
  engine and sets ``_offmt`` for each of them. **Their dumped output changes**: JSON,
  plist and tree reports gain the leading ``Global Header`` record (``Section Header 1``
  for PCAP-NG) the default engine already writes, identical to its, and ``files=True``
  writes that record's file too; frame records are unchanged. :attr:`.Extractor.format`
  now also answers on a capture with no frames. ``format='pcap'`` failing on every
  engine is a separate defect, :issue:`1127` (below) (:issue:`1104`).
* ``format='pcap'`` failed on every engine with a ``TypeError`` from
  ``PCAPIO.__init__()``, missing ``protocol``: :meth:`.Extractor.__init__` created the
  writer before any global header was read, so :class:`.PCAPIO` had no link type. The
  header step now creates it through :meth:`.Extractor._open_output`, and ``run()``
  opens it for engines with no such step; a PCAP writer takes the frame itself and skips
  the ``Global Header`` record, so the default engine writes ``in.pcap`` back byte for
  byte. The third-party engines hand the writer no frame octets, so they fall back to
  JSON with a :exc:`.FormatWarning`, as their flow tracing already does, and a PCAP-NG

  PCAP files did not come back byte for byte; the PCAP engine now passes those fields
  through ``_open_output`` to :class:`.PCAPIO`, and every one does (:issue:`1165`).
* IP reassembly reports only the octets it holds: a truncated fragment, a strict run
  and a zero-length datagram no longer report octets from the declared Total Length
  (:pr:`1368`). Only the final fragment's partial block counts, and a datagram too
  long for its length field never completes (:pr:`1582`, :issue:`1585`,
  :pr:`1598`).
* TCP reassembly judges completion from each buffer's own gaps, compares sequence
  numbers modulo ``2**32``, and holds a FIN until reordered data arrives
  (:pr:`1375`). A TSO fragment's length is its captured length, and ``RCVBT`` covers
  the last block (:pr:`1564`).
* a second TCP flow with the same label truncated the first flow's file; a reused
  label now gets the next free suffix (:issue:`1360`, :pr:`1371`).
* the engine, reassembly, traceflow and dumper registrars accept a built-in back under
  the name it shipped with, restoring the shipped entry after an override; the engine,
  reassembly and traceflow registrars still refuse any other built-in
  (:issue:`1363`, :pr:`1376`).
* PCAP-NG blocks are numbered across the whole file, not per section
  (:issue:`1256`, :pr:`1426`).
* ``format='pcap'`` is kept when an unavailable engine falls back to the default one
  (:issue:`1264`, :pr:`1430`).
* ``extract()`` accepts a file object with no ``name`` as ``fin`` (:issue:`1506`,
  :pr:`1509`), and reads every frame from a pipe or other non-seekable stream
  (:issue:`1586`, :pr:`1595`).
* the third-party engines read what the capture holds. The dpkt engine keeps a frame
  dpkt cannot parse rather than leaking ``AttributeError`` (:issue:`1351`,
  :pr:`1377`), applies each PCAP-NG interface's link type and timestamp resolution
  rather than the first one's (:issue:`1379`, :pr:`1396`), and reads float
  timestamps, Simple Packet Blocks and raw-IP frames (:pr:`1550`). The scapy engine
  resets its interfaces at each PCAP-NG section (:issue:`1522`, :pr:`1546`), takes a
  packet's link type and clock from its interface (:pr:`1563`), and reads each record
  whole (:issue:`1717`, :pr:`1733`). The pyshark engine skips non-packet PCAP-NG
  blocks (:issue:`1515`, :pr:`1531`), and the pypcapfile engine reads the PCAP
  records pypcapfile drops (:issue:`1512`, :pr:`1569`). dpkt and scapy write real PCAP traces
  (:issue:`1507`, :pr:`1511`).
* a callable passed as ``verbose=`` is called on every engine. The scapy, dpkt,
  pyshark, pypcap, pcap-ct and pypcapfile engines replaced it with their own printer,
  which now runs only for ``verbose=True``, its output unchanged (:issue:`1874`,
  :pr:`1880`).
* an :class:`.Extractor` whose constructor raises closes what it owns, the input it
  opened and then the engine it chose, so a PyShark capture's ``tshark`` does not
  outlive it; the original exception still propagates, and a caller's stream stays open
  (:issue:`2100`, :pr:`2106`, :issue:`2107`, :pr:`2119`).
* ``engine='pypcap'`` warns and falls back to the default engine when the ``pcap`` module
  is installed but cannot load, as ``engine='pcap_ct'`` already did, where it raised the
  loader's ``OSError`` (:issue:`2132`, :pr:`2133`).
* TCP reassembly bounded its holes with ``sys.maxsize``, which on GraalPy and 32-bit
  builds is ``2**31 - 1``, inside TCP's sequence space, so a stream past it never
  completed. The bound is
  :data:`~pcapkit.foundation.reassembly.data.tcp.HOLE_OPEN_BOUND`, ``2**63 - 1``, the
  value 64-bit builds already used (:issue:`1959`, :pr:`1965`).
* the method-name registrars, such as ``register_ipv4_option``, and
  ``register_linktype``, ``register_pcap``, ``register_pcapng``, ``register_ethertype``
  and ``register_transtype`` refuse a ``code`` that is not an enum member with

pcapkit.protocols
-----------------

Added
~~~~~

* ESP parsing and construction [:rfc:`4303`], with optional payload decryption and ICV
  verification through ``cryptography`` (``pip install pypcapkit[crypto]``)
  (:pr:`378`). Keys reach the dissector through a new caller-state channel,
  :mod:`pcapkit.corekit.context`, surfaced as the ``context=`` keyword on ``extract()``
  and :class:`.Extractor`, carrying an :class:`.esp.SecurityAssociation`. Nothing here
  raises: with no association the SPI and sequence number are still reported and the
  ciphertext is left opaque with ``status=NO_SA``, and a failed decryption or ICV
  check is recorded on the parsed result the same way. Extended Sequence Numbers, TFC
  padding and anti-replay are not implemented, and an unsupported cipher or MAC is
  refused with a clear error rather than half-processed.
* SCTP as a transport protocol [:rfc:`9260`]: every chunk type, chunk
  parameter and error cause it defines, with the CRC32c both recorded and verifiable (it
  covers the SCTP packet alone, with no IP pseudo-header). Upper layers register
  on the DATA chunk's Payload Protocol Identifier through ``register_sctp``, not
  on a port (:pr:`379`).
* NGAP over SCTP (3GPP TS 38.413), decoding aligned PER through ``pycrate``
  (``pip install pypcapkit[NGAP]``) (:discussion:`251`, :pr:`417`). Decoding is
  generic by ASN.1 shape rather than per-procedure, so every
  elementary procedure and protocol IE works and a new 3GPP release needs no code
  change. Registered as a default on PPID 60 and 66, but only 60 decodes: PPID 66
  is an NGAP PDU inside a DTLS record, and there is no DTLS dissector. ``pycrate``
  was at first left out of the ``all`` extra -- it is LGPL-2.1+ where this package
  is BSD-3-Clause, and lands some 238 MB to obtain one module -- until :issue:`910`
  counted it among ``all``'s core addons, so ``all`` installs it (the ``all`` entry
  under *Project infrastructure*).
* the Mobility Header registry, completed (:pr:`383`, :pr:`437`): the :rfc:`5568`
  fast-handover messages and options, then every registered message data type,
  every registered option (with nested sub-option registries for the flow
  identification, access network identifier, quality-of-service and LMA-controlled MAG
  parameter families) and every CGA extension. The CGA Parameters option, the only
  option that can carry a CGA extension on the wire, was the last to come off the
  generic handler, which is what let the CGA extensions round-trip end to end.
* dispatch entries for dissectors that existed but were reachable from no registry
  (:pr:`436`): FTP-DATA on TCP 20, HTTP/1 on TCP 8080, HTTP on UDP 8080,
  :class:`.L2TPv2` on UDP 1701 and OSPF at
  :class:`~pcapkit.const.reg.transtype.TransType` 89.
  :class:`~pcapkit.protocols.link.vlan.VLAN` became an abstract base with
  :class:`.C_Tag` (802.1Q) and :class:`.S_Tag` (802.1ad) as concrete subclasses, so a
  Q-in-Q frame no longer collapses into one opaque
  :class:`~pcapkit.protocols.misc.raw.Raw`; :class:`~pcapkit.protocols.link.l2tp.L2TP`
  likewise became a base, with :class:`.L2TPv2` carrying the :rfc:`2661` implementation.
* :class:`~pcapkit.protocols.protocol.Protocol`/:class:`.ProtocolBase` gain a ``code=``
  class keyword for the next-layer dispatch registries (:attr:`.Link.__proto__`,
  :attr:`.Internet.__proto__`, :attr:`.TCP.__proto__`, :attr:`.UDP.__proto__`,
  :attr:`.SCTP.__proto__`, :attr:`.Frame.__proto__`, :attr:`.PCAPNG.__proto__`), the
  opt-in treatment :issue:`514` gave :class:`.Engine`, :class:`.Reassembly`,
  :class:`.TraceFlow` and :class:`.Dumper` above, extended to the one family that needed
  a registration key invented. Omitting ``code`` leaves a subclass unregistered, as
  before; the built-in tables are still filled by literal assignment in each layer
  module, so nothing the library ships moves. ``code`` accepts a bare enum member, whose
  *type* infers the destination (:class:`~pcapkit.const.reg.ethertype.EtherType` means
  :class:`.Link`, :class:`~pcapkit.const.reg.transtype.TransType` means
  :class:`.Internet`,
  :class:`~pcapkit.const.sctp.payload_protocol_identifier.PayloadProtocolIdentifier`
  means :class:`~pcapkit.protocols.transport.sctp.SCTP`, and
  :class:`~pcapkit.const.reg.linktype.LinkType` means *both*
  :class:`~pcapkit.protocols.misc.pcap.frame.Frame` **and**
  :class:`~pcapkit.protocols.misc.pcapng.PCAPNG`, mirroring ``register_linktype``), or a
  ``{destination: key}`` mapping, required for a raw ``int`` such as a port number,
  which cannot say which transport it belongs to. Either form may appear in an iterable,
  so one declaration can register a class into several registries (e.g. a
  :class:`~pcapkit.protocols.link.l2tp.L2TP` subclass reachable by IP protocol number
  and by a UDP port), and the mapping form is accepted even where inference would work.
  Inference refuses rather than guesses: an enum member whose type names no known
  destination raises :exc:`.RegistryError`, and an unrecognised class keyword raises
  :exc:`.UnsupportedCall`, matching the other registrar families. Backed by
  :func:`pcapkit.foundation.registry.protocols.register_protocol_code`, also callable
  directly for a class that declined at definition time. It was written up as the
  mechanism :issue:`548` needs; :issue:`548` turned out to need a missing class instead
  (115 is :rfc:`3931` L2TPv3 over IP, not :rfc:`2661`; see the corresponding **Fixed**
  entry below), so its worked example names ``L2TPv3`` (:pr:`570`).
* ``tests/protocols/test_dispatch_reachability_unit.py``, the coverage :issue:`548`
  asked for: every :class:`.ProtocolBase` descendant whose ``__index__`` returns an enum
  member must be reachable under that code in the registry its enum *type*
  designates, read from the same ``_CODE_DESTINATIONS`` table backing ``code=`` so
  the two cannot drift. It walks the classes rather than the registry entries, so it
  catches a class nothing registered, the shape in which
  :class:`~pcapkit.protocols.application.ospf.OSPF` once shipped (:issue:`548`).
* ``tests/protocols/transport/test_tcp_mptcp_join_flag_ordering_unit.py``, covering
  all three MP_JOIN layouts through the *public* constructor, the construct-pack-parse
  cycle for each, the stale-flags case that rules out a zero-valued default, the
  statement order, and controls for the parse path and the flag-independent options.
  The old cases bypassed the public path, so full coverage coexisted with a broken
  one. The stale ``tcp-mptcp/MP_JOIN`` entry is deleted from ``EXPECTED_FAILURES``
  (:issue:`587`).
* ``tests/protocols/test_option_generator_tcp_base_unit.py``, asserting that every
  ``TCP_BASE`` key is a parameter :meth:`.TCP.make` declares (derived from
  ``inspect.signature``) and that the built segment carries the stated header in both
  data model and packed octets (:issue:`602`).
* ILNP nonce sizing coverage in
  ``tests/protocols/internet/test_ipv6_extension_unit.py``, a test per protocol,
  asserting the declared length, the exact packed octets and the construct-pack-parse
  cycle over a spread of nonces, most with a bit length that is *not* a multiple of
  eight, where floor division and the ceiling disagree (:issue:`601`).
* ``SOLUTION`` parameter width coverage in
  ``tests/protocols/internet/test_hip_unit.py``: a spread of widths, each asserting
  the declared length, the reader's acceptance and the construct-pack-parse cycle,
  plus a 57-bit case pinning the 20-octet length :rfc:`5201#section-5.2.5` requires
  of HIPv1. Some widths are deliberately *not* multiples of eight, where the defective
  ``ceil(bits / 4)`` differs from the correct width (:issue:`608`).
* the BSD loopback layer for ``LINKTYPE_NULL`` and ``LINKTYPE_LOOP``, and dissection of
  ``LINKTYPE_RAW`` by the version nibble (:pr:`1594`).
* one home for each RFC- or format-fixed constant spelled out in more than one module
  -- the IPv4, IPv6, AH and TCP header lengths and offsets, ``IP_MAX_LENGTH``, and the
  PCAP and PCAP-NG framing constants -- in the module that owns the protocol
  (:issue:`1739`, :pr:`1752`).

Changed
~~~~~~~

* **a breaking change to** :class:`~pcapkit.protocols.application.ospf.OSPF`,
  :class:`.RARP` and :class:`.DRARP`: they move from :mod:`pcapkit.protocols.link` to
  :mod:`pcapkit.protocols.application`, with no deprecated re-export at the old path
  (:issue:`719`). Layer is decided by designed function, with the IETF as the single
  source of truth -- :rfc:`1812#section-7` places routing protocols in the application
  layer and :rfc:`1122#section-1.1.3` lists RARP there -- and the rule is recorded in
  ``docs/source/contributing/conventions/protocol-layer-placement.rst``.

  Import paths, before to after:

  * ``pcapkit.protocols.link.ospf`` to :mod:`pcapkit.protocols.application.ospf`
  * ``pcapkit.protocols.data.link.ospf`` to
    :mod:`pcapkit.protocols.data.application.ospf`
  * ``pcapkit.protocols.schema.link.ospf`` to
    :mod:`pcapkit.protocols.schema.application.ospf`
  * ``pcapkit.protocols.link.rarp`` to :mod:`pcapkit.protocols.application.rarp`

  ``from pcapkit import OSPF`` and ``from pcapkit.protocols import OSPF`` (likewise
  :class:`.RARP` and :class:`.DRARP`) are unaffected;
  ``from pcapkit.protocols.link import OSPF`` and the deep paths above break. RARP has
  no ``data`` or ``schema`` module of its own, as it reuses ARP's.

  ``layer`` changes from ``'Link'`` to ``'Application'`` for OSPF, RARP and DRARP.
  :class:`~pcapkit.protocols.application.ospf.OSPF` now takes :class:`.Application` as
  its only base, and :class:`.RARP` becomes ``class RARP(Application, ARP)`` -- layer
  base first, because :class:`~pcapkit.protocols.link.arp.ARP`'s chain reaches
  :class:`.Link`, which owns ``__layer__``. :class:`~pcapkit.protocols.link.arp.ARP` and
  :class:`.InARP` stay ``'Link'``. Dispatch keys are unchanged: OSPF is still reached
  from :attr:`.Internet.__proto__` at :attr:`.TransType.OSPFIGP` and RARP from
  :attr:`.Link.__proto__` by EtherType. Leaving :class:`.Link` repoints
  ``OSPF.__proto__`` at :attr:`.ProtocolBase.__proto__`, so OSPF no longer sees Link's
  EtherType entries -- which nothing used, since it is reached by protocol number, and a
  ``-1`` lookup falls back to :class:`~pcapkit.protocols.misc.raw.Raw` in either
  registry without inserting. ``register`` and ``_read_protos`` still resolve, on
  :class:`.ProtocolBase` rather than :class:`.Link`. :class:`.RARP` keeps Link's through
  :class:`~pcapkit.protocols.link.arp.ARP`.

  Layer-limited extraction: ``layer='link'`` no longer sets the termination flag on OSPF
  and ``layer='application'`` now does -- the same inversion applies to RARP -- but the
  extracted protochain is unchanged at every
  ``layer=`` value, including ``'internet'`` (``IPv4:OSPFIGP`` before and after, as IPv4
  ends the chain itself).
* renames with no compatibility alias left behind: PCAP-NG
  :class:`~pcapkit.protocols.schema.misc.pcapng.Option` subclasses spell the namespace
  class keyword ``ns=`` instead of ``namespace=`` (:issue:`439`).
* ``tests/protocols/transport/test_tcp_udp_unit.py`` now reaches the MP_JOIN
  dispatchers through :class:`TCP() <pcapkit.protocols.transport.tcp.TCP>` itself,
  instead of assigning a Python ``set`` to ``_flags`` on a bare ``TCP.__new__(TCP)``. A
  ``set`` answers the same membership tests, so every branch ran while the attribute had
  neither the type production assigns nor the ordering that governs when it exists --
  how :issue:`587` stayed invisible. Reverting :issue:`587`'s hoist, or restoring the
  ``cast('Enum_Flags', 0)`` seed, now fails the file. Test-only (:issue:`603`).
* building a protocol through its constructor with a keyword that names nothing now
  raises :exc:`.UnsupportedCall` instead of discarding it. **This is a behaviour change
  to a public API**: every ``make`` in the tree ends its signature with ``**kwargs`` and
  reads nothing out of it, so a misspelled keyword was accepted, dropped, and the field
  it named kept its default -- wrong octets, nothing said, as in :issue:`602`,
  :issue:`541` and :issue:`556`. The check sits in :meth:`.ProtocolBase.__init__` rather
  than ``make``, because ``__post_init__`` passes one ``**kwargs`` to the construction
  *and* to the parse of what it has just constructed, so a keyword declared only by
  ``read`` legitimately travels through ``make`` (:meth:`.HIP.read` declares
  ``extension``). The accepted set is the union of every keyword-taking parameter of
  ``make``, ``read``, ``pack``, ``unpack``, ``__post_init__`` and ``__init__`` across
  the MRO. Parsing is deliberately untouched: a protocol cannot know which keywords its
  parent passed on. A new ``__keywords__`` opts a class out: a set, for a keyword read
  out of ``**kwargs`` by name (:meth:`.ESP.read` with ``packet``); and ``None``, for a
  dispatcher whose real signature belongs to a class chosen at call time (only
  :meth:`HTTP.make <pcapkit.protocols.application.http.HTTP.make>`). The message names
  the near neighbour (``seq`` reports *did you mean 'seq_no'?*). ``from_data`` warns
  :exc:`.UnknownFieldWarning` rather than raising for a key its own ``_make_data``
  returned, which the caller cannot fix; a keyword passed to ``from_data`` itself
  raises, as for a direct construction (:pr:`1147`). The leftover copies of
  :issue:`602`'s misspelled TCP base, in ``examples/generators/dispatch.py`` and
  ``tests/protocols/transport/``, are fixed. Some ``_make_data`` keys that ``make`` does
  not declare are reported, not fixed: :meth:`.Frame._make_data` returns ``ts_src``
  where ``make`` declares ``ts_sec``, :meth:`.L2TPv2._make_data` returns ``prio`` where
  it declares ``priority``, and :meth:`.Header._make_data` returns a ``magic_number``
  that :meth:`.Header.make` does not take. A *direct* ``SomeProtocol.make(...)`` call is
  not checked and still discards silently (:issue:`617`).
* **a breaking change to** :class:`.Application`: it no longer forbids payload dispatch
  outright. It encodes "no further protocol layer above this one", which undissected
  trailer bytes are not, so ``_decode_next_layer`` and ``_import_next_layer`` accept
  the ``-1`` sentinel -- the rest of the packet, resolving to
  :class:`~pcapkit.protocols.misc.raw.Raw`, or to
  :class:`~pcapkit.protocols.misc.null.NoPayload` when nothing remains -- and
  ``__post_init__`` keeps a payload that ``read`` set instead of overwriting it with
  :class:`~pcapkit.protocols.misc.null.NoPayload`. A real protocol number (any ``proto``
  other than ``-1``) is still refused with :exc:`.UnsupportedCall`. A subclass that
  calls either method with ``-1`` changes from raising to succeeding; no subclass in the
  package does (:issue:`719`).
* the :class:`~pcapkit.protocols.protocol.Protocol` and :class:`.ProtocolMeta`
  docstrings. :class:`~pcapkit.protocols.protocol.Protocol` claimed to be the base of
  every protocol family, though nothing in the package subclasses it, and
  :class:`.ProtocolMeta` claimed to generate attributes its empty body does not.
  :class:`~pcapkit.protocols.protocol.Protocol` is now documented as the base for
  third-party protocols, and :class:`.ProtocolBase` as the one the families derive from
  (:issue:`1101`).
* **a breaking change to** ``OSPF_CrytographicAuthentication``: the misspelling is
  corrected to ``OSPF_CryptographicAuthentication``, and ``CrytographicAuthentication``
  in :mod:`pcapkit.protocols.schema.application.ospf` and
  :mod:`pcapkit.protocols.data.application.ospf` to ``CryptographicAuthentication``,
  with no alias left for the old spelling. Both OSPF names also move to the application
  group of ``schema.__all__`` and ``data.__all__``, after :issue:`719`'s move
  (:issue:`1090`).
* **a breaking change to** a declared length that runs past the data: it is refused
  with :exc:`.ProtocolError` rather than accepted and zero-filled on rebuild, so a
  malformed option looks different in ``info`` (:issue:`1325`, :pr:`1398`).
* dissection is bounded: a frame at 64 layers (:issue:`1610`, :pr:`1620`) and an IPv6
  extension-header chain at 32 headers (:issue:`1604`, :pr:`1608`). Both limits are
  ``PCAPKIT_FRAME_LAYER_LIMIT`` and ``PCAPKIT_EXTENSION_HEADER_LIMIT`` in
  :mod:`pcapkit.utilities.config` (:pr:`1743`). Rebuilding a
  frame cut at the chain bound warns once (:issue:`1619`, :pr:`1630`).
* **a breaking change to** IPv6 extension headers: an unrecognised or unparsable one
  is parsed generically, per :rfc:`6564`, rather than collapsing the packet to
  :class:`~pcapkit.protocols.misc.raw.Raw` (:issue:`891`, :pr:`904`).
  :class:`~pcapkit.protocols.internet.ipv6_ext.IPv6_Ext` does it, and is also the shared
  base of every extension header (:issue:`917`, :pr:`924`).
* **a breaking change to** ``pack()``: it no longer keeps the header it builds on the
  instance it is called on, which in 1.4.1 too left ``schema`` disagreeing with
  ``info``: ``UDP(srcport=1234).pack()`` reset ``schema.srcport`` to 0 while
  ``info.srcport`` kept 1234. Once an instance has been parsed or constructed,
  ``pack()`` builds on a shallow copy, so ``schema``, ``info`` and what ``make()``
  sets, such as TCP's ``connection``, stay as they were. The
  :class:`~pcapkit.protocols.misc.pcap.frame.Frame`,
  :class:`~pcapkit.protocols.misc.pcapng.PCAPNG` and ``HTTPv2`` overrides do the same,
  and re-packing a PCAP-NG block that carries an option allowed only once no longer
  raises. Code that relied on ``pack()`` to re-sync ``schema`` calls ``make()`` or
  constructs a new instance (:issue:`1769`, :pr:`1791`).
* **a breaking change to** the HOPOPT, IPv6-Opts and Mobility Header padding: two
  octets are one ``PadN`` with no data (``01 00``) rather than two ``Pad1`` options,
  as :rfc:`8200#section-4.2` and :rfc:`6275#section-6.2.2` ask. Only a freshly built
  header with exactly two octets of padding changes; a parsed one that carried two
  ``Pad1`` options still rebuilds byte for byte (:issue:`1793`, :pr:`1812`).
* **a breaking change to** :class:`.NTPTimestamp`: it and :class:`.PMIPv6Timestamp` are
  :class:`.Info` classes in :mod:`pcapkit.protocols.data.internet.mh` rather than
  tuples, and :class:`.NTPTimestamp` keeps no alias at its 1.4.x home in
  :mod:`pcapkit.protocols.internet.mh`. As Mappings they no longer index, unpack,
  compare or hash as a tuple does; ``.seconds`` and ``.fraction`` still work, and the
  dumpers write both as keys (:issue:`1886`, :pr:`1887`).
* **a breaking change to** rebuilding from ``to_dict()``: the payload is dispatched only
  from the ``__next_name__`` and ``__next_type__`` keys, and the IPv6 extension-header
  chain only from ``__exthdr__``, never from key order, which on PyPy follows an earlier
  instance's attribute layout and so picked the wrong layer. ``to_dict()``, iteration
  and ``len()`` carry the dunder keys a new :attr:`.Info.__included__` names, and
  :attr:`.Info.__excluded__` only keeps a key out of ``repr``, ``str`` and the dumps. A
  hand-written dict needs those keys, ``__short_read__`` among them, to rebuild, and a
  custom :class:`.Info` lists its own dunder keys in ``__included__`` (:issue:`2003`,
  :pr:`2014`).
* **a breaking change to** ``PCAPNG.context``: the block's section
  :class:`~pcapkit.foundation.engines.pcapng.Context`, which it returned from 1.0.0
  through 1.4.x, is :attr:`.PCAPNG.section_context`, with no alias, and ``context`` is
  the caller-supplied :class:`~pcapkit.corekit.context.ContextRegistry` every protocol
  inherits from :class:`.ProtocolBase`, on a Section Header Block too.
  :attr:`.PCAPNG.section_context` raises :exc:`.UnsupportedCall` where ``context`` did:
  on a block that holds no section, such as a Section Header Block the
  :class:`~pcapkit.foundation.engines.pcapng.PCAPNG` engine has not assigned the section
  it opens. Code reading ``block.context`` for the section reads
  ``block.section_context`` (:issue:`2172`, :pr:`2205`).
* **a breaking change to** HIP's ``REG_FAILED`` parameter: its first octet is the
  Failure Type, and it carries no lifetime (:rfc:`8003#section-4.5`), so
  :class:`pcapkit.protocols.data.internet.hip.RegFailedParameter` replaces ``lifetime``
  with ``failure_type``, a :class:`~pcapkit.const.hip.registration_failure.RegistrationFailure`,
  with no alias, and its ``reg_type`` holds
  :class:`~pcapkit.const.hip.registration.Registration` values rather than failure
  types. :meth:`.HIP._make_param_reg_failed` takes ``failure_type`` in place of
  ``lifetime``, and ``reg_failed`` takes registration types. The octets are unchanged
  (:issue:`2309`).
* **a breaking change to** the HTTP/2 ``RST_STREAM`` and ``GOAWAY`` builders: a frame
  constructed without ``error`` carries ``NO_ERROR`` (``0x0``), the code
  :rfc:`9113#section-7` gives a condition that is not the result of an error, rather
  than ``HTTP_1_1_REQUIRED`` (``0xd``), which asks the peer to use HTTP/1.1 instead.
  A ``make`` that omits ``error`` emits different octets; one that passes it is
  unchanged (:issue:`2311`).

Fixed
~~~~~

* next-layer, option, chunk, block and parameter dispatch all read ``defaultdict``
  registries, so a lookup miss inserted the key into class-level state shared by
  every later instance, after which a legitimate ``register_*`` call warned that
  the code was already registered. Every read now goes through a lookup that does
  not grow the table, and :attr:`.IPv4.__option__` and :attr:`.HIP.__parameter__` became
  inspectable class attributes rather than names assembled at call time
  (:pr:`426`, :pr:`428`, :issue:`429`, :pr:`434`). What breaks: a tuple-registered
  handler pair written to the documented ``OptionParser``/``OptionConstructor``
  signature now works where it could never be called, and a pair written with an
  explicit leading ``self`` -- the only shape that used to work -- now does not.
* the identical defect one layer up, in the schema layer's :attr:`.EnumSchema.registry`:
  ``Option.registry[code]`` for an unregistered ``code`` inserted the default
  schema under that code, so a single lookup made an unassigned TCP option number
  such as ``156`` read back as registered for the rest of the process.
  :attr:`.EnumSchema.__enum__` is now built (or, when a subclass seeds it manually, as
  ``PCAPNG.Option``'s namespaced mapping and ``TCP.MPTCP``'s plain one do) as a
  retention-safe mapping that still returns the registered default on a miss but
  stops recording it; ``.registry`` returns the same object as before, so nothing
  holding a reference is affected (:issue:`555`).
* on Python 3.10 and older, no :class:`.Schema` subclass got its own ``_abc_impl``: all
  fell through to ``collections.abc.Mapping``'s, so a single ``isinstance`` or
  ``issubclass`` answer poisoned every later question about that class for the
  rest of the process. A terminating PCAP-NG
  :class:`~pcapkit.protocols.schema.misc.pcapng.EndRecord` tested ``True`` as an
  :class:`~pcapkit.protocols.schema.misc.pcapng.IPv4Record` (:issue:`439`).
* construction, broken in several places at once: the generated typed ``__init__``
  was never installed, so ``__post_init__`` did not run and a schema built from a
  subset of its fields could not be packed -- ``UDP(srcport=53, dstport=5353)`` now
  packs (:pr:`430`); IPv6 and Mobility Header option padding was wrong, leaving
  construction wholly broken (:pr:`398`);
  :meth:`HTTP.make <pcapkit.protocols.application.http.HTTP.make>` called the versioned
  ``make`` unbound, so every real call raised ``TypeError`` (:issue:`452`, :pr:`462`);
  and :meth:`.IPv4._make_data` returned the fragment offset in octets where the wire
  wants 8-octet units, and read ``data.options`` on a packet that has none
  (:issue:`494`, :pr:`499`).
* a truncated or under-declared area no longer parses "successfully", and no
  longer wedges the process. The option and list loops could spin forever with no
  exception on a truncated area, reachable from untrusted input through HOPOPT,
  IPv6-Opts, MH, HIP and SCTP; each iteration must now advance the stream by at
  least one octet, and the error names the option, the offset and the octets
  remaining (:issue:`431`, :pr:`432`). Separately, wire-derived lengths in
  ``ipv6_opts``, CALIPSO, MPL, REG_INFO and HIP list callbacks
  underflowed below zero, which :class:`.ListField`'s own ``while length > 0`` turned
  into a silent empty list; they are floored and raise instead (:pr:`449`, :pr:`456`,
  :pr:`460`, :issue:`463`).
* field widths and units, each measured against the specification: HIP's
  ``TRANSPORT_FORMAT_LIST``, ``NAT_TRAVERSAL_MODE`` and ``ESP_TRANSFORM`` list
  entries are two octets, not one [:rfc:`7401`, :rfc:`5770`, :rfc:`7402`]
  (:issue:`463`, :issue:`472`); the MN-ID option sizes from its subtype, not from
  ``identifier``'s Python type (:issue:`448`, :pr:`464`, :issue:`467`); IPv6-Route's
  ``Hdr Ext Len`` is computed in 8-octet units on both sides [:rfc:`8200`]
  (:issue:`487`, :pr:`489`); and the Fast Binding Update and Acknowledgment
  Lifetimes are plain seconds [:rfc:`5568`], not :rfc:`6275`'s four-second units
  (:pr:`502`).
* the remaining call sites where a ``_make_*`` method converts an address itself,
  ahead of the schema, so the same ``bool``-as-``int`` mistake reached them,
  unguarded by the schema-layer fix above: ``ARP._make_proto_resolve``,
  :meth:`.IPv6_Route._make_data_type_rpl` (which also derived its RPL compression
  lengths from the laundered value, corrupting the address list), the ``dst``
  parameter of :meth:`.IPv6_Route.make`, and the latent ``OSPF._make_id_numbers``. Each
  now goes through ``parse_ip_address``, the helper :pr:`539` and :issue:`552`
  route their own sites through, completing the programme :pr:`481` and
  :issue:`508` started. Pinning ``version=6`` on the
  :class:`~pcapkit.protocols.internet.ipv6_route.IPv6_Route` sites is a further, smaller
  behaviour change: both converted a plain integer through the family-inferring
  ``ipaddress.ip_address``, so ``ip=[258]`` packed a 4-octet IPv4 address (``0.0.1.2``)
  inside an IPv6-only header; it now packs the 16-octet ``::102`` (:issue:`540`).
* PCAP and PCAP-NG output and parsing: ``bytes(frame)`` returned the *next*
  frame's octets, ``files=True`` wrote names like ``Frame 1..json``, and a PCAP-NG
  ``timestamp_epoch`` was shifted by the reading host's timezone (:pr:`403`); further
  parser defects (:issue:`341`--:issue:`347`, :pr:`371`) and, on the write path, more
  block-parsing ones (:pr:`388`); :class:`.BitField` packed every named
  bit as set (:issue:`359`, :pr:`374`); the extension-header walk failed to advance
  past the last IPv6 extension header (:issue:`348`, :pr:`373`); and IPv6 fragment
  offsets went unscaled, with reassembly keyed on the flow label -- optional, and
  routinely zero, so distinct datagrams collapsed together -- rather than on the
  fragment identification (:pr:`389`).
* :meth:`.TCP._make_mptcp_addaddr` could not build an ``ADD_ADDR`` option end to end:
  its ``kind=``/``length=`` arguments were rejected with :exc:`.UnknownFieldWarning` and
  dropped, and ``.pack()`` then raised ``KeyError: 'length'`` from ``port``'s own
  condition, ``pkt['length'] in (10, 22)``. The cause was one layer up:
  :class:`~pcapkit.protocols.schema.transport.tcp.MPTCP`, the base of every Multipath
  TCP subtype schema, declared ``kind`` and ``length`` only under
  ``typing.TYPE_CHECKING`` rather than as real fields, unlike
  :class:`~pcapkit.protocols.schema.transport.tcp.Option`. That dropped
  ``kind=``/``length=`` for every ``_make_mptcp_*`` constructor, so
  :class:`~pcapkit.protocols.schema.transport.tcp.MPTCP` now declares both for real
  (:issue:`541`). The missing fields broke parsing too: a subtype schema's leading field
  read the ``kind`` octet itself, an off-by-two in field alignment rather than a
  wire-format change (a correct sender's octets were always right). Spec-correct
  ``ADD_ADDR`` and ``MP_PRIO`` options failed with
  ``FieldError: TCP: [OptNo 30] 3 invalid IP version`` and ``KeyError: 'length'``; both
  parse now.
* dropped-keyword/wrong-cast defects flagged in review during this release and
  filed only as :issue:`556`: HIP's ``_make_param_encrypted`` passed ``cipher=`` to a
  schema with no such field, so an AES-cipher ``ENCRYPTED`` parameter built through
  ``make`` packed without its IV; and IPv6-Route's :meth:`.RPL.post_process`, which runs
  on every :meth:`.Schema.pack`, assumed ``self.addresses`` was still the concatenated
  ``bytes`` a parse leaves, and raised slicing the ``list[bytes]`` a ``make``-built
  multi-address header holds (:issue:`556`).
* further defects :issue:`541` exposed by letting construction reach code that had
  never run.
  :attr:`MPTCP.subtype <pcapkit.protocols.schema.transport.tcp.MPTCP.subtype>` was still
  ``typing.TYPE_CHECKING``-only, so ``TCP(options=[(Enum_Option.Multipath_TCP, ...)])``
  raised ``AttributeError: ... has no attribute 'subtype'`` for every subtype but
  ``MP_JOIN``: the convenience constructor reads the schema straight back through
  ``_read_mptcp_*`` with no byte round trip, so :meth:`._MPTCP.post_process`, the only
  code that set ``subtype``, never ran. Fixed on the construction path
  (:meth:`.TCP._make_mode_mp`) rather than by making ``subtype`` a real field too, the
  way ``kind``/``length`` became in :issue:`541`: ``subtype`` is already packed as 4
  bits of each subtype's own ``test`` bitfield, and a second field for the same bits
  would double-encode them or need a "derive, don't pack" field kind this library lacks
  (:issue:`566`). Separately, ``_make_mptcp_capable`` wrote
  ``length=20 if rkey is None else 32`` where :rfc:`8684` section 3.1 gives 12 and 20,
  and
  :attr:`MPTCPCapable.rkey <pcapkit.protocols.schema.transport.tcp.MPTCPCapable.rkey>`'s
  condition (``pkt['length'] != 32``) dropped the receiver's key for exactly the length
  the maker used for "key present": a key-absent MP_CAPABLE could not be built, and a
  key-present one lost its key on the wire. Both, and the guard in
  ``_read_mptcp_capable``, now agree on 12/20. **This changes MP_CAPABLE's packed
  output**: a 20-octet key-present option built or parsed under the old code becomes 12
  octets with no key, or 20 octets with the key present, depending on which the caller
  meant (:issue:`567`).
* TCP's MP_CAPABLE now parses and builds all five lengths of :rfc:`8684` section 3.1
  -- 4 (SYN, no key), 12, 20, 22 (adds the Data-Level Length) and 24 (adds the
  Checksum) -- where ``_read_mptcp_capable`` raised
  ``ProtocolError: TCP: [OptNo 30] invalid format`` for anything but 12 and 20. In the
  schema ``skey`` is now present only for ``length > 4`` and ``rkey`` for
  ``length > 12``, and the fields ``dl_len`` (16 bits, ``length > 20``) and ``checksum``
  (2 octets, ``length > 22``) are new. ``_make_mptcp_capable`` takes ``dl_len`` and
  ``checksum`` too, where it used to drop them silently through ``**kwargs``, and picks
  the length from how many of ``skey``, ``rkey``, ``dl_len`` and ``checksum`` are not
  ``None``. A field given without the one before it raises :exc:`.ProtocolError`. The
  data model :class:`~pcapkit.protocols.data.transport.tcp.MPTCPCapable` gains
  ``dl_len`` and ``checksum``, and ``skey`` becomes ``Optional[int]``: code that
  constructs it directly must now pass both new fields, and ``to_dict()`` carries the
  new keys (:issue:`1042`).
* IPv6-Route's RPL routing data was five octets wide at the front where :rfc:`6554`
  section 3 gives four, with further defects behind it. ``CmprI``, ``CmprE`` and
  ``Pad`` are each 4 bits sharing a 32-bit word with a 20-bit ``Reserved``, but the
  schema declared ``cmpr_i`` and ``cmpr_e`` as whole octets, so a constructed
  two-address header packed to 41 octets while its ``Hdr Ext Len`` of 5 declared 48.
  Correcting the width is a **wire-format change** and reshapes the schema:
  ``RPL(cmpr_i=..., cmpr_e=...)`` is now ``RPL(cmpr={'cmpr_i': ..., 'cmpr_e': ...})``,
  beside the existing ``pad={'pad_len': ...}``. Behind it, the reader's
  ``header.length % 16`` guard read ``Hdr Ext Len`` as an octet count and assumed
  16-octet addresses, which an SRH carries only when ``CmprI`` and ``CmprE`` are both
  0 -- the unit confusion :issue:`487` fixed for Source Route and Type 2, left by
  :pr:`489` for want of a working RPL round trip to validate against. It is replaced
  by section 4.2's address-count arithmetic,
  ``n = (((Hdr Ext Len * 8) - Pad - (16 - CmprE)) / (16 - CmprI)) + 1``, which the
  reader now requires to be non-negative and whole. :meth:`.RPL.post_process` subtracted
  ``pad_len`` a second time from a buffer whose length callback had already taken it
  off, losing one address per ``16 - CmprI`` octets of padding, and set ``ip`` only
  when it had parsed octets, so ``IPv6_Route(type=..., data={'ip': [...]})`` raised a
  bare ``AttributeError: 'RPL' object has no attribute 'ip'``. And
  ``_make_data_type_rpl`` computed ``Pad`` as ``8 - length % 8`` without the outer
  ``% 8``, so an aligned address vector got a full 8 octets of padding where section 3
  requires ``Pad`` to be 0 when ``CmprI`` and ``CmprE`` are both 0. The narrower
  ``cmpr_i`` also removes a latent divide-by-zero (a whole octet could hold 16, making
  ``16 - CmprI`` zero). ``ipv6-route-type/RPL_Source_Route_Header`` round-trips and
  its ``EXPECTED_FAILURES`` entry is deleted; none of this has been checked against a
  real RPL capture (:issue:`564`).
* :class:`.L2TPv2` parsed any version nibble, so an L2TPv3 datagram was reported as v2
  with a tunnel and session ID read out of v3's Control Connection ID. :rfc:`2661`
  §3.1 fixes ``Ver`` at 2 and reserves 1 for L2F, and :attr:`.L2TPv2.version` documented
  that any other value "is a different protocol reached through a different class",
  but nothing enforced it, so the hard-coded ``Literal[2]`` property and
  ``info.version`` answered 2 and 3 on the same octets. ``read`` now raises
  :exc:`.ProtocolError`, degrading the payload to
  :class:`~pcapkit.protocols.misc.raw.Raw` through the existing ``beholder`` path with
  the reason recorded. **This affects real captures**: :rfc:`3931` §4.1.2 puts L2TPv3 on
  port 1701 too, the port :attr:`.UDP.__proto__` binds, so
  ``Ethernet:IPv4:UDP:L2TPv2:Raw`` with invented field values becomes
  ``Ethernet:IPv4:UDP:Raw`` with the octets preserved.

  This resolves :issue:`548`, which reported :attr:`.TransType.L2TP` (115) as registered
  nowhere and proposed binding :class:`.L2TPv2` there. That binding is wrong rather than
  awkward: :rfc:`3931` §4.1.1 gives 115 to *L2TPv3 over IP*, whose session header
  carries **no version nibble at all**, so a v2 parser cannot detect that the
  datagram is not its own. 115 is a missing *class*, not a missing registration, and stays
  unbound until an ``L2TPv3`` class exists; no dissector was invented to fill it.
  The reasoning is recorded in :mod:`pcapkit.protocols.link.l2tp`, and
  ``register_protocol_code``'s worked example, which named :class:`.L2TPv2` at 115,
  names ``L2TPv3`` instead (:issue:`548`).
* building any ``MP_JOIN`` option raised
  ``AttributeError: 'TCP' object has no attribute '_flags'``. :meth:`.TCP.make`
  constructed the options *before* assigning the ``self._flags`` that the option makers
  read, and ``_make_mptcp_join`` branches on it to choose among the three layouts of
  :rfc:`8684` section 3.2 (figure 5, SYN, 12 octets; figure 6, SYN/ACK, 16; figure 7,
  ACK, 24). The parse path was never affected, since ``read`` assigns the flags first.
  Fixed by hoisting the flag resolution above the ``_make_tcp_options`` call, leaving
  only the data-offset computation, which needs the options' total length, after it.
  **Not** fixed by a zero default for ``_flags``, which would have been worse:
  :meth:`.Protocol.pack` is public and calls ``make``, so an instance that had parsed a
  segment had the attribute set and silently built the option for the segment it had
  *read*. A parsed MP_JOIN-SYN instance asked to pack an MP_JOIN-ACK segment emitted
  an ACK header carrying figure 5's 12-octet SYN option, with the caller's 20-octet
  HMAC replaced by an all-zero token and nonce, and nothing raised. Hoisting also made
  a branch reachable for the first time, an MP_JOIN on a segment with neither SYN
  nor ACK: the accumulator was seeded with ``cast('Enum_Flags', 0)``, and
  ``typing.cast`` being a runtime no-op, ``self._flags`` stayed a plain ``int`` and
  the first membership test raised ``TypeError`` rather than the documented
  :exc:`.ProtocolError`. It is now seeded with ``Enum_Flags(0)``, a real flagless member
  that equals ``0`` and ORs identically. The read path's seed is unchanged: a flagless
  MP_JOIN is rejected by ``mptcp_data_selector`` before ``_read_mptcp_join`` runs
  (:issue:`587`).
* the ILNP Nonce option builders in :class:`~pcapkit.protocols.internet.hopopt.HOPOPT`
  and :class:`~pcapkit.protocols.internet.ipv6_opts.IPv6_Opts` sized the option with
  ``math.ceil(nonce.bit_length() // 8)``, floor division dressed as a ceiling (``//``
  floors and ``math.ceil`` of an ``int`` is a no-op). The nonce is packed by a
  :class:`.NumberField` whose width *is* the declared ``len``, so an under-declared
  length silently truncated the nonce on the wire. Every nonce whose bit length was not
  a multiple of eight was affected, and **small values were the worst case rather than
  boundary values**: any nonce below 256 was declared as *zero* octets and dropped
  (``nonce=9`` packed to ``b'\x8b\x00'`` and parsed back as ``0``). Fixed to
  ``max(1, math.ceil(nonce.bit_length() / 8))``, the form used at the other sizing sites
  in ``hip.py`` and ``mh.py``. The one-octet floor is the ``mh.py`` convention and is
  load-bearing because ``nonce`` defaults to ``0``, whose bit length is ``0``: without
  it the default builds an option with no Nonce Value field at all, collapsing "the
  nonce is 0" into "there is no nonce" when :rfc:`6744` gives the option that field. The
  read path takes its width from the ``len`` octet on the wire and was never affected
  (:issue:`601`).
* ``httpv1``'s ``_RE_METHOD`` was unanchored and ``re.match`` anchors only at the
  start, so it prefix-matched, and the request-line reader passed the whole
  ``para1`` to :meth:`.Method.get` rather than the captured ``method`` group. So
  ``b'Get'`` matched on the single character ``G``, satisfied the guard that decides
  a start-line is a request, and handed the mixed-case token to a lookup that raised
  on it. Fixing either half alone still gives a wrong answer (normalising the lookup
  would parse ``b'Get'`` as ``GET`` off a one-character match; passing the group
  would parse it as a method named ``G``). The pattern is anchored at both ends and
  the captured group is looked up, so a non-method token is a malformed request line
  rather than a mis-parsed one. Method tokens are case-sensitive per
  :rfc:`9110#section-9.1`, so no ``re.I`` was added: ``GET`` parses, ``Get`` and
  ``get`` are rejected (:issue:`583`).
* ``_RE_STATUS`` in the same reader had the same unanchored prefix defect, found by
  auditing ``_RE_METHOD``'s siblings, and escaped as the wrong exception type. The
  pattern is only a guard (the value comes from ``int(para2)`` on the raw token), so a
  prefix match let a malformed status past the guard and out of ``int()`` uncaught,
  where ``_read_http_header`` documents :exc:`.ProtocolError`: ``200x`` raised
  ``ValueError: invalid literal for int()`` and ``2000`` raised
  ``ValueError: 2000 is not a valid StatusCode``; both are now :exc:`.ProtocolError`.
  :rfc:`9112#section-4` gives ``status-code = 3DIGIT``, exactly three, so the anchor
  is what the grammar said (the production lives in HTTP/1.1 because ``status-code``
  is part of its ``status-line``; :rfc:`9110#section-15` covers code semantics and the
  registry). ``_RE_VERSION`` was audited and is safe, since every call site reads
  the captured group (:issue:`583`).
* as a consequence of the above, the unhandled ``MemoryError`` in
  ``pcapkit/protocols/protocol.py``'s ``self._file.read()`` call on a truncated
  PCAP-NG capture. ``dhcp_little_endian.pcapng`` cut to 161, 641 or 1389 octets left a
  one-octet read of a little-endian 32-bit block length, which ``rjust()`` turned into
  ``0x78000000`` or ``0x84000000`` (1.88 to 2.06 GiB) and passed straight to

  ``from_data`` discarded both with an :exc:`.UnknownFieldWarning` and an L2TPv2
  priority bit was lost; they are now ``ts_sec`` and ``priority`` (:issue:`1097`). And
  :meth:`.ProtocolBase.from_data` took no keywords, so ``Frame.from_data`` and
  ``PCAPNG.from_data``, which need ``num``/``header`` and ``num``/``sct``/``ctx``, could
  not be called at all. Extra keywords now reach the construction, overriding
  ``_make_data``'s, under the construction-keyword check, so a typo raises
  :exc:`.UnsupportedCall` (:issue:`1126`). ``HTTP.from_data`` always raised
  ``invalid HTTP version: 0``, looking up a ``version`` key neither versioned data
  class has; it now dispatches on the data's class. HTTP/2's ``_make_data`` also
  returned the payload ``length``, which :class:`.ProtocolBase` takes as the parse
  length, so even a direct call failed as shorter than the 9-octet frame header;
  ``make`` now computes it, and every HTTP frame in the sample captures rebuilds byte
  for byte (:issue:`1154`).
* Quick-Start options did not round-trip. The IPv4, HOPOPT and IPv6-Opts readers took
  the function from ``schema.func``, which only a parsed schema carries, so a built
  option raised ``AttributeError``; HOPOPT and IPv6-Opts also sized the 8-octet option
  as 5, misreading the nonce with a ``packet length < 0`` warning (:issue:`1091`).
  TCP's Quick-Start Response reader read one octet past the option, and its maker
  produced a negative rate code below 40 kbps; such a rate now rounds down to zero,
  which :rfc:`4782` permits (:issue:`1119`).
* :class:`~pcapkit.protocols.link.ethernet.Ethernet`,
  :class:`~pcapkit.protocols.link.arp.ARP` and
  :class:`~pcapkit.protocols.misc.pcapng.PCAPNG` packed MAC addresses as ASCII hex text.
  ``Ethernet._make_mac_addr`` returned the separator-stripped hex string and
  ``BytesField(length=6)`` truncated it, so

* TCP's User Timeout maker wrote ``length=3`` where :rfc:`5482` and the reader require
  4, so every option it built failed to parse with :exc:`.ProtocolError`
  (:issue:`1120`).
* **a breaking change to** the HTTP/2 frame ``length``: it counted the 9-octet frame
  header, where :rfc:`9113` section 4.1 counts the payload alone, so ``make()`` wrote
  ``00000e`` for a 5-octet PRIORITY frame and ``read`` rejected RFC-conformant frames
  -- and, since ``_read_http_priority`` checked for 9, pcapkit's own PRIORITY frame.

  ACK), PING, WINDOW_UPDATE, DATA, PUSH_PROMISE and GOAWAY frames that Scapy's
  ``contrib.http2`` packs now parse and rebuild byte for byte (:issue:`1121`).
* **a breaking change to** :meth:`.ARP.make()`: ``hlen`` and ``plen`` are derived from
  the packed ``sha`` and ``spa`` when omitted, and an address that disagrees with its
  length field raises :exc:`.ProtocolError` where it used to be truncated silently --
  ``ARP(ptype=IPv6, spa='::1')`` wrote ``plen=4`` and four octets of the address. A
  non-IP ``str`` protocol address packs as hex octets rather than ASCII text, as
  hardware addresses do since :issue:`1134`, and non-hex input raises
  :exc:`.ProtocolError` (:issue:`1139`).
* HTTP/2 ``SETTINGS`` built each setting pair as a :class:`.SchemaField` with no length,

* :meth:`.HTTP._guess_version` took almost any binary for HTTP/2 on its fall-through:
  nine zero octets read as a DATA frame. The HTTP/2 trial now runs only on a header with
  a type :rfc:`9113` defines, no undefined flag, the reserved bit clear and a stream
  that type is sent on. Over 5,000 fuzzed zero-heavy buffers, HTTP/2 labels fell from
  566 to 101, every one a legal DATA header. Explicit ``version=2`` parsing is unchanged

* **a breaking change to** :meth:`.TCP.make()`'s options: ``_make_tcp_options`` dropped

  ``LinkType(dlt)`` cannot detect an unmapped DLT, because ``_missing_`` mints a
  placeholder rather than raising, so the generator snapshots every known
  :class:`~pcapkit.const.reg.linktype.LinkType` value first and calls ``LinkType(dlt)``
  only once a value is confirmed a member. The real-``tshark`` sweep is gated on a new
  ``HAS_WIRESHARK`` flag, registered in ``tests/_dependency_gates.py``'s
  ``NON_DISTRIBUTION_FLAGS`` next to ``HAS_PROC_FD``, for things pip cannot install. The
  sweep arithmetic is version-pinned (``editcap -T`` accepts 226 encapsulations on
  Wireshark 4.6.9, 224 on 4.2.2, CI's Ubuntu noble), so count assertions run only under
  exactly the measured version, with a separate ``VersionIndependentInvariantTests``
  class for what holds regardless. The only change to ``pcapkit/toolkit/pyshark.py``
  itself is the ``IPMB_LINUX`` entry becoming ``I2C_LINUX``, the canonical name
  :pr:`848` gave value 209 -- the same member either way (:pr:`853`).
* ``tcp_segment`` and its result type are public in :mod:`pcapkit.toolkit.pcap`
  (:issue:`1570`, :pr:`1579`).

Fixed
~~~~~

* the engine adapters, which were quietly wrong rather than loud. The ``dpkt``
  toolkit split TCP and IPv4 headers at their fixed struct size instead of their real
  length, so option octets overwrote payload in the sequence-indexed reassembly buffer;
  it also read an ``ipv6_frag.nh`` that ``dpkt`` does not have, and passed fragment
  offsets unscaled (:issue:`351`, :issue:`370`, :pr:`385`, :pr:`395`). ``scapy`` never
  loaded its layer registry, so that engine did not dissect at all (:pr:`409`), and its
  IPv4 fragment offset reached reassembly unscaled (:issue:`483`, :pr:`484`). The
  IPv6 adapters disagreed about whether the 8-octet Fragment header belongs to
  ``ihl``, ``header`` and ``tl``; per :rfc:`8200` section 4.5 it belongs to none, and
  they now agree (:issue:`415`, :pr:`424`).
* ``pypcapfile``'s ``IP.src``/``.dst`` are dotted-decimal ASCII text in a
  ``ctypes.c_char_p`` (per ``pypcapfile`` 0.12.0's ``ip.py``), not packed 4-byte values,
  so ``ipaddress.IPv4Address(ipv4.src)`` raised ``AddressValueError`` and
  ``ipv4_header()``'s ``struct.pack('...II', ipv4.src, ...)`` raised ``struct.error`` on
  every call. A single ``_parse_ipv4_address()`` chokepoint replaces the separate
  call sites, also accepting packed ``bytes`` or an ``int``. The same engine's
  ``IP.opt``/``.payload`` carry hex-ASCII rather than raw bytes once decoding stops
  short of the transport layer; a new ``_maybe_unhex()`` covers the sites
  that read them. Not ``breaking``: nothing on this path worked on 3.10/3.11, so correct
  behaviour cannot regress a working caller (:issue:`743`).
* ``pypcapfile``'s ``_read_a_packet(layers=0)`` hexlifies a whole frame into ASCII
  text and stops, but ``_decode()`` fed that into ``Ethernet(packet.packet, layers=1)``,
  whose ``__init__`` unpacks the header with ``struct.unpack``, so every field came out
  garbage without raising. Fixed with ``binascii.unhexlify(packet.packet)`` ahead of
  the decoder call, in preference to decoding eagerly at ``layers>0`` inside the lazy
  generator, which would lose ``_decode()``'s per-frame :exc:`.AttributeWarning`
  fallback. Link-layer dispatch resolves from the header's ``ll_type`` and is
  unaffected. Landed with :issue:`743`: standalone, this turns a non-crashing extraction
  into a crashing one, since :meth:`.Extractor.run()` catches only ``EOFError``,
  ``StopIteration`` and ``KeyboardInterrupt`` and the
  ``AddressValueError``/``struct.error`` :issue:`743` fixes escape until both land
  (:issue:`746`).
* **a breaking change to** pyshark link-type resolution in ``tcp_traceflow``: an
  unrecognised encapsulation or filter name now raises :exc:`.MissingKeyError` instead
  of substituting a plausible DLT. ``pcapkit/toolkit/pyshark.py`` resolved a frame's
  link type from ``packet.layers[0].layer_name``, a Wireshark display-filter name, with
  a blanket ``Enum_LinkType.get(name.upper())`` fallback. One filter name serves several
  encapsulations, so that fallback returned *wrong DLTs silently* (``null`` for a
  ``DLT_LOOP`` capture, ``101`` (``RAW``) for ``rawip6``). Re-keyed onto
  ``frame.encap_type``, which is distinct per encapsulation, and the fallback is gone.
  Both tables were measured rather than transcribed (Wireshark's source is not on the
  build host): each entry round-tripped through ``editcap -F pcap -T <encap>`` and read
  back with ``tshark``. ``ENCAP_TYPE_TO_LINKTYPE`` grows to cover every measured
  encapsulation whose DLT has a :class:`~pcapkit.const.reg.linktype.LinkType` member,
  and ``FILTER_NAME_TO_LINKTYPE`` grows from :pr:`838`'s hand-built entries to every
  root filter name, pseudo-protocol roots aside, that resolved to a single
  :class:`~pcapkit.const.reg.linktype.LinkType` member across the encapsulations this
  host's Wireshark can write. ``pcapkit/toolkit/pyshark.py`` reaches full coverage under
  new tests, which fail without the fix; live pyshark parsing stays unexercised,
  since ``pyshark.FileCapture`` does not run on Python 3.14 (:pr:`850`).
* ``pypcapfile``'s ``tcp_reassembly`` set ``last`` one past the segment.
  ``TCP_Packet.last`` is inclusive, and the other adapters set
  ``seqnum + len(payload) - 1``, as this one now does too (:issue:`1100`).
* scapy's ``packet2dict`` dumped nested packets as ``{}`` and mutated its input
  (:pr:`1287`); the dpkt reassembly adapters build their data from the record's own
  octets rather than dpkt's re-serialised bytes, and leave the packet alone
  (:issue:`1297`, :pr:`1335`).
* the TCP adapters: pyshark accepts tshark's ``True``/``False`` TCP flags
  (:issue:`1514`, :pr:`1527`); a TCP segment whose header the snapshot cut is traced
  and reassembled (:issue:`1518`, :pr:`1556`); dpkt reads SYN, FIN and RST whatever
  the NS bit (:issue:`1618`, :pr:`1621`); and the scapy adapters stop at the IP
  datagram's declared length (:issue:`1584`, :pr:`1589`).
* timestamps: dpkt and pypcapfile hand over the correctly rounded timestamp
  (:issue:`1668`, :pr:`1690`), and a copied :class:`.DecimalTimestamp` keeps
  ``orig_len`` under ``_pydecimal`` (:issue:`1647`, :pr:`1653`).
* the third-party engines are best effort: the code each adapter carried only to
  match the default engine is reverted (:pr:`1718`, :pr:`1721`, :pr:`1724`,
  :pr:`1727`, closing :issue:`1708` through :pr:`1743`). What each engine leaves out,
  such as TCP behind a tunnel or an IPv6 extension header, is documented rather
  than warned about. The pypcapfile engine keeps its warning, once per capture,
  that it leaves TCP over IPv6 out (:issue:`1513`, :pr:`1535`).

pcapkit.utilities
-----------------

Added
~~~~~

* :mod:`pcapkit.utilities.logging` as a real interface: ``get_logger()`` for per-module
  children, ``configure()`` to set level, handler, stream, format or propagation at
  runtime, ``reset()`` to return to library-neutral, and ``ensure_output()``. Each
  module that logs now does so under its own ``__name__``, so a consumer can silence
  :mod:`pcapkit.foundation.registry` while keeping :mod:`pcapkit.foundation.extraction`
  (:pr:`384`).
* :mod:`pcapkit.utilities.config`, one module for every tunable limit, each read once
  from a ``PCAPKIT_*`` environment variable: the frame-layer and extension-header
  limits, the pypcapfile engine's TCP-over-IPv6 warning limit, the dumpkit fallback,
  the charset-detection cache, the read chunk and the zero-padding guards. A
  bad value warns with :exc:`.ConfigWarning` and falls back to the default; ``-1`` lifts
  a limit. The homes these limits had in the prereleases keep no re-export
  (:issue:`1726`, :pr:`1743`).
* :mod:`pcapkit.utilities.datetime`, holding
  :func:`~pcapkit.utilities.datetime.fromtimestamp` and
  :func:`~pcapkit.utilities.datetime.totimestamp`, the timestamp conversions of the
  capture-timestamp entry under :mod:`pcapkit.protocols` (:pr:`2111`, :pr:`2136`).

Changed
~~~~~~~

* ``pcapkit`` no longer configures logging at import. It installs a ``NullHandler``
  and sets no level, so verbosity is inherited from the application instead of being
  seized by whichever library was imported second; the old stderr handler stays as the
  ``PCAPKIT_DEVMODE`` opt-in. Consequences: the previous behaviour is
  ``configure(logging.INFO, stream=sys.stderr)``; the registry and extractor ``info``
  calls became ``debug``, so those messages are invisible even at ``INFO``; and the
  handler is no longer ``logger.handlers[0]``. ``verbose=`` output stays on stdout and
  is not logging (:pr:`384`).
* each warning is reported once per channel, and ``pcapkit`` no longer inserts a
  ``simplefilter('ignore', ...)`` at the front of the process-global
  ``warnings.filters`` (:issue:`362`--:issue:`364`, :pr:`390`). The application's own
  filter therefore wins, which is the point and also the sharp edge: under
  ``-W error``, or pytest's ``filterwarnings = error``, a pcapkit warning that used to
  be suppressed will raise. Suppress them deliberately with
  ``warnings.filterwarnings('ignore', category=BaseWarning)``. ``quiet=True`` now
  means no record at any level and no longer sets ``sys.tracebacklimit``, and the
  ``pcapkit.utilities.warnings.DEVMODE`` re-export is gone; its home is
  :mod:`pcapkit.utilities.logging`.
* :mod:`pcapkit.utilities.compat` exports :mod:`pathlib`, :exc:`ModuleNotFoundError`,
  :class:`collections.abc.Collection` and :func:`functools.cached_property` as the
  standard library has them: their fallbacks for interpreters below 3.8 are removed
  with that floor (:issue:`2051`, :pr:`2053`).

Fixed
~~~~~

* further gaps the :issue:`514` keyword audit turned up, none covered by a test:
  :exc:`.StreamEOFError`'s docstring did not say that ``@prepare`` always raises it with
  ``quiet=True`` (the end-of-stream convention :exc:`.StructError` follows via its own
  ``eof=True``), so nothing pinned that silence against regression; and
  ``register_extractor_engine``'s real keyword, ``name``, was not itself under test,
  only its corrected docstring, so a rename could put the two out of step again
  (:pr:`577`).
* :class:`.hold_warnings` is in ``pcapkit.utilities.warnings.__all__`` (:issue:`1602`,
  :pr:`1603`).
* the default threading excepthook is the fallback before Python 3.10, which has no
  ``threading.__excepthook__`` (:issue:`1691`, :pr:`1701`).
* ``stacklevel()`` returns a level relative to its caller, as ``warnings.warn`` and
  ``logging`` count it, so a warning or a :exc:`.BaseError` log record names the
  caller's frame at any stack depth rather than a frame inside ``logging`` or
  pcapkit (:pr:`397`).
* re-executing :mod:`pcapkit.utilities.logging` under ``PCAPKIT_DEVMODE`` keeps one
  stderr handler, where each ``importlib.reload`` added another (:pr:`391`).
* a loud :exc:`.BaseError` no longer sets the process-global ``sys.tracebacklimit``,
  which truncated every later traceback, pcapkit's or not; lazily installed
  ``sys.excepthook`` and ``threading.excepthook`` keep its output terse instead
  (:pr:`983`).
* an import-time warning names the importing module on GraalPy too, where the
  importer's stack level counted the bootstrap frames GraalPy's ``warnings.warn`` skips,
  attributing the warning to ``<sys>:0`` (:issue:`1963`, :pr:`1996`).

pcapkit.vendor
--------------

Fixed
~~~~~

* ``re.sub`` sites under ``pcapkit/vendor/`` passed ``re.MULTILINE`` as the
  fourth *positional* argument, which is ``count``, not ``flags``: substitution capped
  at 8 matches, and a ``DeprecationWarning`` on Python 3.13+ (a future ``TypeError``).
  Found by an AST sweep rather than grep, since most put the flag on a continuation
  line. The flag moves to ``flags=`` at every site, in ``default.py``,
  ``hip/eddsa_curve.py``, ``http/frame.py``, ``http/method.py``,
  ``http/status_code.py``, ``ipv4/router_alert.py``, ``ipv6/option.py``,
  ``ipv6/router_alert.py``, ``ipv6/tagger_id.py``, ``reg/ethertype.py``,
  ``tcp/flags.py``, ``tcp/mp_tcp_option.py`` and ``tcp/option.py``. Behaviour
  preserving: the shared pattern (``r'\r*\n'``) has no MULTILINE-sensitive anchor, so
  no ``const/`` regeneration was needed (:issue:`796`).
* ``main`` was red (:issue:`866`) with ``RecursionError`` in
  ``tests/const/test_const_enum_lookup.py``, ``tests/const/test_const_enum_no_mint.py``
  and ``tests/protocols/misc/test_pcapng_unit.py``.
  ``pcapkit/vendor/pcapng/record_type.py`` and ``secrets_type.py`` rendered a
  ``_missing_`` body whose first line did not return:
  ``cls._unregistered_member(value, 'Unassigned')`` followed by ``return cls(value)``.
  That was harmless while the first line was ``extend_enum(...)``, which registers the
  member so ``cls(value)`` found it; :pr:`861` (above) replaced it with
  ``_unregistered_member``, which deliberately does not register, so ``cls(value)``
  missed and re-entered ``_missing_``. :pr:`861` fixed the *generated* modules but
  not these *crawlers*, so a live regeneration reintroduced the defect. Both crawlers
  now collapse to the single
  returning line the other registries use, and their const files are regenerated. A
  new guard at the crawler-emission layer requires a hard-coded ``_missing_`` body to
  end in a return and no emitted line to re-enter ``_missing_`` for the same value --
  deliberately narrower than "every emitted line must return", which
  :meth:`.Vendor.process`'s shape legitimately breaks. The guard sees only some
  crawlers; the rest are covered behaviourally. Closes :issue:`866` (:pr:`867`).
* ``python -m pcapkit.vendor <target>`` could not fail: ``run()`` swallowed
  every crawler exception as a filterable :exc:`.VendorRuntimeWarning` and
  ``main()`` always returned ``0``, so a broken crawler regenerating nothing
  looked like success to a human and to the cron job. Per the owner's ruling --
  discard only what a failing sub-vendor changed, and let a cron job warn about
  failed sub-vendors without failing as a whole -- the pieces below land.
  **Exit code** (``pcapkit/vendor/__main__.py``): ``run()`` returns whether its
  target succeeded; ``main()`` attempts every target and
  returns ``1`` if any raised, writing the failing target's qualified name and
  exception ``repr`` to stderr unconditionally via ``print()`` rather than the
  filterable warning. **Per-target snapshot and restore**: a new
  ``_snapshot_and_restore`` context manager backs up a target's const file with
  ``tempfile.mkstemp`` before it runs (resolving the destination through
  :meth:`.Vendor._dest_path`, now a ``classmethod`` in ``pcapkit/vendor/default.py``
  so it can be called before ``Vendor.__init__`` fetches, renders or writes),
  restores the backup via ``os.replace`` on any exception before re-raising,
  and discards it on success. A target whose destination cannot be resolved (a
  crawler outside the real tree) runs unprotected rather than failing the
  snapshot step, since ``Vendor.__init__`` hits the same resolution failure
  itself; a destination that does not exist yet is left alone. **Workflow**
  (``.github/workflows/cron-vendor.yml``): the "Update Vendor" step no longer
  aborts under ``bash -e`` when ``pcapkit-vendor`` exits non-zero. The exit
  code is captured around that one command, so targets that succeeded are still
  sorted by ``isort``, diffed, committed and pushed, while a "Warning" block naming the
  failed target(s) is appended to ``$GITHUB_STEP_SUMMARY``, a ``::warning::``
  annotation is emitted per failure, and the step's own exit code is always
  ``0``. A per-target ``git checkout -- <path>`` restore step was dropped: with
  snapshot/restore, a failed target's const file is never touched. Closes
  :issue:`872` (:pr:`873`).
* ``_snapshot_and_restore`` (:pr:`873`) carried an unpinned invariant and inaccurate
  prose and lint, none of it changing behaviour. **1.**
  ``except BaseException:`` in ``_snapshot_and_restore`` is pinned:
  a test asserts that a ``KeyboardInterrupt`` still restores the file and propagates.
  **2.** A false docstring clause is corrected: a crawler whose ``_dest_path`` is an
  instance-method-only override fails the *class* call ``_snapshot_and_restore``
  makes but not the *instance* call inside ``__init__``, so that target runs
  unprotected and **succeeds silently**. **3.** The
  ``# pylint: disable=no-else-raise`` pragma is **kept**, because it is needed: under
  the ``Makefile``'s flags, which CI runs, pylint reports R1720 on the ``else:``. A
  ``--disable=all --enable=no-else-raise`` run reports nothing there, since enabling
  the one message does not re-enable the check on a ``try``/``except``/``else`` the way
  ``--enable=R`` does, so such a run cannot show the pragma unneeded. The ``else:`` is
  deliberate: it makes the backup cleanup unreachable from the ``except``. Left out of
  scope: an untested ``os.close(fd)`` leak (harmless, since ``copy2`` reopens the path)
  and the semantically identical unindented form of the same ``else:``. Closes :issue:`875` (:pr:`876`).
* :class:`~pcapkit.const.pcapng.tls_key_label.TLSKeyLabel` tracked the Mozilla NSS
  key-log wiki, but ``draft-ietf-opsawg-pcapng-06`` section 4.7 now points at
  ``[I-D.ietf-tls-keylogfile]`` (draft-05), published as :rfc:`9850`, "The SSLKEYLOGFILE
  Format for TLS", whose section 4.2 creates the IANA "TLS SSLKEYLOGFILE Labels"
  registry. Against it, :class:`~pcapkit.const.pcapng.tls_key_label.TLSKeyLabel` was
  missing ``ECH_SECRET`` and ``ECH_CONFIG`` (:rfc:`9850` sections 2.3 and 4.2), so
  ``TLSKeyLabel('ECH_SECRET')`` raised ``ValueError`` on a legitimate Decryption Secrets
  Block; both are added, ``ECH_SECRET`` keeping the file's ``# nosec B105`` bandit
  convention for ``*_SECRET`` members. ``RSA`` has no row in :rfc:`9850`'s registry (it
  is an NSS-only label the NSS wiki records as removed in NSS 3.34) and is kept, since
  removing a public member is breaking, with a docstring comment marking it the
  historical exception. ``pcapkit/vendor/pcapng/secrets_type.py``'s stale
  ``# NSS Key Log Format`` comment is repointed at RFC 9850, and
  :class:`~pcapkit.const.pcapng.tls_key_label.TLSKeyLabel`'s docstring cites it. A new
  test pins the member set against RFC 9850 plus the ``RSA`` exception. Closes
  :issue:`882` (:pr:`883`).
* both spellings of an IANA citation render as ``:rfc:`` roles in the generated
  :mod:`pcapkit.const` docstrings (:issue:`1664`, :pr:`1673`).
* ``MAX_RETRY`` and ``CI_MODE`` stay in :mod:`pcapkit.vendor.default`, read from
  ``PCAPKIT_VENDOR_RETRY`` and ``PCAPKIT_CI_MODE``; a bad value warns with
  :exc:`.ConfigWarning` and falls back, where 1.4.x crashed on a non-integer and read

* the IPX socket crawler no longer scrapes Wikipedia, whose page dropped the socket

* the crawlers send a descriptive ``User-Agent`` built from the package metadata,

* :mod:`pcapkit.vendor` and :mod:`pcapkit.vendor.mh` list ``MH_HandoverInitiateStatus``

  ``pcapkit-vendor`` run reaches its crawler (:pr:`531`).
* with no terminal on stdin, a failed fetch re-raises rather than waiting for an

* each crawler derives its ``const/`` path from the :mod:`pcapkit.vendor` root, so a

* the generated const comments render as written: a URL reference followed by another

* without the ``vendor`` extra, ``pcapkit-vendor`` and ``python -m pcapkit.vendor``
  exit 1 with one line naming the missing packages and ``pypcapkit[vendor]``, where

Changed
~~~~~~~

* **a breaking change to** ``requires-python``: it is ``>=3.8``, so pip refuses an
  older interpreter at install, as "requires a different Python". The sources use 3.8
  syntax, and the ``bpc-*`` backport tools that converted it for 3.6 and 3.7 are no
  longer maintained, so the conversion goes: the ``bpc-*`` requirements,
  ``refactor()`` and the ``setup.py`` build commands that ran it. The 3.7 KTLO (*keep
  the lights on*) legs go with it, and ``coverage-comment.yml`` lists no install
  failure as by design any more, which closes :issue:`2040` (:issue:`2051`,
  :pr:`2053`).
* ``setup.py`` is gone, and ``pyproject.toml`` is the only build configuration. With
  the 3.8 floor it was a Python 2 guard and a bare ``setup()``: the wheel's files are
  identical without it, ``pip install -e .`` goes through PEP 660, pip still refuses
  3.7 as "requires a different Python", and on 2.7 it fails on the ``setuptools``
  build requirement before it would reach ``setup.py``.
  ``examples/benchmark/Dockerfile`` stops copying it, and a test fails should
  ``setup.py`` return or a ``COPY`` there name a file the repository does not track.
  Dependabot now fetches ``pyproject.toml`` in ``setup.py``'s place and passes it
  through unstubbed; the static ``readme`` stays, as it does not depend on what a stub
  would supply (:issue:`2061`, :pr:`2066`).
* renames with no compatibility alias left behind: ``examples/sample`` and
  ``examples/samples`` -- one letter apart, holding different things -- are now
  ``examples/captures`` and ``examples/generators``.
* the README is a landing page now, and Markdown rather than reStructuredText.
  ``README.rst`` became a much shorter ``README.md``, keeping what a reader arriving
  from PyPI or a search result needs (what the library is, why it exists rather than
  Scapy or DPKT, how to install it, a worked example, where the documentation lives).
  **Module Structure**, **Engine Comparison**, **Engine support by Python version**,
  **Test Environment**, **Test Results** and **Installation Notes** were already
  duplicated in fuller form in ``docs/source/index.rst``, so they are linked rather than
  restated; the blocks that existed nowhere else moved: **Testing** is now
  ``docs/source/contributing/testing.rst``, and the ``pipenv`` and ``make setup`` block
  joined the Installation section of ``docs/source/index.rst``. Requested by the
  project owner, and a deliberate exception to the reStructuredText convention, for the
  README only, since its renderers are GitHub and PyPI rather than Sphinx.
  ``setup.py`` read ``README.md`` and declared ``text/markdown`` (``pyproject.toml``
  declares the ``readme`` statically since :pr:`1994`), and ``MANIFEST.in``
  gains ``include README.md``, which is belt-and-braces rather than load-bearing:
  setuptools' ``sdist`` ships a ``README.md`` regardless. Of the ``include`` lines
  only ``CHANGELOG.md`` is load-bearing, measured in the :pr:`631` entry below.
  ``examples/benchmark/Dockerfile`` copies ``README.md``, while the ``README.md``
  that ``examples/benchmark/benchmark.py`` names is the benchmark suite's own
  (:pr:`619`).
* ``CODE_OF_CONDUCT.md`` moves from Contributor Covenant 1.4 to 3.0, at the
  owner's request. The text is the canonical 3.0 Markdown fetched from
  https://www.contributor-covenant.org/version/3/0/code_of_conduct/code_of_conduct.md
  rather than transcribed. Some things needed deciding. 3.0's ``[NOTE``
  placeholders are filled or removed: the reporting channel names
  ``jarryshaw@icloud.com`` (the contact 1.4 carried and ``SECURITY.md`` uses as email
  fallback) plus GitHub's report-abuse form for a report about the maintainer, which a
  single-maintainer project cannot otherwise cover; the enforcement placeholder is an
  instruction to the adopter and is removed. 3.0's plural "Community Moderators" become
  the singular maintainer, this repository having no moderators.
  The enforcement ladder (Warning, Temporarily Limited Activities, Temporary
  Suspension, Permanent Ban) is a suggestion and is **kept**, each rung mapping to a
  lever one person holds on GitHub. 3.0 is CC BY-SA 4.0 where 1.4 carried no licence
  notice, so the attribution names version 3.0, links the permanent ``version/3/0/``
  URL, carries the CC BY-SA 4.0 notice, indicates changes were made as BY requires, and
  says the share-alike term covers this document only (the code remains BSD-3-Clause,
  ``LICENSE`` untouched). The ladder renders as nested list items, checked against
  GitHub's Markdown API; :pr:`613` had to repair the 1.4 file when a stray list marker
  collapsed it into one nested item (:pr:`624`).
* reconciled which private (``_xxx``) attributes and methods the Sphinx build
  documents, replacing an ad hoc mix with one rule: document the contract, hide the
  recipe. A member every subclass must implement, or whose shape a caller depends on,
  stays documented despite its underscore; a private helper that only keeps one method
  short does not. Module-level directives for pure implementation detail
  (``esp._resolve``, ``esp._CRYPTO``, ``ngap._convert``, ``ngap._revert``,
  ``ngap._PYCRATE``, ``ngap._PDU_LOCK``, ``pypcapfile._NamedStream``) were dropped,
  while ``autoattribute`` directives were added for class-private state that *is*
  contract, among them :attr:`.Extractor._flag_f`, the :class:`.PyPCAP` and
  :class:`.PCAP_CT` engines' ``_backend`` (the only third-party engines with one),
  :class:`.TraceFlow`'s internal fields, :class:`.FieldBase`/:class:`.Field` internals,
  the built-in :class:`.PCAP` engine's ``_gbhdr``, ``_vinfo``, ``_nnsec`` and ``_dlink``
  (shared with :class:`.PyPCAP`, :class:`.PCAP_CT` and :class:`.PyPCAPFile`) and
  :class:`~pcapkit.foundation.engines.pcapng.PCAPNG`'s ``_ctx``/``_ctx_list``. The
  runtime definitions of ``_missing_`` (under :mod:`pcapkit.const`, and inline in
  :mod:`pcapkit.protocols`) gained one write-up in place of a directive per class, a new
  "Unrecognised Values" section in ``docs/source/pcapkit/const/index.rst``
  cross-referenced from ``registry.rst`` (``conf.py`` already excludes ``_missing_``
  from every ``autoclass``). ``CONTRIBUTING.md`` gained the rule as a named section. The
  new Sphinx warning, a bare ``Type`` newly rendered by :attr:`.TraceFlow._foutio`'s
  directive, is :issue:`709`. No line under ``pcapkit/`` changed (:issue:`684`).
* ``examples/captures/out.json``, ``out.plist``, ``out.txt`` and ``pcapng.txt`` are no
  longer tracked in git; they are build output, not fixtures, and a tracked rendering
  with no reader goes stale silently. ``pcapng.txt`` is exactly that: it still recorded
  ``packet -> NIL`` for the Enhanced Packet Blocks of ``dhcp.pcapng`` long after
  :pr:`683` gave those blocks their captured octets back. Rather than regenerate it
  again and leave the drift free to recur, these files are removed from the index and
  folded into ``examples/captures/``'s blanket ``.gitignore`` rule; the genuine inputs
  ``in.pcap`` and ``dhcp.pcapng`` stay tracked. ``examples/legacy_smoke/Makefile`` and
  its ``README.md`` now describe regenerating these reports via ``make fixtures``, and
  ``tests/project/test_capture_tracking.py`` pins the invariant (:issue:`685`).
* ``tests/project/test_isort_clean.py`` gated on ``isort`` with a
  ``try``/``except ImportError`` inside ``setUpClass``, which
  ``tests/_dependency_gates.py`` cannot see (``_gates_of()`` walks a decorator list,
  never a function body), and ``isort`` was in no ``pyproject.toml`` extra, so the
  file reported ``OK (skipped=1)`` on every CI leg and the dependency-gate guard could
  not tell. It now gates on a module-level ``HAS_ISORT`` and a class-level
  ``@unittest.skipUnless`` so ``gated_scopes()`` counts it, ``MODULE_PROVIDERS`` maps
  ``isort``, and ``isort`` joins the ``test`` extra rather than being excluded
  (``lint.yml`` installs none, so unlike ``mypy`` there is no existing check to defer
  to). No workflow changed, every pytest job already building on ``.[test]``;
  ``gated_scopes()`` gains this scope and ``dependency_gate_gaps()`` is unchanged.
  Another instance of the hazard :issue:`745` exists to stop (:issue:`766`).
* ``tests/vendor/test_vendor_reg_apptype_generator_unit.py`` gated on ``mypy`` with no
  ``MODULE_PROVIDERS`` entry, so ``_top_level_providers()`` died on a bare
  ``KeyError: 'mypy'`` once the gate became visible -- a further instance of the
  hazard :issue:`745` exists to stop, like :issue:`766` above.
  ``MODULE_PROVIDERS['mypy'] = ('mypy',)`` fixes the lookup, and the bare
  ``MODULE_PROVIDERS[...]`` subscripts route through that function, which raises an
  ``AssertionError`` naming the module, key and table on any future gap. ``mypy`` is
  deliberately not added to a ``pyproject.toml`` extra: no extra carries it, it is a
  ``Pipfile`` dev-dependency that ``lint.yml`` installs and already runs
  whole-package, and ``lint.yml`` runs no pytest job for ``pytest_jobs()`` to see, so
  the fix is a ``DEPENDENCY_GATE_EXCLUSIONS['HAS_MYPY']`` entry on ``test``,
  ``engine-tests`` and ``gate``. ``dependency_gate_gaps()`` gains
  the new ``(flag, job)`` pairs, each expected (:issue:`779`).
* ``engine='pyshark'`` had no CI job driving it through a real ``tshark``-parsed
  capture. ``pypcap-parity`` installs ``pyshark`` but its ``apt-get install`` named no
  ``tshark`` package, so :meth:`.PyShark.unsupported_reason()` declined the engine, the
  extractor fell back to the built-in parser, and the only real-extraction assertion,
  ``assertGreater(extractor.length, 0)``, passed against the fallback's output: a vacuous
  pass invisible in every skip count. ``pypcap-parity`` now installs ``tshark`` with the
  debconf pre-seed ``engine-tests`` carries, and the test proves which engine ran (no
  :exc:`.EngineWarning`, ``extractor._exnam == 'pyshark'``, a :class:`.PyShark`
  instance), as the PyPCAP parity test does. Only
  ``tests/integration/test_engine_runtime.py`` and ``test_engine_parity.py`` change; the
  length assertion is kept (:pr:`846`).
* ``engine-tests`` ran a Python-version leg per interpreter regardless of which
  engines that interpreter could install, so ``pyproject.toml``'s
  ``PyPCAPFile = ["pypcapfile; python_version < '3.12'"]`` marker resolved to
  *nothing* on 3.12--3.14, yet the ``Engines Python 3.12/3.13/3.14`` legs passed and,
  once required, gated merges while exercising an engine that was never installed.
  Rebuilt as a Python x engine matrix in which every cell has an expected outcome:
  ``supported`` cells install through the real extra and must pass; ``unsupported``
  cells (``PyPCAPFile`` on 3.12--3.15, ``PyShark`` on 3.14/3.15) install by raw
  ``pip install`` to bypass the marker and assert the engine's own
  ``PYTHON_CEILING`` decline; and ``not-installable`` cells (``PyPCAP`` on
  3.12--3.15) log a genuine C-extension build failure and skip the test step. The
  install step never passes silently in either direction. Python 3.15 is
  ``continue-on-error`` throughout. Job names
  change shape (``Engines Python X`` becomes ``Engines Python X (engine)``), so the
  branch-protection ruleset's required-check list was updated in the same window, lest
  a required check that stopped existing block every merge (:pr:`849`).
* Ruleset ``23497679``'s ``required_status_checks`` names exact check contexts, and
  GitHub rulesets match literally with no wildcard, so the list needs hand-editing on
  every matrix change. The old ``Engines Python <version>`` names in it are dead since
  :pr:`849`; the ``Compat Python 3.10``-``3.14`` names stay live, emitted by
  ``python-compatibility.yml``, and are untouched. Adds a job,
  ``required-checks`` (context ``Required checks passed``), depending on
  ``[test, integration, engine-tests, pypcap-parity]`` with
  ``if: always() && inputs.gate-only != true`` and an explicit per-dependency check
  that fails loudly, naming the job, on anything but ``success``: a bare ``needs:``
  list would leave it *skipped* rather than failed when a dependency failed, and
  GitHub's docs list a skipped required check as passing. That context is meant to
  replace the ruleset's ``test``, ``integration``, ``Engines`` and ``pypcap-parity``
  entries once the ruleset is updated separately, as a repository setting outside the
  change; the ``Compat`` names are excluded from the replacement. Only
  ``.github/workflows/unit-tests.yml`` changes; no library or test code (:pr:`856`).
* ``engine-tests`` runs one job per engine, ``Engines (<engine>)``, each looping over
  its interpreters in fresh virtual environments, in place of :pr:`849`'s job per
  Python and engine. ``required-checks`` also needs ``changes`` and ``project-tests``:
  ``project-tests`` must pass on every diff, and a skipped leg passes only where
  ``changes`` classifies the diff as docs-only (:issue:`1052`, :pr:`1055`), which may
  skip ``test``, ``integration``, ``engine-tests`` and ``pypcap-parity``, or as
  test-only, which may skip ``engine-tests`` and ``pypcap-parity`` (:issue:`2243`,
  :pr:`2244`).
* the prose the post-:issue:`719` defect wave added or touched, checked against the
  code; no code changes. :attr:`.MesgIDOption.seconds` in the Mobility Header schema
  said seconds since 1970 where it holds an :rfc:`1305` NTP count from 1900;
  :meth:`.HTTP._guess_version` comments predated the HTTP/2 gate; and the
  ``_parse_next_layer`` note miscounted the captured octets.
  :meth:`.Extractor._open_output` now says only the PCAP engine passes header fields,
  :meth:`.Extractor.run` and the PCAP-NG engine's ``run`` list the :exc:`.FormatError`
  for PCAP output from a PCAP-NG input, and the extraction and engine pages document the
  PCAP-output path (:pr:`1179`, :pr:`1180`, :pr:`1186`, :issue:`1103`).
* **a breaking change to** the ``all`` extra: it carries the core addons only --

* the ``Scapy`` and ``dev`` extras require ``scapy>=2.6.0`` (:issue:`1572`,

* the READMEs of ``examples/benchmark`` and ``examples/legacy_smoke`` are Markdown,

Fixed
~~~~~

* places where a documentation page contradicted the code (:pr:`413`),
  ambiguous cross-references and autodoc signature failures (:pr:`416`), and
  :class:`.Extractor`'s documented exception plus phantom or stale ``Args:`` labels
  (:pr:`501`).
* both halves of what the ``Changelog drift`` gate told an author, in
  ``util/changelog_md.py``. ``ResidualMarkupError`` named the entry file but numbered
  its lines against the *converted* body, which rule 6 joins onto one line per block,
  so a reported number could not reach most of the file, and roles on separate source
  lines were all reported as one line. The
  conversion now carries a source map, so every complaint cites a line of the file the
  message names, one per construct, in the entry's order (:issue:`588`). Rule 2 accepted
  only the bare-number spelling of Sphinx's ``:rfc:`` role, so :rfc:`6554#section-3`
  fell past it and was reported as a role the rules do not cover; both spellings now
  convert, the anchor carried into the link target and the link text taken from
  Sphinx's own (:issue:`592`). Regenerating ``CHANGELOG.md`` is byte-identical over
  every committed entry: the fix changes what the gate *says*, not what it emits.
* ``examples/generators/options.py``'s ``TCP_BASE`` spelled header fields with
  names :meth:`.TCP.make` does not declare, so every option fixture in
  ``examples/captures/options-tcp.pcap`` was built from values the generator had not
  asked for. ``make`` ends in ``**kwargs`` and reads nothing out of it, so an
  undeclared keyword is accepted and discarded with no warning. ``'seq': 1`` was
  ``seq_no``, so every captured frame carried sequence number 0; ``'urgent_pointer'``
  was ``urgent`` (requested value and default both 0); and ``'ack_flag': False`` was
  ``ack`` while ``'ack': 0`` bound to ``ack`` itself, the acknowledgement *flag*
  rather than the number (``ack_no``), so that pair was wrong both ways. Each is renamed
  to the parameter ``make`` declares, keeping the intended values.
  ``TCP(**TCP_BASE).info.seq`` was 0 against a declared 1 and is now 1, and
  ``options-tcp.pcap`` changes only in the low octet of each frame's sequence number,
  with no case status or ``EXPECTED_FAILURES`` entry moving. The
  module's other base mappings were audited: the rest pass nothing their ``make`` does
  not declare, and HIP's ``extension`` is declared by :meth:`.HIP.read`, this library's
  documented way of forwarding a read-path keyword, not another instance
  (:issue:`602`).
* ``util/bump_version.py`` left ``CITATION.cff`` naming the previous release. Nothing
  else maintains that file, so every bump since :pr:`615` would have stranded the
  ``version`` and ``date-released`` that GitHub's "Cite this repository" button,
  citation managers, Zenodo and dependency inventories read. Both fields now move with
  ``__version__``, together, since the file's header says both describe the newest
  *published* release and moving only one would assert that 1.5.0b5 was released on the
  day 1.5.0b4 was. The date is UTC, because seven of the thirty most recent bumps were
  made late evening US-Eastern, where a local date is a day behind the publish; the bump
  triggers ``create-release.yml``, the median gap to the PyPI upload is three minutes,
  and the UTC dates agree 30 times of 30. The rewrite is line-oriented, so the comment
  header, key ordering and each field's quoting survive (``cff-version`` and a
  ``references`` entry's own ``version`` are anchored out at column zero), and the
  result is checked with ``cffconvert --validate``. An absent file is reported on stderr
  and skipped rather than failing the vendor cron before its ``git commit``, which would
  discard a whole registry crawl for a documentation file; a file with no ``version``
  field raises before anything is written, since reporting success while rewriting
  nothing is the staleness being fixed. The script gains a ``main()`` guard (it ran the
  whole bump at import, hence no testable surface), and the ``import pcapkit``
  fallback in its version reader, which returned ``"1.5.0b4'\n"`` (closing quote and
  newline, which ``packaging`` rejects), is fixed; it never worked and went unnoticed
  because the only caller installs the package first. A new gate asserts the committed
  file still names the packaged version, covering hand-made version changes that never
  run this script (:pr:`625`).
* ``LICENSE``'s copyright notice began the term at 2018, a year after the work it
  covers. The repository's first commit is ``c57f7d0b7``, dated 2017-11-07, so the
  notice understated the term and contradicted ``docs/source/conf.py``, whose Sphinx
  footer is ``f'2017-{datetime.date.today().year}, Jarry Shaw'``. The wrong start year
  survived every maintenance pass because each looked only at the other end of the
  range: ``bc836cfa2`` (2020-05-31) introduced ``2018-2020`` when the BSD-3-Clause
  text replaced MPL 2.0, and hand bumps to ``2018-2022``, ``2018-2023`` and
  ``2018-2026`` (:pr:`615`) each copied ``2018`` forward. 2017 is **restored** rather
  than newly asserted: the initial MIT ``LICENSE`` read
  ``Copyright (c) 2017 Jarry Shaw``, and the GPL v3 era carried
  ``Copyright (C) 2017 Jarry Shaw`` in its appendix; it was lost on 2018-12-08, when
  ``4f3e00d5f`` relicensed to Apache 2.0 under ``Copyright 2018 Jarry Shaw`` and
  ``1c69341dc`` replaced that with MPL 2.0 text with no author notice. The end year is
  **dropped** rather than automated: the notice ships inside the sdist and wheel, so
  its text is fixed at build time in every copy already downloaded and cannot be
  computed like the docs footer; copyright subsists from creation whether or not a
  notice names the current year; and BSD-3-Clause's canonical form is a singular
  ``Copyright (c) <year> <owner>``. A range was six years of hand maintenance buying
  nothing, and automation was considered and rejected, since automating a value that
  need not be current is worse than not carrying it. ``conf.py`` is untouched (a
  self-maintaining footer showing a range is conventional and correct). The
  ``BSD 3-Clause License`` title line and the comma in the notice follow
  choosealicense.com's template, whose first line is that title and whose notice reads
  ``Copyright (c) [year], [fullname]``. The licence body is unaltered: the change is confined to the copyright line, and the ``DAMAGE.``
  that :pr:`615` repaired from ``DAMAGE.s`` is still clean (:pr:`630`).
* ``CITATION.cff`` shipped in no source distribution. ``MANIFEST.in`` had an ``include``
  each for ``README.md``, ``LICENSE`` and ``CHANGELOG.md`` but none for the citation
  file, and its ``global-include`` patterns (``*.rst``, ``*.py``) could not match a
  ``.cff``. Removing those ``include`` lines and rebuilding shows ``README.md`` and
  ``LICENSE`` shipping anyway (setuptools adds the latter from ``license_files``,
  recorded as ``License-File: LICENSE`` in ``PKG-INFO``) while ``CHANGELOG.md``
  vanishes, so only ``CHANGELOG.md`` is load-bearing, and a citation file, which no
  packaging default covers, is in the same position. The gap is invisible from the web
  UI, because GitHub renders "Cite this repository" from the repository; citation
  managers, Zenodo and dependency inventories read the published artifact, the surface
  that was missing it. :pr:`615` flagged the omission and :pr:`619` did not address it.
  It matters because :pr:`625` taught ``util/bump_version.py`` to keep the file's
  ``version`` and ``date-released`` in step, and a release exercising that path would
  publish an sdist omitting the artefact under test. It also lets
  ``RepositoryCitationTests`` in ``tests/project/test_bump_version.py`` (the gate
  :pr:`625` added for hand-authored bumps) run against an unpacked sdist, where it
  skipped itself with "CITATION.cff is not
  shipped in the source distribution". ``python -m build --sdist`` now differs from
  before only by the archive entry ``pypcapkit-1.5.0b4/CITATION.cff``, the shipped copy
  is byte-identical, and ``twine check --strict`` passes on both (:pr:`631`).
* the release workflow published to PyPI and to Anaconda with nothing a human had to
  approve. ``create-release.yml``'s ``pypi`` job had ``environment: release`` commented
  out while the ``id-token: write`` from the same upstream snippet was re-added live
  below it, so the block read as disabled as a unit when only its gate still was; the
  ``conda`` job had no ``environment:`` at all. Neither needed a tag: the workflow also
  fires on completion of ``Vendor Update``, so a scheduled registry crawl that bumped
  the version was enough to publish to both public indexes, a median three minutes from
  bump to upload. Every job that reaches outside the run is now gated: ``github`` on
  ``github-release`` (the GitHub Release and the ``v*`` tag), ``tag`` on ``conda-tag``
  (the commit pushed to ``main``), ``pypi`` on ``pypi``, ``conda`` on ``anaconda``.
  One environment per credential rather than a shared ``release``, because approval is
  granted to an environment and not a job, so one ``release`` approved once would
  release both indexes together. PyPI has to be answerable alone: an accepted version
  number cannot be reused, and ``skip-existing: true`` makes the re-upload *succeed*
  having published nothing, so an unintended publish permanently consumes the number
  the intended release wanted. The workflow half is only half the fix: an
  ``environment:`` naming one that does not exist is created implicitly with no
  protection rules and the job proceeds unapproved, so this is inert until each of
  these environments exists in repository settings with a required reviewer, and each
  one's "Deployment branches and tags" must
  stay unrestricted or the ``tags: v*`` trigger fails outright instead of pausing.
  ``github-pages`` is the standing example, carrying no protection rule since 2021. The
  new test asserts the general rule, that no job running a publishing action or a
