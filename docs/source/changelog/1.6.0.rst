1.6.0 -- unreleased
===================

Wave 2 of the roadmap, per the contributing docs' enhancement-proposal page: the
protocol pairs that wanted a shared abstract base, and the two that simply had
no dissector at all. Alongside it come the Linux cooked-capture headers and a
dissector for each ``arphrd_type`` they do not read as an EtherType, the IP
pseudo-header, verified and computed one's-complement checksums, stricter
handling of a malformed IPv6 extension header, and HTTP dispatched to its
HTTP/1 and HTTP/2 classes under the RFC names.

* **Added** -- :class:`~pcapkit.protocols.link.linux_sll1.LinuxSLL1` and
  :class:`~pcapkit.protocols.link.linux_sll2.LinuxSLL2`, dissectors for the
  Linux "cooked" capture headers ``tcpdump -i any`` writes, under
  ``LINKTYPE_LINUX_SLL`` (113) and ``LINKTYPE_LINUX_SLL2`` (276), on a
  :class:`~pcapkit.protocols.link.linux_sll.LinuxSLL` family base; PCAP and
  PCAP-NG frames of either link type dispatch to them (:issue:`2438`,
  :pr:`2443`). ``'LinuxSLL'`` selects either version, and each version's own
  name selects that version alone. ``protocol_type`` dispatches onward as an
  EtherType, except under the ``arphrd_type`` values that carry none --
  ``FRAD``, ``NETLINK``, ``IPGRE``/``IP6GRE`` and ``IEEE80211_RADIOTAP`` --
  each of which has a dissector of its own, below (:issue:`2460`), reached
  through ``LinuxSLL``'s own registry keyed by ``arphrd_type``, which
  :func:`~pcapkit.foundation.registry.protocols.register_arphrd` extends
  (:issue:`2510`, :pr:`2527`), as does a protocol class declaring
  ``code=ARPHRD.X``, since ``ARPHRD`` names ``LinuxSLL`` as its
  ``__proto_dest__`` (:issue:`2533`, :pr:`2598`). A parse told to stop there -- at ``LinuxSLL``,
  the version itself or the link layer -- keeps the payload
  :class:`~pcapkit.protocols.misc.raw.Raw` on either path (:issue:`2532`,
  :pr:`2587`). The hardware types are
  :class:`~pcapkit.const.linux.arphrd.ARPHRD`, generated by
  :class:`pcapkit.vendor.linux.arphrd.ARPHRD` from a hand-maintained table. It
  names only the ``<linux/if_arp.h>`` values that table lists, so any other,
  ``ARPHRD_ETHER`` included, reads as ``Unassigned`` (:issue:`2495`,
  :pr:`2497`).

* **Added** -- :class:`~pcapkit.protocols.link.frad.FRAD`, a dissector for Frame
  Relay's multiprotocol encapsulation (:rfc:`2427`, obsoleting :rfc:`1490`),
  which :class:`~pcapkit.protocols.link.linux_sll.LinuxSLL` dispatches to for
  ``ARPHRD_FRAD`` (:pr:`2499`). The direct NLPID and SNAP-encapsulated forms
  both dispatch onward, to IPv4/IPv6 and (via the EtherType registry every
  Ethernet/VLAN/LinuxSLL frame shares) ARP among others; any other NLPID or
  SNAP OUI is kept as :class:`~pcapkit.protocols.misc.raw.Raw`, and
  :func:`~pcapkit.foundation.registry.protocols.register_frad` registers a
  dissector for a further NLPID (:pr:`2527`).

* **Added** -- :class:`~pcapkit.protocols.link.netlink.Netlink`, a dissector for
  the fixed 16-octet ``nlmsghdr`` framing of Linux's kernel/userspace IPC
  transport (the kernel's ``netlink(7)`` man page;
  :rfc:`3549#section-2.3.2`), which
  :class:`~pcapkit.protocols.link.linux_sll.LinuxSLL` dispatches to for
  ``ARPHRD_NETLINK`` (:issue:`2500`, :pr:`2507`). Netlink is IPC rather than a
  wire format, so the header's byte order is ambiguous;
  :func:`~pcapkit.protocols.link.netlink.nlmsg_byteorder` guesses it the way
  Wireshark's netlink dissector does. Only the first message's header is
  dissected: what follows it, its per-family payload and any further message
  in the same capture, is kept as :class:`~pcapkit.protocols.misc.raw.Raw`
  unless :func:`~pcapkit.foundation.registry.protocols.register_netlink`
  registers a dissector for its ``nlmsg_type`` (:pr:`2527`).

* **Added** -- :class:`~pcapkit.protocols.link.gre.GRE`, a dissector for the
  Generic Routing Encapsulation base header (:rfc:`2784`) plus the optional Key
  and Sequence Number extensions (:rfc:`2890`), which
  :class:`~pcapkit.protocols.link.linux_sll.LinuxSLL` dispatches to for both
  ``ARPHRD_IPGRE`` and ``ARPHRD_IP6GRE`` -- the same GRE framing either way,
  the two differing only in the tunnel's outer IP version (:issue:`2501`,
  :pr:`2508`). The Protocol Type field dispatches onward as an EtherType,
  through the family registry
  (:attr:`Link.__proto__ <pcapkit.protocols.link.link.Link.__proto__>`)
  Ethernet, VLAN and LinuxSLL share. A non-zero Version, :rfc:`2637`'s
  Enhanced GRE, is kept as :class:`~pcapkit.protocols.misc.raw.Raw` rather than
  misread.

* **Added** -- :class:`~pcapkit.protocols.link.radiotap.Radiotap`, a dissector
  for the radiotap header (<https://www.radiotap.org/>) capture tools prepend to
  an 802.11 frame, which :class:`~pcapkit.protocols.link.linux_sll.LinuxSLL`
  dispatches to for ``ARPHRD_IEEE80211_RADIOTAP`` (:issue:`2502`, :pr:`2509`).
  It decodes the fixed 8-octet start (``it_version``, ``it_pad``, ``it_len``)
  and records every present-flags word, following bit 31 from one word to the
  next. The optional fields those words select are kept whole rather than
  decoded, and the 802.11 MAC frame behind them, which has no dissector in this
  package yet, as :class:`~pcapkit.protocols.misc.raw.Raw`.

* **Added** -- :class:`~pcapkit.protocols.internet.icmpv4.ICMPv4` (:rfc:`792`)
  and :class:`~pcapkit.protocols.internet.icmpv6.ICMPv6` (:rfc:`4443`), on an
  abstract :class:`~pcapkit.protocols.internet.icmp.ICMP` base, for IP
  protocols 1 and 58, which were kept as
  :class:`~pcapkit.protocols.misc.raw.Raw` (:issue:`2436`, :pr:`2446`); a
  protochain names ``ICMPv6`` where it named ``IPv6_ICMP``. Echo, Destination
  Unreachable, Time Exceeded and Parameter Problem bodies are decoded, and
  ICMPv6's Packet Too Big; every other type, Neighbor Discovery and MLD
  included, keeps its body raw. ICMPv4 takes the plain ``ICMP`` of :rfc:`792`
  as its ``id()`` and alias.
  :func:`~pcapkit.foundation.registry.protocols.register_icmp_type` registers a
  message-body parser. The type and code registries are
  :mod:`pcapkit.const.icmp` and :mod:`pcapkit.const.icmpv6`, crawled from IANA.

* **Added** -- IGMPv1 (:rfc:`1112`), IGMPv2 (:rfc:`2236`) and IGMPv3
  (:rfc:`3376`), as :class:`~pcapkit.protocols.internet.igmpv1.IGMPv1`,
  :class:`~pcapkit.protocols.internet.igmpv2.IGMPv2` and
  :class:`~pcapkit.protocols.internet.igmpv3.IGMPv3`, each named after its
  module (:issue:`2529`, :pr:`2542`), on an abstract
  :class:`~pcapkit.protocols.internet.igmp.IGMP` base bound at IP protocol 2,
  which picks the version from the message type alone except for a Membership
  Query: one of 8 octets is IGMPv1 if its Max Resp Time is zero and IGMPv2
  otherwise, one of 12 or more IGMPv3 (:issue:`2439`, :issue:`2448`,
  :pr:`2444`, :pr:`2465`). An IGMPv3 Query carries its source list and a
  Membership Report its group records, and an IGMPv3 Query's Max Resp Code and
  QQIC are decoded from their floating-point form. Any other message, a 9- to
  11-octet Query included, is kept as :class:`~pcapkit.protocols.misc.raw.Raw`.
  IGMPv1 takes the plain ``IGMP`` of :rfc:`1112` as its ``id()`` and alias, and
  IGMPv2's and IGMPv3's ``id()`` are their own names alone, ``('IGMPv2',)`` and
  ``('IGMPv3',)``; the base's is ``('IGMP', 'IGMPv2', 'IGMPv3')``, each
  member's canonical name (:issue:`2512`, :pr:`2506`, :pr:`2518`). IGMPv2's
  and IGMPv3's ``name`` carries the version,
  ``'Internet Group Management Protocol version 2'`` say, while IGMPv1's, as
  in :rfc:`1112`, does not (:issue:`2558`, :pr:`2590`). The registries are
  :mod:`pcapkit.const.igmp`: the types crawled from IANA, the group record
  types from a hand-maintained table.

* **Added** -- :class:`~pcapkit.protocols.transport.dccp.DCCP` (:rfc:`4340`)
  for IP protocol 33, which was kept as
  :class:`~pcapkit.protocols.misc.raw.Raw` (:issue:`2489`, :pr:`2593`). It
  reads and builds the generic header with short and long sequence numbers,
  the fields of every packet type, DCCP-Listen (:rfc:`5596`) and the options;
  the Data Checksum option's CRC-32c is recorded rather than checked. Its
  checksum is verified and computed as TCP's is, below, over the enclosing IP
  layer's pseudo-header and the part of the packet its Checksum Coverage
  gives (:rfc:`4340#section-9.2`): a coverage running past the packet is
  ``INVALID`` and warns, and a ``make()`` that computes the checksum writes a
  coverage reaching the end of the packet as 0, as Linux did.
  :func:`~pcapkit.foundation.registry.protocols.register_dccp` registers a
  port's dissector, and
  :func:`~pcapkit.foundation.registry.protocols.register_dccp_option` an
  option parser. The registries are :mod:`pcapkit.const.dccp`, crawled from
  IANA.

* **Added** -- :class:`~pcapkit.protocols.application.tls.TLS` (SSLv3 and TLS
  1.0 to 1.3) at TCP 443 and :class:`~pcapkit.protocols.application.dtls.DTLS`
  (DTLS 1.0, 1.2 and 1.3) at UDP 5684, on an abstract
  :class:`~pcapkit.protocols.application.ssl.SSL` base (:issue:`2437`,
  :pr:`2441`). Each reads every version of its record layer and reports it
  through ``alias``, as :class:`~pcapkit.protocols.link.arp.ARP` does by
  operation, telling 1.3 apart by its ``supported_versions`` extension;
  ``id()`` stays ``('TLS',)`` or ``('DTLS',)``. A cleartext handshake record is
  decoded -- ClientHello and ServerHello down to their cipher suites,
  compression methods and extensions, EncryptedExtensions down to its
  extensions, any other message at type and length -- as are an alert and
  ChangeCipherSpec, while encrypted records stay opaque octets. An extension's
  body is read and built for ``server_name``, ``supported_groups``,
  ``signature_algorithms``, ALPN, ``supported_versions`` and ``key_share``, a
  HelloRetryRequest's included, and kept as octets for any other type or for a
  body its parser rejects, which logs nothing;
  :func:`~pcapkit.foundation.registry.protocols.register_tls_extension`
  registers a parser and constructor for a further type (:issue:`2514`,
  :pr:`2595`). Each whole TLS record in a TCP segment is a layer of its own,
  the previous record's payload, so each alias names its own version --
  ``TCP:TLS 1.3:TLS 1.2`` -- and one that fails to decode is
  :class:`~pcapkit.protocols.misc.raw.Raw` with the rest of the segment
  (:issue:`2517`, :pr:`2537`).
  :class:`~pcapkit.protocols.application.sslv3.SSLv3`, in
  :mod:`pcapkit.protocols.application.sslv3` (:issue:`2529`, :pr:`2602`),
  exists for explicit construction only. A record split across TCP segments is
  not reassembled and stays :class:`~pcapkit.protocols.misc.raw.Raw`. DTLS also
  reads and builds DTLS 1.3's unified-header records
  (:rfc:`9147#section-4.1`), except one carrying a connection ID, which stays
  Raw as an :rfc:`9146` ``tls12_cid`` record does (:issue:`2467`,
  :pr:`2494`). Each whole DTLS record in a UDP datagram is likewise a layer of
  its own -- a DTLS 1.2 record then a DTLS 1.3 unified-header record read
  ``DTLS 1.2:DTLS 1.3`` -- a unified-header record with no length running to
  the end of the datagram, and one that fails to decode is
  :class:`~pcapkit.protocols.misc.raw.Raw` with the rest of the datagram
  (:issue:`2535`, :pr:`2603`). The content, handshake and extension types are
  :mod:`pcapkit.const.tls`, crawled from IANA (:issue:`2495`, :issue:`2514`,
  :pr:`2503`, :pr:`2595`).

* **Added** -- :class:`~pcapkit.protocols.application.sslv2.SSLv2`, a dissector
  for SSL version 2 (draft-hickman-netscape-ssl-00), whose record layer shares
  nothing with TLS's (:issue:`2457`, :pr:`2466`). It is bound to no port: on
  TCP 443 a segment's first record that TLS rejects is tried as SSLv2, and
  kept only as a complete CLIENT-HELLO or SERVER-HELLO whose length fields
  agree, so anything else stays :class:`~pcapkit.protocols.misc.raw.Raw`; a
  kept one drops the rejected TLS trial's warnings (:issue:`2525`,
  :pr:`2537`). Each whole record after the first in a TCP segment, whatever
  its message type, is a further SSLv2 layer, the previous record's payload,
  as with TLS -- a ``CLIENT-HELLO`` then a ``CLIENT-MASTER-KEY`` read
  ``SSLv2:SSLv2`` -- and one that fails to decode is
  :class:`~pcapkit.protocols.misc.raw.Raw` with the rest of the segment
  (:issue:`2567`, :pr:`2585`). Its constants are :mod:`pcapkit.const.sslv2`,
  from a hand-maintained table.

* **Added** -- dissection of every whole HTTP/2 frame in a TCP segment: each
  after the first, which was kept as :class:`~pcapkit.protocols.misc.raw.Raw`,
  is a further :class:`~pcapkit.protocols.application.httpv2.HTTPv2` layer, the
  previous frame's payload, as with TLS -- a ``SETTINGS`` then a
  ``WINDOW_UPDATE`` frame read ``TCP:HTTP/2:HTTP/2`` (:issue:`2536`,
  :pr:`2609`). One that fails to decode is
  :class:`~pcapkit.protocols.misc.raw.Raw` with the rest of the segment and
  the parser's ``error``, and a frame the segment ends inside stays
  :class:`~pcapkit.protocols.misc.raw.Raw` with none. A parse told to stop at
  HTTP/2 keeps the rest of the segment raw, and
  :data:`~pcapkit.utilities.config.FRAME_LAYER_LIMIT` bounds how many frames
  are dissected.

* **Added** -- :class:`pcapkit.foundation.reassembly.dtls.DTLS`, exported as
  ``DTLS_Reassembly``, which reassembles a DTLS handshake message fragmented
  across records (:rfc:`6347#section-4.2.3`), keyed by the UDP 4-tuple and the
  epoch, accepting overlapping fragments and holding a buffer until it
  completes (:issue:`2440`, :pr:`2451`). It is opt-in, as ``dtls=True`` with
  ``reassembly=True`` to :class:`~pcapkit.foundation.extraction.Extractor` or
  :func:`~pcapkit.interface.core.extract`, and runs on the default engine
  alone, fed by :func:`~pcapkit.toolkit.pcap.dtls_reassembly` and its
  :mod:`pcapkit.toolkit.pcapng` counterpart from the first record of each
  datagram only; any other engine turns it off with a warning.
  :func:`~pcapkit.foundation.analysis.dtls.dtls_handshake` decodes a
  reassembled message (:issue:`2496`, :pr:`2528`). A reassembled
  :class:`Datagram <pcapkit.foundation.reassembly.data.dtls.Datagram>` holds
  that decode as ``packet``, run on its first read as an IP or TCP datagram's
  is, and :data:`None` for an incomplete message (:issue:`2531`, :pr:`2605`).

* **Added** -- :class:`~pcapkit.protocols.misc.checksum.ip_pseudo.IP_Pseudo`,
  the IPv4 (:rfc:`793`) or IPv6 (:rfc:`8200#section-8.1`) pseudo-header an
  upper-layer checksum covers, built from an IPv4 or IPv6 layer, explicit
  values, or both (:issue:`2471`, :pr:`2479`). From a layer it takes the final
  destination of a source route or of a Routing header with segments left, a
  Home Address option's address as the IPv6 source, and the upper-layer
  length, from UDP's Length or a jumbogram's Jumbo Payload Length where those
  apply; a fragment of a larger packet, or a header it cannot walk at any
  depth of the chain, raises :exc:`~pcapkit.utilities.exceptions.ProtocolError`
  (:issue:`2513`, :pr:`2543`). It is not a layer on the wire.

* **Added** -- verification and computation of the one's-complement Internet
  checksum (:rfc:`1071`) of the IPv4 header, TCP, UDP, ICMP, ICMPv6 and OSPFv2,
  in :mod:`pcapkit.corekit.checksum.internet` (:issue:`2470`, :issue:`2472`,
  :issue:`2473`, :issue:`2474`, :issue:`2475`, :pr:`2543`), where
  :mod:`pcapkit.corekit.checksum` holds a module per checksum family and
  imports nothing from :mod:`pcapkit.protocols` (:issue:`2580`, :pr:`2586`).
  Parsing verifies only under ``PCAPKIT_CHECKSUM_VERIFY``, off by default,
  recording a :class:`~pcapkit.corekit.checksum.internet.ChecksumStatus`
  as ``checksum_status`` and warning on a mismatch with
  :exc:`~pcapkit.utilities.warnings.ChecksumWarning`, a
  :exc:`~pcapkit.utilities.warnings.ProtocolWarning` a filter can silence
  alone. Construction computes a checksum the caller leaves out, unless
  ``PCAPKIT_CHECKSUM_COMPUTE`` is off. An IPv4 or IPv6 layer verifies and
  computes its upper layer's checksum over the
  :class:`~pcapkit.protocols.misc.checksum.ip_pseudo.IP_Pseudo` it builds, and
  ``make()`` of TCP, UDP and ICMPv6 also takes a ``pseudo``. What checksum
  offload leaves on the sending host is ``NOT_COMPUTED`` rather than a
  mismatch; a fragment's TCP, UDP, ICMP or ICMPv6 checksum, which covers
  octets the fragment lacks, is ``NO_PSEUDO_HEADER``.

* **Added** -- :func:`~pcapkit.foundation.registry.protocols.register_ipx`,
  :func:`~pcapkit.foundation.registry.protocols.register_loopback`,
  :func:`~pcapkit.foundation.registry.protocols.register_sctp_chunk`,
  :func:`~pcapkit.foundation.registry.protocols.register_sctp_parameter` and
  :func:`~pcapkit.foundation.registry.protocols.register_sctp_cause`, wrapping
  IPX's packet-type map, Loopback's address-family map and SCTP's chunk,
  chunk-parameter and error-cause parser maps with the validation the other
  wrappers carry, and the
  :meth:`IPX.register <pcapkit.protocols.internet.ipx.IPX.register>` and
  :meth:`Loopback.register <pcapkit.protocols.link.loopback.Loopback.register>`
  classmethods the IPX and Loopback wrappers call (:issue:`2511`,
  :pr:`2521`).

* **Changed** -- **a breaking change to** the IPv6 extension-header walk: a
  known extension header whose dedicated parser raises is now the upper layer,
  parsed once as :class:`~pcapkit.protocols.misc.raw.Raw`, and the walk stops
  there, as :rfc:`8200#section-4` has a node discard such a packet
  (:issue:`2477`, :pr:`2480`). It used to fall back to the generic
  :class:`~pcapkit.protocols.internet.ipv6_ext.IPv6_Ext` and walk on;
  ``IPv6_Ext`` now parses only Shim6, which has no dedicated parser, and
  ``IPv6.__generic_ext_codes__``, the headers that fell back, is removed. The
  library no longer passes
  :meth:`IPv6_Ext.read() <pcapkit.protocols.internet.ipv6_ext.IPv6_Ext.read>`
  an ``error=``, so
  :attr:`IPv6_Ext.error <pcapkit.protocols.data.internet.ipv6_ext.IPv6_Ext.error>`
  is :data:`None` unless a caller supplies one; the ``Raw`` layer's
  ``info.error`` holds the failure instead.

* **Changed** -- **a breaking change to** construction: a checksum left out of
  ``make()`` is computed rather than zero, so the octets built change
  (:issue:`2471`, :pr:`2543`). :class:`~pcapkit.protocols.internet.ipv4.IPv4`
  computes its header checksum, an IPv4 or IPv6 layer that of a TCP or UDP
  payload built without one, and
  :class:`~pcapkit.protocols.application.ospf.OSPF` that of an OSPFv2 packet.
  A checksum given is written as given, and turning
  ``PCAPKIT_CHECKSUM_COMPUTE`` off restores zero.

* **Changed** -- **a breaking change to**
  :class:`~pcapkit.protocols.application.drarp.DRARP` and
  :class:`~pcapkit.protocols.link.inarp.InARP`, which move from
  :mod:`pcapkit.protocols.application.rarp` to
  :mod:`pcapkit.protocols.application.drarp` and from
  :mod:`pcapkit.protocols.link.arp` to :mod:`pcapkit.protocols.link.inarp`,
  with no re-export at the old paths, as a module holds one protocol class
  (:issue:`2529`, :pr:`2540`, :pr:`2596`). ``pcapkit.DRARP``,
  ``pcapkit.InARP``, their :mod:`pcapkit.protocols` exports and a parsed
  RARP's ``DRARP`` or ARP's ``InARP`` alias are unchanged.

* **Changed** -- **a breaking change to** HTTP: parsing octets through
  :class:`~pcapkit.protocols.application.http.HTTP`, building it from fields
  and its ``from_data`` give the
  :class:`~pcapkit.protocols.application.httpv1.HTTPv1` or
  :class:`~pcapkit.protocols.application.httpv2.HTTPv2` member, never an
  instance of the base, and so does a TCP or UDP payload on an HTTP port, whose
  data sits under ``httpv1`` or ``httpv2`` where it sat under ``http``
  (:issue:`2524`, :pr:`2544`). The members are renamed after their modules,
  ``httpv1.HTTP`` and ``httpv2.HTTP`` becoming ``HTTPv1`` and ``HTTPv2`` along
  with their schema and data classes, with no re-export at the old paths
  (:issue:`2529`); ``pcapkit.HTTPv1``, ``pcapkit.HTTPv2`` and the package
  exports of those names are unchanged. ``id()`` takes the RFC names,
  ``('HTTP/1',)`` and ``('HTTP/2',)``, and the base's lists both, where they
  were ``('HTTP', 'HTTPv1')``, ``('HTTP', 'HTTPv2')`` and
  ``('HTTP', 'HTTPv1', 'HTTPv2')``. So a layer no longer compares equal to
  ``'HTTP'``, ``'HTTPv1'`` or ``'HTTPv2'``; ``'HTTP'`` still selects either
  version, and each version's own name, ``'HTTP/1'`` or ``'HTTPv1'`` say,
  selects it alone, where any HTTP layer matched ``'HTTPv1'`` and ``'HTTPv2'``
  both. On the transport path a payload neither version recognises, a bare
  connection preface included, is :class:`~pcapkit.protocols.misc.raw.Raw`
  with no ``error``, where it carried ``'HTTP: unknown version'`` or
  ``'HTTP/2: connection preface with no frame'``; a direct ``HTTP(...)`` on it
  still raises :exc:`~pcapkit.utilities.exceptions.ProtocolError`. One that
  passes for an HTTP/2 frame header but ``HTTPv2`` refuses carries that
  parser's own error on either path, where it was ``'HTTP: unknown version'``.
  ``HTTPv2`` itself now parses a payload opening with the connection preface,
  kept as ``preface``, and its ``make()`` takes ``preface``.

* **Changed** -- **a breaking change to** IPv6 reassembly: a fragment
  overlapping another of its datagram, other than an exact duplicate, abandons
  the datagram, reported as
  :attr:`Completion.OVERLAP <pcapkit.foundation.reassembly.data.data.Completion.OVERLAP>`,
  as :rfc:`8200#section-4.5` requires; 1.5.x overwrote the octets it overlapped,
  as IPv4 still does under :rfc:`791` (:issue:`2547`, :pr:`2569`).
  :class:`~pcapkit.foundation.reassembly.data.ip.Buffer` gains a required
  ``extent`` field.

* **Changed** -- **a breaking change to** TCP reassembly's gap cap:
  ``pcapkit.foundation.reassembly.tcp.TCP.__window__`` is removed with no
  alias, and the cap is :data:`~pcapkit.utilities.config.TCP_GAP_LIMIT`, set
  by ``PCAPKIT_TCP_GAP_LIMIT``, 16 MiB by default as before and ``-1`` for no
  limit (:issue:`2546`, :pr:`2579`). It is a safety limit, read each time
  :meth:`TCP.reassembly <pcapkit.foundation.reassembly.tcp.TCP.reassembly>`
  runs, and ``-1`` or a value above the default warns with
  :exc:`~pcapkit.utilities.warnings.ConfigWarning`.

* **Changed** -- **a breaking change to**
  :class:`~pcapkit.foundation.extraction.Extractor` and
  :func:`~pcapkit.interface.core.extract`: their ``dtls`` parameter, above,
  follows ``tcp``, so a positional argument from ``buffer_size`` on moves one
  place along, and :class:`~pcapkit.foundation.reassembly.ReassemblyManager`
  takes a required ``dtls`` (:issue:`2496`, :pr:`2528`).

* **Changed** -- protocol class bodies are reordered to the member-order
  convention, with no change in behaviour, and a project test guards the
  order (:issue:`2490`, :pr:`2491`, :pr:`2522`, :pr:`2523`, :pr:`2538`,
  :pr:`2539`, :pr:`2541`, :pr:`2613`).

* **Changed** -- the house conventions record that a protocol class takes its
  module's name, one to a module (:issue:`2529`, :pr:`2542`); that a
  versioned family's base dispatches on every path, so parsing, building and
  ``from_data`` give a member rather than the base (:issue:`2524`,
  :pr:`2544`); that a docstring or prose block carries one ``versionadded``
  per version, without a body that only names the thing added (:issue:`2530`,
  :pr:`2542`); and that each class-level registry map has a wrapper in
  :mod:`pcapkit.foundation.registry` (:issue:`2511`, :pr:`2521`). ``const`` is
  a label added alongside a commit type rather than a type, in the pull
  request template and ``CONTRIBUTING.md`` too, and a span the transport
