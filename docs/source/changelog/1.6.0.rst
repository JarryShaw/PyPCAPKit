1.6.0 -- unreleased
===================

Wave 2 of the roadmap, per the contributing docs' enhancement-proposal page: the
protocol pairs that wanted a shared abstract base, and the two that simply had
no dissector at all. Alongside it come the Linux cooked-capture headers and a
dissector for each ``arphrd_type`` they do not read as an EtherType, the IP
pseudo-header, and stricter handling of a malformed IPv6 extension header.

* **Added** -- :class:`~pcapkit.protocols.link.linux_sll1.LinuxSLL1` and
  :class:`~pcapkit.protocols.link.linux_sll2.LinuxSLL2`, dissectors for the
  Linux "cooked" capture headers ``tcpdump -i any`` writes, under
  ``LINKTYPE_LINUX_SLL`` (113) and ``LINKTYPE_LINUX_SLL2`` (276), on a
  :class:`~pcapkit.protocols.link.linux_sll.LinuxSLL` family base; PCAP and
  PCAP-NG frames of either link type dispatch to them (:issue:`2438`,
  :pr:`2443`). ``'LinuxSLL'`` selects either version, and each version's own
  name selects that version alone. ``protocol_type`` dispatches onward as an
  EtherType, except under the ``arphrd_type`` values that carry none --
  ``FRAD``, ``NETLINK``, ``IPGRE``/``IP6GRE`` and ``IEEE80211_RADIOTAP`` --
  each of which has a dissector of its own, below (:issue:`2460`). The
  hardware types are :class:`~pcapkit.const.linux.arphrd.ARPHRD`, generated
  from a hand-maintained table of ``<linux/if_arp.h>`` in
  :class:`pcapkit.vendor.linux.arphrd.ARPHRD` (:issue:`2495`, :pr:`2497`).

* **Added** -- :class:`~pcapkit.protocols.link.frad.FRAD`, a dissector for Frame
  Relay's multiprotocol encapsulation (:rfc:`2427`, obsoleting :rfc:`1490`),
  which :class:`~pcapkit.protocols.link.linux_sll.LinuxSLL` dispatches to for
  ``ARPHRD_FRAD`` (:pr:`2499`). The direct NLPID and SNAP-encapsulated forms
  both dispatch onward, to IPv4/IPv6 and (via the EtherType registry every
  Ethernet/VLAN/LinuxSLL frame shares) ARP among others; any other NLPID or
  SNAP OUI is kept as :class:`~pcapkit.protocols.misc.raw.Raw`.

* **Added** -- :class:`~pcapkit.protocols.link.netlink.Netlink`, a dissector for
  the fixed 16-octet ``nlmsghdr`` framing of Linux's kernel/userspace IPC
  transport (the kernel's ``netlink(7)`` man page;
  :rfc:`3549#section-2.3.2`), which
  :class:`~pcapkit.protocols.link.linux_sll.LinuxSLL` dispatches to for
  ``ARPHRD_NETLINK`` (:issue:`2500`, :pr:`2507`). Netlink is IPC rather than a
  wire format, so the header's byte order is ambiguous;
  :func:`~pcapkit.protocols.link.netlink.nlmsg_byteorder` guesses it the way
  Wireshark's netlink dissector does. Only the first message's header is
  dissected: its per-family payload, and any further message in the same
  capture, are kept as :class:`~pcapkit.protocols.misc.raw.Raw`.

* **Added** -- :class:`~pcapkit.protocols.link.gre.GRE`, a dissector for the
  Generic Routing Encapsulation base header (:rfc:`2784`) plus the optional Key
  and Sequence Number extensions (:rfc:`2890`), which
  :class:`~pcapkit.protocols.link.linux_sll.LinuxSLL` dispatches to for both
  ``ARPHRD_IPGRE`` and ``ARPHRD_IP6GRE`` -- the same GRE framing either way,
  the two differing only in the tunnel's outer IP version (:issue:`2501`,
  :pr:`2508`). The Protocol Type field dispatches onward as an EtherType,
  through the family registry
  (:attr:`Link.__proto__ <pcapkit.protocols.link.link.Link.__proto__>`)
  Ethernet, VLAN and LinuxSLL share. A non-zero Version, :rfc:`2637`'s
  Enhanced GRE, is kept as :class:`~pcapkit.protocols.misc.raw.Raw` rather than
  misread.

* **Added** -- :class:`~pcapkit.protocols.link.radiotap.Radiotap`, a dissector
  for the radiotap header (<https://www.radiotap.org/>) capture tools prepend to
  an 802.11 frame, which :class:`~pcapkit.protocols.link.linux_sll.LinuxSLL`
  dispatches to for ``ARPHRD_IEEE80211_RADIOTAP`` (:issue:`2502`, :pr:`2509`).
  It decodes the fixed 8-octet start (``it_version``, ``it_pad``, ``it_len``)
  and records every present-flags word, following bit 31 from one word to the
  next. The optional fields those words select are kept whole rather than
  decoded, and the 802.11 MAC frame behind them, which has no dissector in this
  package yet, as :class:`~pcapkit.protocols.misc.raw.Raw`.

* **Added** -- :class:`~pcapkit.protocols.internet.icmpv4.ICMPv4` (:rfc:`792`)
  and :class:`~pcapkit.protocols.internet.icmpv6.ICMPv6` (:rfc:`4443`), on an
  abstract :class:`~pcapkit.protocols.internet.icmp.ICMP` base, for IP
  protocols 1 and 58, which were kept as
  :class:`~pcapkit.protocols.misc.raw.Raw` (:issue:`2436`, :pr:`2446`); a
  protochain names ``ICMPv6`` where it named ``IPv6_ICMP``. Echo, Destination
  Unreachable, Time Exceeded and Parameter Problem bodies are decoded, and
  ICMPv6's Packet Too Big; every other type, Neighbor Discovery and MLD
  included, keeps its body raw. The checksum is recorded, never verified or
  computed (:issue:`2470`). ICMPv4 takes the plain ``ICMP`` of :rfc:`792` as
  its ``id()`` and alias.
  :func:`~pcapkit.foundation.registry.protocols.register_icmp_type` registers a
  message-body parser. The type and code registries are
  :mod:`pcapkit.const.icmp` and :mod:`pcapkit.const.icmpv6`, crawled from IANA.

* **Added** -- IGMPv1 (:rfc:`1112`), IGMPv2 (:rfc:`2236`) and IGMPv3
  (:rfc:`3376`), as :class:`IGMPv1 <pcapkit.protocols.internet.igmpv1.IGMP>`,
  :class:`IGMPv2 <pcapkit.protocols.internet.igmpv2.IGMP>` and
  :class:`IGMPv3 <pcapkit.protocols.internet.igmpv3.IGMP>` on an abstract
  :class:`~pcapkit.protocols.internet.igmp.IGMP` base bound at IP protocol 2,
  which picks the version from the message type and length (:issue:`2439`,
  :issue:`2448`, :pr:`2444`, :pr:`2465`). An IGMPv3 Query carries its source
  list and a Membership Report its group records, and an IGMPv3 Query's Max
  Resp Code and QQIC are decoded from their floating-point form. Any other
  message, a 9- to 11-octet Query included, is kept as
  :class:`~pcapkit.protocols.misc.raw.Raw`. IGMPv1 takes the plain ``IGMP`` of
  :rfc:`1112` as its ``id()`` and alias, and IGMPv2's ``id()`` is its own name
  alone (:pr:`2506`). The registries are :mod:`pcapkit.const.igmp`: the types
  crawled from IANA, the group record types from a hand-maintained table.

* **Added** -- :class:`~pcapkit.protocols.application.tls.TLS` (SSLv3 and TLS
  1.0 to 1.3) at TCP 443 and :class:`~pcapkit.protocols.application.dtls.DTLS`
  (DTLS 1.0, 1.2 and 1.3) at UDP 5684, on an abstract
  :class:`~pcapkit.protocols.application.ssl.SSL` base (:issue:`2437`,
  :pr:`2441`). Each reads every version of its record layer and reports it
  through ``alias``, as :class:`~pcapkit.protocols.link.arp.ARP` does by
  operation, telling 1.3 apart by its ``supported_versions`` extension;
  ``id()`` stays ``('TLS',)`` or ``('DTLS',)``. A cleartext handshake record is
  decoded -- ClientHello and ServerHello down to their cipher suites,
  compression methods and extension types, any other message at type and
  length -- as are an alert and ChangeCipherSpec, while encrypted records stay
  opaque octets. :class:`~pcapkit.protocols.application.tls.SSLv3` exists for
  explicit construction only. A record split across TCP segments is not
  reassembled and stays :class:`~pcapkit.protocols.misc.raw.Raw`. DTLS also
  reads and builds DTLS 1.3's unified-header records
  (:rfc:`9147#section-4.1`), except one carrying a connection ID, which stays
  Raw as an :rfc:`9146` ``tls12_cid`` record does (:issue:`2467`,
  :pr:`2494`). The content and handshake types are :mod:`pcapkit.const.tls`,
  crawled from IANA (:issue:`2495`, :pr:`2503`).

* **Added** -- :class:`~pcapkit.protocols.application.sslv2.SSLv2`, a dissector
  for SSL version 2 (draft-hickman-netscape-ssl-00), whose record layer shares
  nothing with TLS's (:issue:`2457`, :pr:`2466`). It is bound to no port: on
  TCP 443 a record TLS rejects is tried as SSLv2, and kept only as a complete
  CLIENT-HELLO or SERVER-HELLO whose length fields agree, so anything else
  stays :class:`~pcapkit.protocols.misc.raw.Raw`. Its constants are
  :mod:`pcapkit.const.sslv2`, from a hand-maintained table.

* **Added** -- :class:`pcapkit.foundation.reassembly.dtls.DTLS`, exported as
  ``DTLS_Reassembly``, which reassembles a DTLS handshake message fragmented
  across records (:rfc:`6347#section-4.2.3`), keyed by the UDP 4-tuple and the
  epoch, accepting overlapping fragments and holding a buffer until it
  completes (:issue:`2440`, :pr:`2451`). It is opt-in: given to the
  :class:`~pcapkit.protocols.application.dtls.DTLS` dissector as
  ``reassembly=``, with the 4-tuple as ``flow=``, it lets the completing
  fragment's message decode, for the first record of each datagram only.
  :class:`~pcapkit.foundation.extraction.Extractor` does not drive it
  (:issue:`2496`).

* **Added** -- :class:`~pcapkit.protocols.misc.checksum.ip_pseudo.IP_Pseudo`,
  the IPv4 (:rfc:`793`) or IPv6 (:rfc:`8200#section-8.1`) pseudo-header an
  upper-layer checksum covers, built from an IPv4 or IPv6 layer, explicit
  values, or both (:issue:`2471`, :pr:`2479`). From a layer it takes the final
  destination of a source route or of a Routing header with segments left, a
  Home Address option's address as the IPv6 source, and the upper-layer
  length, from UDP's Length or a jumbogram's Jumbo Payload Length where those
  apply; a fragment of a larger packet, or a header it cannot walk, raises
  :exc:`~pcapkit.utilities.exceptions.ProtocolError`. It is not a layer on the
  wire.

* **Changed** -- **a breaking change to** the IPv6 extension-header walk: a
  known extension header whose dedicated parser raises is now the upper layer,
  parsed once as :class:`~pcapkit.protocols.misc.raw.Raw`, and the walk stops
  there, as :rfc:`8200#section-4` has a node discard such a packet
  (:issue:`2477`, :pr:`2480`). It used to fall back to the generic
  :class:`~pcapkit.protocols.internet.ipv6_ext.IPv6_Ext` and walk on;
  ``IPv6_Ext`` now parses only Shim6, which has no dedicated parser, and
  ``IPv6.__generic_ext_codes__``, the headers that fell back, is removed.

* **Changed** -- a pull request no longer adds its own changelog bullet: an
  unreleased version's entries are written centrally by the maintainer, and
  ``CONTRIBUTING.md`` and the pull request template say so (:issue:`2449`,
  :pr:`2483`).

* **Fixed** -- selecting ``'IPv6_Ext'`` matched none of the dedicated
  extension headers:
  :meth:`IPv6_Ext.id() <pcapkit.protocols.internet.ipv6_ext.IPv6_Ext.id>` now
  lists its direct concrete subclasses -- HOPOPT, IPv6_Route, IPv6_Frag, ESP,
  AH, IPv6_Opts, MH and HIP -- each of which keeps its own name alone, as AH
  and ESP do under IPsec (:issue:`2462`, :pr:`2464`).

* **Fixed** -- a membership test such as ``'ESP' in layer`` on an extension
  header parsed by the IPv6 header's walk -- AH, HOPOPT, IPv6_Route, IPv6_Frag,
  IPv6_Opts, MH, HIP or the generic IPv6_Ext -- raised :exc:`AttributeError`.
  The layer now holds :class:`~pcapkit.protocols.misc.null.NoPayload`, the
  upper layer belonging to the enclosing IPv6 header (:issue:`2484`,
  :issue:`2487`, :pr:`2486`, :pr:`2488`).
