1.6.0 -- 2026-11-05
===================

Wave 2 of the roadmap, per the contributing docs' enhancement-proposal page: the
protocol pairs that wanted a shared abstract base, the Linux cooked-capture headers
among them, and the two that simply had no dissector at all. Alongside it come a
dissector for each ``arphrd_type`` those headers do not read as an EtherType, the IP
pseudo-header, verified and computed one's-complement checksums, stricter
handling of a malformed IPv6 extension header, and HTTP dispatched to its
HTTP/1 and HTTP/2 classes under the RFC names.

* **Added** -- :class:`~pcapkit.protocols.link.linux_sll1.protocol.LinuxSLL1` and
  :class:`~pcapkit.protocols.link.linux_sll2.protocol.LinuxSLL2`, dissectors for the
  Linux "cooked" capture headers ``tcpdump -i any`` writes, under
  ``LINKTYPE_LINUX_SLL`` (113) and ``LINKTYPE_LINUX_SLL2`` (276), on a
  :class:`~pcapkit.protocols.link.linux_sll.protocol.LinuxSLL` family base; PCAP and
  PCAP-NG frames of either link type dispatch to them (:issue:`2438`,
  :pr:`2443`). ``'LinuxSLL'`` selects either version, and each version's own
  name selects that version alone. ``protocol_type`` dispatches onward as an
  EtherType, except under the ``arphrd_type`` values that carry none --
  ``FRAD``, ``NETLINK``, ``IPGRE``/``IP6GRE`` and ``IEEE80211_RADIOTAP`` --
  each of which has a dissector of its own, below (:issue:`2460`), reached
  through ``LinuxSLL``'s own registry keyed by ``arphrd_type``, which
  :func:`~pcapkit.foundation.registry.protocols.link.register_arphrd` extends
  (:issue:`2510`, :pr:`2527`), as does a protocol class declaring
  ``code=ARPHRD.X``, since ``ARPHRD`` names ``LinuxSLL`` as its
  ``__proto_dest__`` (:issue:`2533`, :pr:`2598`). A parse told to stop there -- at ``LinuxSLL``,
  the version itself or the link layer -- keeps the payload
  :class:`~pcapkit.protocols.misc.raw.protocol.Raw` on either path (:issue:`2532`,
  :pr:`2587`). The hardware types are
  :class:`~pcapkit.const.linux.arphrd.ARPHRD`, generated by
  :class:`pcapkit.vendor.linux.arphrd.ARPHRD` from a hand-maintained table. It
  names only the ``<linux/if_arp.h>`` values that table lists, so any other,
  ``ARPHRD_ETHER`` included, reads as ``Unassigned`` (:issue:`2495`,
  :pr:`2497`), and :mod:`pcapkit.const` exports it as ``Linux_ARPHRD``
  (:issue:`2661`, :pr:`2663`).

* **Added** -- :class:`~pcapkit.protocols.link.frad.protocol.FRAD`, a dissector for Frame
  Relay's multiprotocol encapsulation (:rfc:`2427`, obsoleting :rfc:`1490`),
  which :class:`~pcapkit.protocols.link.linux_sll.protocol.LinuxSLL` dispatches to for
  ``ARPHRD_FRAD`` (:pr:`2499`), as do PCAP and PCAP-NG frames of
  ``LINKTYPE_FRELAY`` (107) (:issue:`2649`, :pr:`2667`). The direct NLPID and SNAP-encapsulated forms
  both dispatch onward, to IPv4/IPv6 and (via the EtherType registry every
  Ethernet/VLAN/LinuxSLL frame shares) ARP among others; any other NLPID or
  SNAP OUI is kept as :class:`~pcapkit.protocols.misc.raw.protocol.Raw`, and
  :func:`~pcapkit.foundation.registry.protocols.link.register_frad` registers a
  dissector for a further NLPID (:pr:`2527`). A Q.922 address other than the
  2-octet form, its EA bits other than 0 then 1, is refused with
  :exc:`~pcapkit.utilities.exceptions.ProtocolError` unless the capture cut it
  short, and is kept as ``Raw`` with nothing logged behind ``LinuxSLL`` or a
  ``LINKTYPE_FRELAY`` capture. A header the capture cut short, before its NLPID
  included, rebuilds as captured and logs nothing (:issue:`2710`, :pr:`2719`).
  The data model records as ``pad`` whether the one ``0x00`` pad octet
  :rfc:`2427#section-3` allows ahead of an NLPID was captured, so a frame
  rebuilds with its pad or without it, as captured; ``make()`` takes ``pad``,
  by default writing one ahead of a SNAP header or an NLPID of 0, and refuses
  ``pad=False`` with an NLPID of 0 (:issue:`2716`, :pr:`2721`).

* **Added** -- :class:`~pcapkit.protocols.link.netlink.protocol.Netlink`, a dissector for
  the fixed 16-octet ``nlmsghdr`` framing of Linux's kernel/userspace IPC
  transport (the kernel's ``netlink(7)`` man page;
  :rfc:`3549#section-2.3.2`), which
  :class:`~pcapkit.protocols.link.linux_sll.protocol.LinuxSLL` dispatches to for
  ``ARPHRD_NETLINK`` (:issue:`2500`, :pr:`2507`). Netlink is IPC rather than a
  wire format, so the header's byte order is ambiguous;
  :func:`~pcapkit.protocols.link.netlink.protocol.nlmsg_byteorder` guesses it the way
  Wireshark's netlink dissector does. Only the first message's header is
  dissected: what follows it, its per-family payload and any further message
  in the same capture, is kept as :class:`~pcapkit.protocols.misc.raw.protocol.Raw`
  unless :func:`~pcapkit.foundation.registry.protocols.link.register_netlink`
  registers a dissector for its ``nlmsg_type`` (:pr:`2527`).

* **Added** -- :class:`~pcapkit.protocols.link.gre.protocol.GRE`, a dissector for the
  Generic Routing Encapsulation base header (:rfc:`2784`) plus the optional Key
  and Sequence Number extensions (:rfc:`2890`), which
  :class:`~pcapkit.protocols.link.linux_sll.protocol.LinuxSLL` dispatches to for both
  ``ARPHRD_IPGRE`` and ``ARPHRD_IP6GRE`` -- the same GRE framing either way,
  the two differing only in the tunnel's outer IP version (:issue:`2501`,
  :pr:`2508`), as does an IP layer for IP protocol 47, through the registry
  (:attr:`Internet.__proto__ <pcapkit.protocols.internet.internet.Internet.__proto__>`)
  IPv4 and IPv6 share (:issue:`2649`, :pr:`2667`). So with reassembly and
  tracing on, analysis follows a GRE tunnel: TCP inside GRE over IP
  reassembles under its inner addresses, and a fragmented GRE datagram
  reassembles to a parsed GRE layer. The Protocol Type field dispatches onward as an EtherType,
  through the family registry
  (:attr:`Link.__proto__ <pcapkit.protocols.link.link.Link.__proto__>`)
  Ethernet, VLAN and LinuxSLL share. A non-zero Version, :rfc:`2637`'s
  Enhanced GRE, is kept as :class:`~pcapkit.protocols.misc.raw.protocol.Raw` rather than
  misread.

* **Added** -- :class:`~pcapkit.protocols.link.radiotap.protocol.Radiotap`, a dissector
  for the radiotap header (<https://www.radiotap.org/>) capture tools prepend to
  an 802.11 frame, which :class:`~pcapkit.protocols.link.linux_sll.protocol.LinuxSLL`
  dispatches to for ``ARPHRD_IEEE80211_RADIOTAP`` (:issue:`2502`, :pr:`2509`),
  as do PCAP and PCAP-NG frames of ``LINKTYPE_IEEE802_11_RADIOTAP`` (127)
  (:issue:`2608`, :pr:`2632`). It decodes the fixed 8-octet start (``it_version``, ``it_pad``, ``it_len``)
  and records every present-flags word, following bit 31 from one word to the
  next. The optional fields those words select are kept whole as ``fields``,
  which a rebuild writes, and decoded as ``decoded``, an entry in wire order
  for each bit that selects a radiotap field or switches namespace, each field
  aligned from the start of the header as radiotap.org lays it out
  (:issue:`2576`, :pr:`2657`). That covers radiotap.org's defined
  fields, the RTS and data retries of bits 16 and 17, the radiotap and vendor
  namespace switches, a vendor namespace's data kept raw, and the items of TLV
  mode, a vendor item split into its header and raw data. An item a producer
  cut short of its layout, as radiotap.org allows, decodes with the octets it
  lacks as zeros and rebuilds as captured (:issue:`2655`, :pr:`2690`). A bit
  no field is defined for, or a field running past the region, ends the walk
  as an :class:`~pcapkit.protocols.link.radiotap.data.Unknown` entry holding
  the rest, and ``make()`` takes the fields decoded as well as raw. Each field
  type has a concrete
  :class:`~pcapkit.protocols.link.radiotap.schema.RadiotapField` schema, and
  is read and made through
  :attr:`Radiotap.__field__ <pcapkit.protocols.link.radiotap.protocol.Radiotap.__field__>`,
  which
  :meth:`Radiotap.register_field <pcapkit.protocols.link.radiotap.protocol.Radiotap.register_field>`
  and :func:`~pcapkit.foundation.registry.protocols.link.register_radiotap_field`
  extend. A bitmap
  radiotap.org defines bit by bit is a member of its flag registry, which
  keeps the bits it does not name. One mixing value subfields with flags --
  MCS ``flags``, HE ``data1`` and ``data2``, HE-MU ``flags1`` and ``flags2``
  and U-SIG ``common`` -- decodes into a data model of its subfields, each an
  :class:`int`, and, except in MCS's, its other bits as ``known``, a member of a
  known-bits registry such as
  :class:`~pcapkit.const.radiotap.he_data1_known.HEData1Known`; ``make()``
  takes it as a mapping, refusing a subfield its bits cannot hold or a
  ``known`` setting a subfield's bit with
  :exc:`~pcapkit.utilities.exceptions.ProtocolError` (:issue:`2647`,
  :pr:`2696`). :class:`~pcapkit.corekit.fields.numbers.BitmapField` reads
  such a word, an integer in its byte order split into subfields counted from
  its least-significant bit. The field types and those registries are
  :mod:`pcapkit.const.radiotap`, crawled from radiotap.org's pages; a flag
  takes the name of its macro in Linux's ``ieee80211_radiotap.h``, or in
  Wireshark where Linux defines none, and radiotap.org's wording where neither
  does. The 802.11 MAC frame behind the header is dissected as
  :class:`~pcapkit.protocols.link.ieee802_11.protocol.IEEE802_11`, below, looked up in
  ``Radiotap``'s own registry under
  :attr:`LinkType.IEEE802_11 <pcapkit.const.reg.linktype.LinkType.IEEE802_11>`,
  and :func:`~pcapkit.foundation.registry.protocols.link.register_radiotap`
  replaces that dissector (:issue:`2575`, :pr:`2607`).

* **Added** -- :class:`~pcapkit.protocols.link.ieee802_11.protocol.IEEE802_11`, a
  dissector for the IEEE 802.11 MAC header of a protocol version 0 frame,
  which :class:`~pcapkit.protocols.link.radiotap.protocol.Radiotap` dispatches to
  (:issue:`2575`, :pr:`2607`), as do PCAP and PCAP-NG frames of
  ``LINKTYPE_IEEE802_11`` (105) (:issue:`2608`, :pr:`2632`). It reads Frame Control, the Control Frame
  Extension and S1G Beacon layouts included, and the address, sequence, QoS
  Control and HT Control fields each frame type carries; a Control frame of a
  subtype it does not model, and an Extension frame, are read as the minimal
  header. The frame body is kept as :class:`~pcapkit.protocols.misc.raw.protocol.Raw`,
  with the FCS and radiotap's pad octets where captured, as ``Radiotap``
  decodes the Flags that mark them but does not pass them on, and any other
  protocol version is refused. The frame types and subtypes are
  :mod:`pcapkit.const.ieee802_11`, from hand-maintained tables of IEEE Std
  802.11-2020's Table 9-1.

* **Added** -- :class:`~pcapkit.protocols.internet.icmpv4.protocol.ICMPv4` (:rfc:`792`)
  and :class:`~pcapkit.protocols.internet.icmpv6.protocol.ICMPv6` (:rfc:`4443`), on an
  abstract :class:`~pcapkit.protocols.internet.icmp.protocol.ICMP` base, for IP
  protocols 1 and 58, which were kept as
  :class:`~pcapkit.protocols.misc.raw.protocol.Raw` (:issue:`2436`, :pr:`2446`); a
  protochain names ``ICMPv6`` where it named ``IPv6_ICMP``. Echo, Destination
  Unreachable, Time Exceeded and Parameter Problem bodies are decoded, and
  ICMPv6's Packet Too Big; every other type, Neighbor Discovery and MLD
  included, keeps its body raw. ICMPv4 takes the plain ``ICMP`` of :rfc:`792`
  as its ``id()`` and alias.
  :func:`~pcapkit.foundation.registry.protocols.internet.register_icmp_type` registers a
  message-body parser. The type and code registries are
  :mod:`pcapkit.const.icmp` and :mod:`pcapkit.const.icmpv6`, crawled from IANA.

* **Added** -- IGMPv1 (:rfc:`1112`), IGMPv2 (:rfc:`2236`) and IGMPv3
  (:rfc:`3376`), as :class:`~pcapkit.protocols.internet.igmpv1.protocol.IGMPv1`,
  :class:`~pcapkit.protocols.internet.igmpv2.protocol.IGMPv2` and
  :class:`~pcapkit.protocols.internet.igmpv3.protocol.IGMPv3`, each named after its
  module (:issue:`2529`, :pr:`2542`), on an abstract
  :class:`~pcapkit.protocols.internet.igmp.protocol.IGMP` base bound at IP protocol 2,
  which picks the version from the message type alone except for a Membership
  Query: one of 8 octets is IGMPv1 if its Max Resp Time is zero and IGMPv2
  otherwise, one of 12 or more IGMPv3 (:issue:`2439`, :issue:`2448`,
  :pr:`2444`, :pr:`2465`). An IGMPv3 Query carries its source list and a
  Membership Report its group records, and an IGMPv3 Query's Max Resp Code and
  QQIC are decoded from their floating-point form. An IGMPv3 message the
  capture cut short, a Report cut inside its group records included, parses
  and rebuilds as captured, whether parsed on its own or carried by IPv4, and
  IGMPv3's ``make()`` takes ``num_group_records``, from the record count to
  ``0xFFFF`` (:issue:`2650`, :issue:`2660`, :pr:`2662`, :pr:`2672`). The
  octets it lacks read as zeros, in the group record the cut lands inside
  included, and a Report's header schema cut inside the Additional Data past
  its records packs back as captured (:issue:`2686`, :issue:`2687`,
  :pr:`2701`); no group record past the cut is read, however the Report is
  framed (:issue:`2756`, :pr:`2758`), and no source address past it either, in
  a Query or a group record. A Query's data model carries ``num_sources``,
  which ``make()`` takes, so one cut inside its sources keeps the count it
  declared and one whose sources are edited recounts them (:issue:`2760`,
  :pr:`2766`). A Report parsed on its own sizes its
  group records by its record count, so one cut before the records it counts
  reads ``TRUNCATED``, as it does behind IPv4, holding the records captured
  and none made up, and a count no IP payload could carry raises
  :exc:`~pcapkit.utilities.exceptions.ProtocolError` (:issue:`2711`,
  :pr:`2738`); one cut inside a counted record reads quietly (:issue:`2749`,
  :pr:`2755`). Any other message, a 9- to 11-octet Query included, is kept as
  :class:`~pcapkit.protocols.misc.raw.protocol.Raw`.
  IGMPv1 takes the plain ``IGMP`` of :rfc:`1112` as its ``id()`` and alias, and
  IGMPv2's and IGMPv3's ``id()`` are their own names alone, ``('IGMPv2',)`` and
  ``('IGMPv3',)``; the base's is ``('IGMP', 'IGMPv2', 'IGMPv3')``, each
  member's canonical name (:issue:`2512`, :pr:`2506`, :pr:`2518`). IGMPv2's
  and IGMPv3's ``name`` carries the version,
  ``'Internet Group Management Protocol version 2'`` say, while IGMPv1's, as
  in :rfc:`1112`, does not (:issue:`2558`, :pr:`2590`). The registries are
  :mod:`pcapkit.const.igmp`: the types crawled from IANA, the group record
  types from a hand-maintained table.

* **Added** -- construction through a versioned family's base:
  :class:`~pcapkit.protocols.internet.ip.protocol.IP` and
  :class:`~pcapkit.protocols.link.l2tp.protocol.L2TP`, which raised :exc:`TypeError` in
  1.5.x, and the :class:`~pcapkit.protocols.internet.icmp.protocol.ICMP`,
  :class:`~pcapkit.protocols.internet.igmp.protocol.IGMP` and
  :class:`~pcapkit.protocols.link.linux_sll.protocol.LinuxSLL` bases above give a member,
  never an instance of the base, on parsing octets, building from fields and
  ``from_data`` (:issue:`2574`, :pr:`2639`). The ``version`` keyword names the
  member. Without it, IP's, IGMP's and L2TP's octets give the member they
  describe, and ``from_data`` the one its data names, IGMP's data models
  carrying a ``version`` for it. Building from fields without it raises
  :exc:`~pcapkit.utilities.exceptions.ProtocolError`, whose message asks for
  ``version``, and so do ICMP and Linux cooked-capture octets, which carry no
  version; their ``from_data`` on a :class:`dict` raises it too, as does a
  version a family has no member for, such as L2TP's ``3``. A member built
  directly takes ``version`` as well, which must be its own. HTTP's base follows
  the same rules, a breaking change given below (:issue:`2628`, :pr:`2651`).
  IPv4 and IPv6
  check the Version field before the rest of the header, so octets of the other
  version raise ``[IPv4] invalid version: 6`` say, where IPv4's error named
  whichever field they broke first.

* **Added** -- :class:`~pcapkit.protocols.transport.dccp.protocol.DCCP` (:rfc:`4340`)
  for IP protocol 33, which was kept as
  :class:`~pcapkit.protocols.misc.raw.protocol.Raw` (:issue:`2489`, :pr:`2593`). It
  reads and builds the generic header with short and long sequence numbers,
  the fields of every packet type, DCCP-Listen (:rfc:`5596`) and the options;
  the Data Checksum option's CRC-32c is recorded rather than checked. Its
  checksum is verified and computed as TCP's is, below, over the enclosing IP
  layer's pseudo-header and the part of the packet its Checksum Coverage
  gives (:rfc:`4340#section-9.2`): a coverage running past the packet is
  ``INVALID`` and warns, and a ``make()`` that computes the checksum writes a
  coverage reaching the end of the packet as 0, as Linux did.
  :func:`~pcapkit.foundation.registry.protocols.transport.register_dccp` registers a
  port's dissector, and
  :func:`~pcapkit.foundation.registry.protocols.transport.register_dccp_option` an
  option parser. The registries are :mod:`pcapkit.const.dccp`, crawled from
  IANA. Its ``make()`` refuses a value a field cannot hold with
  :exc:`~pcapkit.utilities.exceptions.ProtocolError` naming the field
  (:issue:`2614`, :pr:`2670`), and an option given as empty raw octets
  (:issue:`2723`, :pr:`2728`).

* **Added** -- :class:`~pcapkit.protocols.application.tls.protocol.TLS` (SSLv3 and TLS
  1.0 to 1.3) at TCP 443 and :class:`~pcapkit.protocols.application.dtls.protocol.DTLS`
  (DTLS 1.0, 1.2 and 1.3) at UDP 5684, on an abstract
  :class:`~pcapkit.protocols.application.ssl.protocol.SSL` base (:issue:`2437`,
  :pr:`2441`). Each reads every version of its record layer and reports it
  through ``alias``, as :class:`~pcapkit.protocols.link.arp.protocol.ARP` does by
  operation, telling 1.3 apart by its ``supported_versions`` extension;
  ``id()`` stays ``('TLS',)`` or ``('DTLS',)``. A cleartext handshake record is
  decoded -- ClientHello and ServerHello down to their cipher suites,
  compression methods and extensions, EncryptedExtensions down to its
  extensions, any other message at type and length -- as are an alert and
  ChangeCipherSpec, while encrypted records stay opaque octets. An extension's
  body is read and built for ``server_name``, ``supported_groups``,
  ``signature_algorithms``, ALPN, ``supported_versions`` and ``key_share``, a
  HelloRetryRequest's included, and kept as octets for any other type or for a
  body its parser rejects, which logs nothing;
  :func:`~pcapkit.foundation.registry.protocols.application.register_tls_extension`
  registers a parser and constructor for a further type (:issue:`2514`,
  :pr:`2595`). ``make()`` refuses a value too wide for its field, in the record
  header or in the content it builds, with
  :exc:`~pcapkit.utilities.exceptions.StructError` (:issue:`2614`, :pr:`2638`),
  and a name, or a code too wide, for an enumeration field with
  :exc:`~pcapkit.utilities.exceptions.ProtocolError`, as the other makers do,
  below (:issue:`2594`, :pr:`2692`).
  Each whole TLS record in a TCP segment is a layer of its own,
  the previous record's payload, so each alias names its own version --
  ``TCP:TLS 1.3:TLS 1.2`` -- and one that fails to decode is
  :class:`~pcapkit.protocols.misc.raw.protocol.Raw` with the rest of the segment
  (:issue:`2517`, :pr:`2537`).
  :class:`~pcapkit.protocols.application.sslv3.protocol.SSLv3`, in
  :mod:`pcapkit.protocols.application.sslv3` (:issue:`2529`, :pr:`2602`),
  exists for explicit construction only. A record split across TCP segments is
  not reassembled and stays :class:`~pcapkit.protocols.misc.raw.protocol.Raw`. DTLS also
  reads and builds the DTLS 1.3 unified-header records of
  :rfc:`9147#section-4.1` (:issue:`2467`, :pr:`2494`) and :rfc:`9146`
  ``tls12_cid`` records. A
  :class:`~pcapkit.protocols.application.dtls.protocol.DTLSContext`, given to
  ``extract()`` as its ``context``, resolves the connection ID of a
  ``tls12_cid`` record, or of a unified-header record with its ``C`` bit set
  (:issue:`2625`, :pr:`2643`), from those the capture's hellos negotiate in
  their ``connection_id`` extension, which TLS and DTLS both decode, or from
  the ``cid_length`` the caller gives it, and one it cannot resolve stays Raw.
  An ID a DTLS 1.3 ``NewConnectionId`` issues is encrypted, so only the caller
  can give it. A unified-header record's ``info`` carries its ID as ``cid``,
  :data:`None` when the ``C`` bit is clear, as ``length`` is when the ``L`` bit
  is, so that the one header keeps one data model, as settled on
  :issue:`2625`; its ``make()`` takes a ``cid`` and sets the ``C`` bit.
  A ``tls12_cid`` record's schema and data model are ``DTLSCIDCiphertext``, in
  the DTLS package, and the extension's data model is ``ConnectionId``, in the
  SSL package's (:issue:`2515`, :pr:`2631`, :pr:`2641`).
  Each whole DTLS
  record in a UDP datagram is likewise a layer of
  its own -- a DTLS 1.2 record then a DTLS 1.3 unified-header record read
  ``DTLS 1.2:DTLS 1.3`` -- a unified-header record with no length running to
  the end of the datagram, and one that fails to decode is
  :class:`~pcapkit.protocols.misc.raw.protocol.Raw` with the rest of the datagram
  (:issue:`2535`, :pr:`2603`). The content, handshake and extension types are
  :mod:`pcapkit.const.tls`, crawled from IANA (:issue:`2495`, :issue:`2514`,
  :pr:`2503`, :pr:`2595`). Each record, an SSLv2 one TLS adopts and a DTLS 1.3
  unified-header or ``tls12_cid`` record included, rebuilds from its
  ``to_dict()`` as from its data model (:issue:`2762`, :pr:`2764`).

* **Added** -- :class:`~pcapkit.protocols.application.sslv2.protocol.SSLv2`, a dissector
  for SSL version 2 (draft-hickman-netscape-ssl-00), whose record layer shares
  nothing with TLS's (:issue:`2457`, :pr:`2466`). It is bound to no port: on
  TCP 443 a segment's first record that TLS rejects is tried as SSLv2, and
  kept only as a complete CLIENT-HELLO or SERVER-HELLO whose length fields
  agree, so anything else stays :class:`~pcapkit.protocols.misc.raw.protocol.Raw`; a
  kept one drops the rejected TLS trial's warnings (:issue:`2525`,
  :pr:`2537`). Each whole record after the first in a TCP segment, whatever
  its message type, is a further SSLv2 layer, the previous record's payload,
  as with TLS -- a ``CLIENT-HELLO`` then a ``CLIENT-MASTER-KEY`` read
  ``SSLv2:SSLv2`` -- and one that fails to decode is
  :class:`~pcapkit.protocols.misc.raw.protocol.Raw` with the rest of the segment
  (:issue:`2567`, :pr:`2585`). Its constants are :mod:`pcapkit.const.sslv2`,
  from a hand-maintained table.

* **Added** -- dissection of every whole HTTP/2 frame in a TCP segment: each
  after the first, which was kept as :class:`~pcapkit.protocols.misc.raw.protocol.Raw`,
  is a further :class:`~pcapkit.protocols.application.httpv2.protocol.HTTPv2` layer, the
  previous frame's payload, as with TLS -- a ``SETTINGS`` then a
  ``WINDOW_UPDATE`` frame read ``TCP:HTTP/2:HTTP/2`` (:issue:`2536`,
  :pr:`2609`). One that fails to decode is
  :class:`~pcapkit.protocols.misc.raw.protocol.Raw` with the rest of the segment and
  the parser's ``error``, and a frame the segment ends inside stays
  :class:`~pcapkit.protocols.misc.raw.protocol.Raw` with none. A parse told to stop at
  HTTP/2 keeps the rest of the segment raw, and
  :data:`~pcapkit.utilities.config.FRAME_LAYER_LIMIT` bounds how many frames
  are dissected.

* **Added** -- :class:`pcapkit.foundation.reassembly.dtls.DTLS`, exported as
  ``DTLS_Reassembly``, which reassembles a DTLS handshake message fragmented
  across records (:rfc:`6347#section-4.2.3`), keyed by the UDP 4-tuple and the
  epoch, accepting overlapping fragments and holding a buffer until it
  completes (:issue:`2440`, :pr:`2451`). It is opt-in, as ``dtls=True`` with
  ``reassembly=True`` to :class:`~pcapkit.foundation.extraction.Extractor` or
  :func:`~pcapkit.interface.core.extract`, and runs on the default engine
  alone, fed by :func:`~pcapkit.toolkit.pcap.dtls_reassembly` and its
  :mod:`pcapkit.toolkit.pcapng` counterpart from the first record of each
  datagram only; any other engine turns it off with a warning.
  :func:`~pcapkit.foundation.analysis.dtls.dtls_handshake` decodes a
